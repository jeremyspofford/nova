**2026-11-06 · Models · Computers that sleep, and wake when work needs them**
- What changed: each compute computer now has a sleep policy you choose on its Models screen, in a new last section, "Sleep and wake". "When it's idle" is Never sleep, or sleep after 15, 30, 60 or 120 minutes. "When work needs it" is Nova wakes it, or Wait until it's turned on. The computer's own device agent enforces the policy with a new, sixth verb, `power`. It takes only hold, release or sleep, and only for its own machine. While Nova has work running or queued there, a model it loaded is still in memory (5 minutes), or a service is placed there, the hub's heartbeat answer says hold, and the agent stops the operating system from sleeping (systemd-inhibit, caffeinate, SetThreadExecutionState). When nothing of Nova's has run there and no one has touched the keyboard or mouse for the chosen time, the agent checks again (not in safe mode, no workload being installed or started, still no hold). It then tells the hub it is going to sleep, so the hub shows it asleep at once, and suspends the machine. Agents now also report whether each wired card has Wake-on-LAN on (ethtool or the card's wakeup file on Linux, `womp` on macOS; Windows and Wi-Fi report unknown). A card with it off isn't woken. When work routed to a sleeping computer's role needs it, Nova wakes it, waits for its heartbeat and its Ollama, and checks again that the model still fits on what it reports now. If it didn't wake, or the model no longer fits (a game holds the GPU), another awake computer of yours where the role's model fits runs it, with a note: "Dell desktop didn't wake, so qwen3:8b on Small tower answered." If none can, local-only work waits on your devices. Local-first work now asks before the cloud: "Use the cloud model this once". Before, it went to the cloud with a note. If the computer checks in but its Ollama doesn't answer within a minute, Nova says so and opens a problem. The Models screen shows the approved states: Asleep, wakeable (with the measured wake time), Asleep or away (with the reason), Waking (with the task and how long Nova will wait), Awake and Loading, and Couldn't wake (what happened, what Nova does instead, and "Try waking it again"). Settings › Models names each route's wake state: "Coding → Dell desktop (asleep, wakeable; waking took 38 s)".
- What you can now do: let a GPU computer sleep when nothing needs it and have Nova wake it for the work that does. You can also answer a waiting local-first task with "Use the cloud model this once".
- Still unfinished: a computer on a network without the hub can't be woken (relaying a wake from another always-on device is open question 2, deferred). On Windows, the idle time is read in the agent's own session, so an agent running as a service may never see the machine as idle. The Wake-on-LAN reading on Windows is always unknown. None of this has been tried on a real machine: suspend, inhibit and idle reading are covered only by stand-ins. The services track's placement doesn't yet treat a computer that sleeps by design as "down, wakeable".
- Checked: the ADR's 16 golden cases are tests: cases 2, 3, 4, 5, 11, 12 and 13 in the hardening PR's file, the rest in `tests/core/wol-golden.test.ts`. They run with a recorder in place of the network, a fake clock for the waits, and stand-ins for the operating system's suspend, inhibitor and idle readings. A UI test changes both sleep choices on a computer's Models screen in the app and reads the reasons back. See the PR's gate table.
