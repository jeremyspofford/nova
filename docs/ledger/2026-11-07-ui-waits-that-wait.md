**2026-11-07 · Tests · UI tests' readiness waits actually wait (the phone navigation failure)**
- What changed: nothing in Nova itself. The intermittent "navigation reachability: phone" failure (#356's CI: the crawl recorded the conversation page without its /schedules link) came from the tests' own readiness check never waiting. Playwright's `page.waitForFunction` doesn't await an async check: a Promise counts as true, so `waitForFunction(async () => false)` returns at once. The crawl's `drawn()` used one, as did seven other waits in four test files (two backups tests, the health/caps service-worker test, the fold helper). A new `until()` in tests/ui/support.ts polls `page.evaluate`, which does await, with the same 30 s default; all eight now use it. With a check that really runs, two more gaps showed and are closed: the crawl's readiness didn't count a view's "nothing here yet" line (Activity's empty state) as drawn, so it now does; and it now also waits for a conversation's deferred fade-in (`#thread.no-anim`, then two frames, as the m9 and fold helpers already did) and, after a tap on a link, for the address to change before checking readiness, so it never reads the page it just left.
- What you can now do: nothing new. The UI gate stops failing at random on this, and the waits these tests claim are real.
- Still unfinished: nothing known. With the waits real, a test that had been passing on a no-op wait could now show a real failure; CI's full UI gate is the check.
- Checked: tests/ui/navigation-drawn.test.ts holds the frame that starts a conversation's fade for 300 ms, so the window is open every run. It fails with `drawn()` on the old `waitForFunction` and passes with `until()`; it also proves `waitForFunction` resolves on an async false while `until()` waits. The navigation crawl (phone and rail), the navigation guards, the backups, health/caps and fold tests all pass in iso.sh (39/39).
