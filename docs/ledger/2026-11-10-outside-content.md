**2026-11-10 · Security · Memory waits after outside content, and every service reply is screened (F-033, F-037, D6)**
- What changed: src/runner.js keep() held a memory change (`<remember>`, `<note>`, `<forget>`) for the person only when the run was tainted. Command output and a connected service's reply rarely or never tainted it, so a paraphrased instruction in either could write memory that every later prompt reads. Now the runner works out, at the start of each run, which outside content the conversation has seen (Runner.outputSeen), and adds to it as each read is screened. keep() holds every memory change once there is any, as a memory candidate whose taint names what was seen ("a command’s output", "a web page", "a file from outside", "a connected service’s reply"), so the Memory view's "Waiting for your OK" shows it unchanged. Narrowed by the owner's ruling of 2026-11-10: only screened outside content holds (web pages, search results, mail, files Nova didn't write, command output, service replies). Nova's own read-only status tools (nova_capture, nova_schedules, nova_settings, nova_instance, code_status, infra_status, network_status) hold only when their screen flagged the output, the T3 pattern, and Nova's own unscreened tools (the person's own files, schedules, skills, helpers) never do. The same conversation-wide condition also makes a standing-file change ask (T3); before, only tool output in the current run did. service_call (and home_call, its older name) was never screened: outsideRead returned null. Its reply is now screened on every call, done or failed, as `connector` content from "the <service> service", and the model sees only the screened form. Under owner ruling D6 option (b) it taints the run only when the screen found something (a check flagged it, or a trusted model wasn't sure), the same rule as a command's output.
- What you can now do: rely on outside content never quietly changing what Nova remembers. Nova checking its own status, and an ordinary service reply, don't make you review every memory or approve every later step.
- Still unfinished: the hold lasts for the whole conversation, so a long main conversation that has read anything from outside holds every memory change for review. A report handed in from a helper or a schedule doesn't count; it brings its run's taint, as before. Without a trusted screen model, a paraphrased injection in a service reply or status output that no check matches doesn't taint, and the status output then doesn't hold memory either.
- Checked: tests/ingest/outside-content.test.js, 9 tests. Memory is held after a command's output (in that turn and the next), a web page, a file Nova didn't write, and a service reply, each naming what was seen. After only a status tool (nova_capture), memory is written. After a status tool whose output the screen flags, memory is held. With no outside content, memory is written. A flagged service reply taints, and a later command asks even with commands set to yes. A clean service reply is screened, doesn't taint, and the command runs.
