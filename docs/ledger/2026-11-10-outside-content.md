**2026-11-10 · Security · Memory waits after tool output, and every service reply is screened (F-033, F-037, D6)**
- What changed: a memory change (`<remember>`, `<note>`, `<forget>`) was held for the person only when the run was tainted (src/runner.js keep), and command output and a connected service's reply rarely or never tainted it, so a paraphrased instruction in either could write memory that every later prompt reads. Now the runner works out, at the start of each run, which tool output the conversation has seen (Runner.outputSeen: every tool item with a result, in any turn), adds to it as each tool runs, and keep() holds every memory change once there is any, as a memory candidate whose taint names what was seen ("a tool’s output", "a connected service’s reply"), so the Memory view's "Waiting for your OK" shows it unchanged. The same conversation-wide flag now drives T3's standing-file rule, which looked only at the current run. service_call (and home_call, its older name) was never screened (outsideRead returned null). Its reply is now screened as `connector` content from "the <service> service" on every call, done or failed, and the model sees only the screened form. Under owner ruling D6 option (b) it taints the run only when the screen found something (a check flagged it, or a trusted model wasn't sure), the same rule as a command's output.
- What you can now do: rely on a tool's output or a service's reply never quietly changing what Nova remembers, and on an ordinary service reply not making every later step ask.
- Still unfinished: the hold covers every tool, Nova's own read-only ones too, and lasts for the whole conversation, so a long main conversation that has used any tool holds every memory change for review. A report handed in from a helper or schedule doesn't count as tool output; it brings its run's taint as before. Without a trusted screen model, a paraphrased injection in a service reply that no check matches reaches the model as held-back data and doesn't taint.
