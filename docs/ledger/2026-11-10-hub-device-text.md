**2026-11-10 · Security · The hub cleans what a paired device says about itself, once, where it comes in**
- What changed: a device's reports (heartbeat versions, any service's workload said and failed, hardware, problem detail, capture paused, a capture batch's source, its join name and platform) were stored and shown with only C0 controls removed, some with nothing removed: terminal escapes, C1 controls, bidi overrides and zero-width characters were kept. src/core/mesh/device-text.ts cleans every string in a report once at the start of the heartbeat, report and capture-status handlers (escapes out, controls to a space, format characters and lone surrogates out, 1000 characters and 8 levels at most), so any service added later is covered with no path of its own. Signed batch fields are cleaned after the signature check. Each handler's own shorter limits still apply; an honest device's text is unchanged. The screens already escaped device text (no XSS found); a new UI test guards that.
- What you can now do: trust that a broken or hostile device can't put escape codes, invisible text or text that reads backwards on your hub's screens.
- Still unfinished: capture item content and /mesh/inbox content are bounded but not stripped of bidi characters (content, not reports; inbox content isn't shown today). A compromised device can vary the device id it claims in a capture batch to raise a new problem on every refused request, since the limit is keyed on the refusal text.
- Checked: 8 new cases fail on the base and pass (a 900 kB string with escapes, RLO, NUL, CR LF, isolates and zero-width characters through each entry point); mesh, device, workloads, topology, capture, reset, services and ui-devices suites; m4a-devices UI test; typecheck.
