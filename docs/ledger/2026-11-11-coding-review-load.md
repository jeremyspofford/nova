**2026-11-11 · Pipeline · The coding-review preview tests check the processes, not a port another test can take (#509)**
- What changed: the two "review 2" tests in tests/core/coding-review.test.ts concluded that a preview had stopped because nothing answered HTTP at its port 500 ms (or 2.5 s) later. That port came from the kernel's ephemeral range, which on this machine (WSL in mirrored networking) is 41890 to 45985, and a full `npm test` keeps many servers taking and freeing ports there. Measured under the core and acceptance suites: a port freed and asked again 500 ms later was answered by someone else's server 4 times in 300 (0 in 100 on a quiet machine). Nova had stopped the preview; another test's server answered at its old port, and the test read that as "not stopped". Nova was right: `stopRecorded` (src/core/coding/preview.ts:171) sends SIGKILL to the recorded group synchronously inside `start()`, and the exit handler in src/core/coding/index.ts:561 signals the group in the same callback that reaps its shell. The tests now ask the kernel instead. After a restart, the recorded leader has SIGKILL pending (/proc/<pid>/status ShdPnd) the moment `start()` returns, and the test then waits for the group's 'close' event and checks it was SIGKILL. The process with another start time must still be running: the test's own SIGTERM is what ends it. When a preview's shell exits, the test waits for the record to say it isn't running, then checks that every process left in its group has SIGTERM or SIGKILL pending or is gone. The fixed sleeps (500, 300 and 2500 ms) are gone, and no assertion was dropped or loosened. Nothing in src/ changed.
- What you can now do: run `npm test` beside the Docker UI gate or other agents' suites without these two tests failing because someone else's server took a freed port.
