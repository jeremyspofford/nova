**2026-11-11 · Performance · The status icon redraws its animations at 20 fps, which cuts a long thread's scroll work from 5.9 to 3.2 ms p95 (#486)**
- What changed: on the owner's ruling of 2026-11-11 ("Do not change the budget. 8 ms stands. Fix the render instead"), ui/js/status-icon.js now redraws an icon that is animating (a loop, a morph, the success flourish) at ANIMATION_FPS (20), not on every display frame. Each redraw copies the shader's picture out of the shared WebGL canvas into the icon's own canvas, and without a GPU that copy is a synchronous readback: most of each scroll frame's work in the #486 profile. A change of state, anything else that marks an icon dirty, its first paint, and the frame an animation ends on are still drawn at once, and reduced motion is unchanged. Nothing about the artwork or its treatments changed. Before throttling, the ruling's alternatives were checked. CSS can't express the treatments: the radius-falloff twirl, the luminance gradient-map tint and the black core pinned under every treatment are per-pixel. An OffscreenCanvas WebGL context handing each frame to the icon by transferToImageBitmap and a bitmaprenderer context didn't remove the readback on a machine without GPU compositing: the wait moved into transferToImageBitmap (1.0 to 1.6 ms of a 64 px frame), and with icons of several sizes it cost more than today's copy (3.2 against 2.3 ms median per frame). So nothing was eliminated, and the one shared WebGL context is kept.
- What you can now do: scroll a long thread with about a third of the page work per frame it took before. On the same machine and in the CI image, page work was 3.23 ms p95 (median of 6 runs) against 5.86 ms on main (7 runs), and the typical frame dropped from 4.43 to 0.91 ms. That is under half the 8 ms budget, which is unchanged.
- Still unfinished: two in every three scroll frames are now light, but the third still carries one readback, about 1 to 2 ms on a quiet host, so the p95 frame is a copy frame. The only way to take the readback off the page's main thread is to render in a worker (an OffscreenCanvas transferred to a worker). status-icon.js is served before pairing on the owner's condition that it stays self-contained, which tests/public-status-icon.test.js enforces and which forbids workers, so that would be a question for the owner, not an edit. Local timings also vary with load on the Windows host, which the quiet-machine readings don't see (#501).
- Checked: a new UI test in tests/ui/status-icon.test.ts (Chromium with software WebGL). A looping icon is redrawn at no more than 20 fps and keeps moving. A change is drawn on the next frame. A morph to a still state ends drawn exactly as a fresh icon of that state. A still state, and a looping state under reduced motion, aren't redrawn. Forty more icons still use one WebGL context. The throttle bounds fail on main, which redraws on every frame. Also the scroll profile (6 fix and 7 main runs in the CI image, plus 4 runs that timestamped every icon copy in the trace: exactly 134 copies in 402 frames, one per frame at most, always the rail icon on the shader path), typecheck, token lint, theme check, changelog check, npm test, the UI gate in Chromium and WebKit, and the shots walkthrough (see the PR).
