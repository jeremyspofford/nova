**2026-11-10 · Security · A paired device can't flood the problems list or the log**
- What changed: a refused capture batch raised a problem limited per session and refusal text, and that text carried what the batch claimed (a device id, item counts), so a compromised device could vary it to raise a new problem, and a never-cleared map entry, on every request; the warn log line had no limit. Refused task requests, stale settings changes and safe-mode flips from a device raised a problem each, with no limit. One shared ReportThrottle (src/core/mesh/limiter.ts) now allows one report per authenticated device and fixed kind every ten minutes, counts what it held back, and keeps at most 1,000 keys; capture refusals, spokes problems and enrollment's per-address reports all use it. The first report of each kind is still full; the next says how many more there were. The device still gets the exact reason, and every refused inbox item is still kept and listed.
- What you can now do: rely on the problems list staying readable even if a paired device misbehaves.
- Still unfinished: each new client address rate-limited at enrollment still raises its own problem (per-address by design; a hub-wide cap would close it). A refused task's reason can quote the device's words without deviceText. logs/nova.log has no rotation.
