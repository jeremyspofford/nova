**2026-11-10 · Devices · A copy started alongside keeps its port, and a workload that keeps dying says why**
- What changed: the device agent picked a shadow or alongside copy's port by binding port 0 and closing it, which hands the port back to the OS for any other program's port-0 bind before the workload binds it by number; the copy then crashed three times and the agent gave up (the root of the M10h pilot failure under load). sidePort() now picks 20000-32000, below every default ephemeral range and out of Linux's configured one, skipping ports any installed manifest names or a running copy holds, and checks it binds. Workloads' stderr is now read into an 8 KiB tail, and safe mode appends the last exit and the end of stderr, one line, at most 300 characters, with escapes, control, format and direction characters removed and stack frames dropped. This is generic: any workload a person adds.
- What you can now do: see on the hub why a workload stopped (for example "exited with code 1 and wrote: ... EADDRINUSE ..."), and run a new version alongside the live one without it losing its port.
- Still unfinished: the hub does not yet bound or clean the failed/said text a device sends; a workload's stderr can carry whatever it logs, to the person's own hub only. On Windows a stopped workload's children can outlive it (process groups), as before.
