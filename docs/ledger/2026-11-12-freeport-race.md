**2026-11-12 · Coding · The preview binds a port the kernel gives it, and its link is confirmed to be its own**
- What changed: a coding run's preview used to be given a port Nova had found free and closed again, so another program could take it first: the preview then failed to start, or Nova's readiness check and the link it showed reached that other program (#516). On Linux the preview now gets PORT=0 and binds a port the kernel assigns as it binds, so no port is ever free in between. Nova reads from the kernel which loopback port the preview's own process group holds a listening socket on, asks there, and accepts the answer only if that same socket is still the group's afterwards; nothing the previewed app prints or serves decides which port is its own. Off Linux the preview starts as before. The other caller of freePort, the services supervisor, keeps its fixed-port contract, but its health and contract checks now count an answer only when the port is held by the service's own process group, before and after the request. docs/plans/M10c.md and M10e.md say so.
- What you can now do: get a working preview link on a busy machine, and trust that the link Nova shows reaches the preview it started; a supervised service is never taken as healthy, or routed to, because some other program answered on its port.
- Still unfinished: off Linux (no /proc) the preview's port is still found free and closed before it binds, so the race remains there. A preview command that refuses PORT=0 now fails to start where it used to work; most servers read 0 as any free port. A service's ports are still found free and closed before it starts, so a taken port still fails that start (now without mistaking the other program for the service); removing that needs a change to the service contract.
