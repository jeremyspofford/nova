# M7.5 — Demo

Turn on Wake-on-LAN and power-on after a power cut on a test device, with the owner's approval,
and roll the change back; then try a boot entry the machine never comes back on and watch the
watchdog put the default back; then power cycle a machine through its BMC. The device is the real
`novad` with its fake BIOS and bootloader (two JSON files, `novad`'s `fake` backends), so the
Hub ↔ `novad` protocol, the Hub-signed authorizations and `novad`'s watchdogs run for real while
nothing on this machine changes or restarts. The BMC is the fake Redfish server from the tests.
Everything runs offline.

## Preconditions
- Linux; `npm ci && npm run build`; a fresh data directory.
- A `novad` build in a dist folder: `node scripts/cargo.mjs build --release`, then
  `mkdir -p /tmp/nova-dist && cp services/novad/target/release/novad /tmp/nova-dist/novad-linux-amd64`
  (`arm64` on an ARM machine).
- Open the Hub at this machine's LAN address (for example `http://192.168.1.20:7419`), not
  `localhost`: the Hub does not build an install command for a loopback address.
- The test machine: a fake BIOS, a fake bootloader and a fake `systemctl`. `novad` restarts a
  machine with `systemctl reboot`; the fake one first on its PATH only records the call, so this
  computer never restarts (as in J9.5). Run this, and the rest of the device's commands, in the
  terminal `novad` will run in:

  ```sh
  D=/tmp/nova-demo-device && mkdir -p $D/bin
  cat > $D/firmware.json <<'EOF'
  {
    "platform": { "vendor": "Nova Labs", "product": "Demo Desk PC", "biosVendor": "Nova",
                  "biosVersion": "1.0.4", "biosDate": "2026-09-01", "uefi": true },
    "adminPasswordSet": false,
    "requiresReboot": true,
    "settings": {
      "wol": { "vendorKey": "WakeOnLan", "value": "Disabled", "type": "enum", "allowed": ["Disabled", "Enabled"] },
      "powerOnAfterPowerLoss": { "vendorKey": "AcPowerRecovery", "value": "Off", "type": "enum", "allowed": ["Off", "On", "Last"] },
      "virtualization": { "vendorKey": "VirtualizationTechnology", "value": "Enabled", "type": "enum", "allowed": ["Disabled", "Enabled"] },
      "secureBoot": { "vendorKey": "SecureBoot", "value": "Enabled", "type": "enum", "allowed": ["Disabled", "Enabled"] }
    },
    "failWrites": []
  }
  EOF
  cat > $D/bootloader.json <<'EOF'
  {
    "entries": [
      { "id": "nova-6.8.conf", "title": "Nova Linux 6.8" },
      { "id": "nova-6.12-rc.conf", "title": "Nova Linux 6.12 (test kernel)" }
    ],
    "default": "nova-6.8.conf", "booted": "nova-6.8.conf", "oneshot": null
  }
  EOF
  printf '#!/bin/sh\necho "$*" >> %s/systemctl.log\n' "$D" > $D/bin/systemctl && chmod +x $D/bin/systemctl
  ```

- "The machine never came back" is played by stopping `novad` and moving its watchdog's deadline
  into the past (or waiting it out). This moves the deadline of `firmware/pending.json` or
  `boot/pending.json` in `novad`'s data folder:

  ```sh
  expire() { node -e 'const fs = require("fs"); const f = process.argv[1]; const m = JSON.parse(fs.readFileSync(f, "utf8")); const t = Date.now() - 5000; fs.writeFileSync(f, JSON.stringify({ ...m, deadline: new Date(t).toISOString(), deadlineMs: t }), { mode: 0o600 });' "$D/novad/$1/pending.json"; }
  ```

## Script
1. Start the Hub with the BMC redirect (needed for step 8 only):

   ```sh
   NOVA_HOST=0.0.0.0 NOVA_NOVAD_DIST=/tmp/nova-dist NOVA_DATA_DIR=$(mktemp -d) \
   NOVA_E2E_BMC_REDIRECT=192.0.2.80=127.0.0.1 \
   node --import ./e2e/support/bmc-redirect.ts apps/hub/src/main.ts
   ```

   The Hub refuses a BMC on loopback or on one of its own addresses, and the fake BMC can only
   listen on this machine; the preload sends just the TCP connection for `192.0.2.80` (a TEST-NET
   address) to it, while the pinning, the credentials and the approvals run for real. Open the
   setup link at the LAN address, **Finish setup**, **Skip setup**.
2. **Add the test device.** Sidebar → **Devices** → **Add device** → **Compute node** → **Create
   code**. Under "On a computer without a screen", the one-line command carries `--hub`,
   `--pairing` and `--pin`; run `novad install` here with those three and the short code on stdin:

   ```sh
   echo ABCD-EFGH | services/novad/target/release/novad install --hub http://192.168.1.20:7419 \
     --code - --pairing '…' --pin '…' --no-service --data-dir $D/novad --role compute \
     --name desk-pc --listen 127.0.0.1:7420
   ```

   It prints `Confirm this code on the Hub: 123 456`. The Hub shows "desk-pc wants to join": type
   the digits, **Approve**; the page says "desk-pc is added" and the command prints `Registered as
   device …`. Give `novad` the fake machine, allow it to restart (through the fake `systemctl`) and
   start it:

   ```sh
   node -e 'const fs = require("fs"); const [f, fw, boot] = process.argv.slice(1); const c = fs.existsSync(f) ? JSON.parse(fs.readFileSync(f, "utf8")) : {}; c.power = { ...c.power, allowActions: true }; c.firmware = { backend: "fake", fakePath: fw }; c.boot = { backend: "fake", fakePath: boot }; fs.writeFileSync(f, JSON.stringify(c, null, 2));' \
     $D/novad/config.json $D/firmware.json $D/bootloader.json
   PATH=$D/bin:$PATH services/novad/target/release/novad run --data-dir $D/novad
   ```

3. **Firmware changes are off.** Devices → desk-pc → **Firmware**: **Supported**, the platform
   ("Nova Labs Demo Desk PC", "Nova 1.0.4 (2026-09-01), UEFI", "Test backend (no real firmware)")
   and the settings Nova may change (an allowlist): Wake-on-LAN **Disabled**, After a power cut
   **Off**, Virtualization, Secure Boot. The tab says "BIOS and firmware changes are off." with
   **Turn it on in Settings → Devices**, and offers no plan; the Hub refuses one too
   (`firmware_disabled`).
4. **Turn them on, with consent.** Settings → **Devices** → "Firmware and boot": **Allow
   BIOS/firmware changes** asks first ("Allow BIOS and firmware changes on devices?": each change
   needs your approval here in Nova, and can be rolled back) → **Allow firmware changes**. "Allow
   changes that weaken security" stays off.
5. **The change, with approval.** Back to desk-pc → **Firmware** → "Plan a change": Wake-on-LAN
   **Enabled**, After a power cut **On** → **Plan the change**. The current change shows
   Disabled → Enabled and Off → On, **Planned**, "Takes effect after the device restarts.";
   `$D/firmware.json` still says `Disabled` and `Off`: a plan changes nothing. **Ask for approval**:
   the card "Approve this firmware change on desk-pc" says "Only you can answer this, in Nova: here
   or on the Approvals page. Chat channels, email links and agents cannot answer it." (**Open in
   Approvals** shows the same card there). **Allow once**: "Approved. Nothing has changed yet".
   **Apply…** lists "Wake-on-LAN: Disabled → Enabled" and "After a power cut: Off → On"; untick
   **Restart desk-pc now, with the watchdog** → **Apply to desk-pc**: "Applied to desk-pc."
   `$D/firmware.json` now says `Enabled` and `On`, **Read again** shows them, and the history lists
   the change as **Applied** with before and after.
6. **Roll it back.** On the applied change, **Roll back the change applied …**: "Wake-on-LAN: back
   to Disabled" → **Plan the rollback**. The rollback has its own Hub-only card ("Approve restoring
   the firmware settings of desk-pc") → **Allow once** → **Apply the rollback…** → **Roll back
   desk-pc**: "Rolled back on desk-pc."; `$D/firmware.json` is back to `Disabled` and `Off`.
   Optional: plan Secure Boot **Disabled (weakens security)**: the plan says "This weakens security:
   Secure Boot Disabled." and asking for approval is refused, because "Allow changes that weaken
   security" is off.
   Optional, the firmware watchdog: plan Wake-on-LAN **Enabled** again, **Ask for approval**,
   **Allow once**, **Apply…** with the restart ticked: "Applied. desk-pc is restarting with the
   watchdog armed.", and `$D/systemctl.log` says `reboot`. The machine "never comes back": stop
   `novad` (Ctrl+C), run `expire firmware` (or wait the watchdog's 10 minutes), start `novad`
   again. The change turns **Reverted by the watchdog** ("The device did not come back in time: its
   watchdog restored the previous settings.") and `$D/firmware.json` says `Disabled`.
7. **A boot entry that never comes up.** desk-pc → **Boot**: the entries the device lists
   ("Nova Linux 6.8", Default, Booted now; "Nova Linux 6.12 (test kernel)") and "Low-level boot
   changes are off." "New boot profile": name "Test kernel", entry "Nova Linux 6.12 (test kernel)",
   **Create profile**; **Try Test kernel on next boot** stays disabled ("Needs low-level boot
   changes on."). Settings → **Devices** → **Allow low-level boot changes** → "Allow low-level boot
   changes on devices?" → **Allow boot changes**. Back on **Boot**: **Try Test kernel on next
   boot** → Watchdog **2 minutes**, **Restart desk-pc as soon as you approve** ticked → **Ask for
   approval**. The Hub-only card shows Next boot: "Nova Linux 6.8" → "Nova Linux 6.12 (test
   kernel), once"; **Allow once**. It is sent at once: "desk-pc boots “Nova Linux 6.12 (test
   kernel)” once", the trial says **Trying**, `$D/bootloader.json` has `"oneshot":
   "nova-6.12-rc.conf"` with the default untouched, and `systemctl.log` has another `reboot`. Stop
   `novad`, run `expire boot` (or wait two minutes), start `novad`: the trial says **Back on the
   default**, "It did not come up on the entry in time, so it returned to its default entry.",
   `oneshot` is `null` again and **Make default…** is not offered.
8. **Out of band.** In another terminal start the fake Redfish BMC; it prints its port, user name,
   password and certificate fingerprint:

   ```sh
   node --input-type=module -e "const { startFakeRedfish } = await import('./packages/core/test/fixtures/oob/fake-redfish.ts'); const b = await startFakeRedfish(); console.log('port', b.port, '| user', b.state.username, '| password', b.state.password, '| fingerprint', b.pin);"
   ```

   Sidebar → **Devices**: "Out-of-band management" says **Off.** → **Open out-of-band
   management**: "Add a BMC" is disabled. **Turn on…** → "Turn on out-of-band management?" (every
   change waits for your approval in Nova) → **Turn on out-of-band management**. **Add a BMC**: name
   "Rack BMC", **Redfish**, address `127.0.0.1`, the printed port, user name and password, Device
   **desk-pc** → **Add BMC**: refused, "Enter the BMC’s own address on the network."; address
   `192.0.2.80` → **Add BMC**: "Rack BMC added." **Check the connection**: "Is this your BMC’s
   certificate?" with the printed fingerprint (in pairs, with colons); no credential has been sent
   yet. **Yes, it is my BMC’s…** → **Confirm the fingerprint**: "Certificate confirmed. The Hub may
   now send the BMC its credentials." **Read the power state**: "Power: On", a read with no
   approval. **Power cycle…**
   ("The BMC turns the machine off and on again at once.") → **Ask to power cycle**: the Hub-only
   card waits under "Waiting for you"; **Allow once**: the action log shows **Power cycle**,
   **Done**, "With your approval". desk-pc's page now has an **Out-of-band** tab for this BMC.
9. **The audit.** Settings → **Diagnostics** → Audit log lists the switches turned on
   (`devices.firmware.allowChanges`, `devices.boot.allowLowLevel`) and
   `device.firmware.plan|approval|apply|rollback|watchdog`, `device.boot.request|set|watchdog` and
   `device.oob.enable|endpoint.create|pin|power.status|power.cycle`; **Export audit log** has their
   before and after values.

## Expected results
- BIOS changes are impossible until "Allow BIOS/firmware changes" is on, and turning it on (or
  low-level boot, or out-of-band management) asks first and is audited with before and after.
- Each firmware change shows its diff, takes a snapshot, waits for a card only the signed-in owner
  can answer in Nova, and rolls back with its own approval; a change that weakens security needs a
  separate switch.
- A boot trial is a one-shot: the watchdog clears it when the machine does not come back on it in
  time, and the default entry never changes; a firmware change whose restart never comes back is
  restored the same way.
- Out-of-band management is off by default; the Hub sends a BMC credentials only after the owner
  confirms its certificate, and runs a power action only after the owner allows its card.
- Nothing on this computer changed or restarted: the BIOS and the bootloader are the two JSON
  files and every restart is a line in `systemctl.log`.
