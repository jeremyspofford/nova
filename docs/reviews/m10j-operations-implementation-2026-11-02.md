## Delivered behavior and API

Explicit trusted `CoreOptions.k3s` composition creates `K3sOperations`; absent this option the application remains supervisor/native and has no cluster routes. Metadata alone cannot make the missing launcher available. The ordinary `ServiceManager.plan` skips a k3s driver even if someone includes it in the generic driver list; native selection remains unchanged.

All new POST routes require existing `approver` access. `/api/v1/services/clusters/{cluster}/{service}` has:

- `/network`: exact `{version, expected}`. Resolves only a registered definition, checks capability/current approver/active hub/placement, collects actual expected state without effects, and creates an existing M10d snapshot/diff change on the **previously bound** network target. Existing `/tasks/{id}/approve` applies its tier-3 network task with explicit confirmation. Caller cannot supply target, URL, manifest, argv, credentials or a capability flag.
- `/deploy`: exact `{version, expected, network_change}`. Creates an internal WorkLedger task; it does not report Serving. The network reference is an existing `c` + 10-hex change ID. Exact canonical patch, rendered policy identity, target, verified tier-3 apply task, sealed snapshot/proposal and fresh target readback are required before workload effects. A network change is bound to one task through the existing ledger idempotency key; reuse with different inputs refuses, identical reuse returns the same task.
- `/promote` and `/rollback`: exact `{version, expected}`. Return WorkLedger tasks. Rollback version must equal approved `expected.previous`.
- `/replicas`: explicit 409 unsupported. No general scaling claim through the kept-resource stop port.
- `/tasks/{task}/retry`: exact `{}`; rechecks caller access and original task registration. Existing Ledger retry/approval behavior is retained. No automatic background replay on reconnect.

`expected` is the existing closed `ServiceExpectedState`: `{live, previous, assigned}`; assigned is null or `{version,want,at}`. All task and proposal bodies are strict; no raw ClusterTools operation can be selected by a caller. Read-only phones, unknown clusters, extra fields, forged `/tasks` creation and unsupported service semantics refuse.

## WorkLedger and execution contract

`k3s-operations` is a symbol-protected `LanedWorker`, one lane per cluster/service, external effects with commit points, existing confirmation verification and conservative `remote` egress. It respects the existing privacy gate (the loopback fixtures explicitly choose cloud-allowed; production does not silently loosen privacy).

Closed task inputs are exactly `{operation, cluster, namespace, service, version, artifact, registration, expected, network_change, actor}`. Operation is deploy/promote/rollback; artifact and registration are hashes of the immutable public definition and approved trusted registration; actor is console or the requesting device ID. No tool argv or credential value is persisted. All durable operation state is the existing task, task_event, report and verification data; no operation/approval queue or new DB table.

Ordinary deployment/promotion asks at tier 2; existing privileged service policy (console/secrets/OS permissions) gives tier 3; requested rollback is tier 2. Stateful/secret/OS-incompatible services already refuse through driver planning rather than receiving fabricated capability. Registration/joins/credential setup are not implemented publicly; their tier-3 authority has not been invented by this checkpoint.

Before any effect, the worker checks current configuration/definition digest, current requesting-device approver permission/trust, active-hub authority, driver capability and current placement. Driver deploy receives the approved expected state inside its actual serialization; the fixed child port atomically compares revision plus live/previous/assignment at mutation. Placement is recomputed after awaited network authorization, before the commit point, preventing floating placement from masking revocation of the previously selected device. Subsequent target mutations verify actual resource device IDs against current eligible placement.

Control-plane loss before effects reports blocked + `notStarted`, yielding actual Waiting with a plain reason, zero consumed attempts, preserved approval and the same task identity on explicit retry. `committing` precedes effects. The fixed port tags mutations with task ID and returns actual last-mutation evidence. Uncertain prepare or promotion is never replayed. An actual task-bound successful validate or rollback can reconcile on readback; an interrupted canary stays unverified Waiting even after selector equality and elapsed time. Only actual uninterrupted canary completion gets a durable `k3s_completed` event. Post-commit retries follow existing Ledger renewed approval policy. Restart recovery holds possible effects; cancellation before effects aborts safely, in-flight committed work refuses cancellation until it returns, and terminal cancelled tasks cannot retry.
