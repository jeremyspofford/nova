# M10g plan: hub promotion, planned and emergency, and the promotion drill

**Sources (binding):** `docs/plans/M10-orchestration.md` (Point 10, the M10g row of Order, the tiers
table, Point 9's candidacy, Hard limits) with the owner's decisions
(`docs/builder-packet/INPUT-2026-10-31-ORCHESTRATION-DECISIONS.md`): **Decision 2** (the roster's
lineage and the stable mesh name transfer; private keys never move; the roster pins every hub
candidate's key, each candidacy tier 3, so a cold promotion needs no re-pairing; epochs only rise; a
roll-back is epoch + 2) and **Decision 5** (no vault-key escrow; backups never contain keys; after a
cold promotion connectors are signed in again, and the sheet says so with the backup's time and what
was lost). The owner's own words: `INPUT-2026-10-31-SERVICE-ORCHESTRATION.md` point 10. The packet:
NOVA-SPEC §6 (tiers), CONTRACTS §5, LOCAL-FIRST-AND-DEVICE-MESH, ARCHITECTURE-AND-DECISIONS ADR-11
(one active hub). Tier numbers: 0 silent, 1 act and report with undo, 2 ask first, 3 explicit
confirmation every time.

## What is built

1. **Trust widened safely:** device agents pin every hub candidate the roster lists (Decision 2), and
   fencing treats every pinned candidate as a possible successor, so a cold promotion onto any
   candidate is followed by devices without pairing again, and the hub it replaced steps down.
2. **Planned promotion** ("Promote to hub" in Settings › Devices, tier 3), run by the hub as a chain
   of ledger tasks: pre-checks, catch-up, drain, transfer, demotion, verification. The old hub takes
   the role back by itself at epoch + 2 (tier 1) only on positive evidence: the new hub, reached and
   authenticated, says it is failing and acknowledges standing down. A new hub that can't be reached
   stays the hub; the person may take the hub back at tier 3 (after the review, §8).
3. **Emergency promotion from the latest backup** (tier 3), on a hub candidate whose hub can't be
   reached and which has no live copy: the sheet states the backup's time, what was lost, and that
   connectors need signing in again; nothing is escrowed. It takes epoch max + 1 with its own keys.
4. **The promotion drill:** two Nova homes in temp folders on this machine, real processes on
   loopback, a paired stand-in computer (the real boot agent) and phone, a stand-in stable name (a
   loopback forwarder), and a backup folder. A script (`scripts/promotion-drill.ts`) and a test
   (`tests/acceptance/m10g-drill.test.ts`) run the same drill; its run is recorded as evidence.

## 1. Trust: every candidate, safely

- `rosterKeys(r)` = hub, standby, and every `candidates[]` key. A computer's agent accepts a node as
  hub only if it proves one of these keys, says it is hub at an epoch no lower than known, and hands
  over a roster signed by that same key naming it as hub (unchanged rules, wider key set).
- `bundleKeys(r)` = hub and standby only. Runtime bundles stay signed by the hub; M10f held candidate
  trust back because these keys also sign bundles. A candidate that becomes hub signs bundles as hub.
- Where agents look (`candidates(d)`): the address they last reached the hub at, the roster's hub,
  standby and candidates' addresses, and the address they joined at (the stable name).
- **Fencing** (`MeshRole.fence`) asks every trusted peer with an address **and the stable name**
  (`publicUrl`, when another node answers there). A higher epoch, proven with a roster signed by the
  peer's own pinned key, makes this hub step down when the peer is a possible successor: the standby,
  the hub its role file names, or **any trusted hub candidate** (Decision 2). Any other key, even with
  a valid signature, is refused and said once (unchanged).

## 2. Planned promotion

`POST /api/v1/mesh/promotions/check {device_id}` (tier 0, a dry run) and
`POST /api/v1/mesh/promotions {device_id, confirm: true}` (tier 3, the hub's screen or an approver),
then `GET /api/v1/mesh/promotion` for progress. The hub (A) drives the candidate (B) over B's mesh
address with requests signed by A's identity key (`nova-promotion-v1|<step>|<from>|<to>|<epoch>|<time>|<nonce>|<sha256 body>`),
which B checks against the hub key its role file and registry hold; every answer that carries
authority (B's roster) is signed by B's pinned key and checked by A.

| Step | On | What happens | Ledger task (evidence) |
|---|---|---|---|
| 0 | A | **Not automated:** a candidate that isn't the live standby is refused, saying to make it the standby first (Add a device, as a standby). | the refused pre-check |
| 1. Pre-checks | A | role (trusted, hub candidate, the standby, with an address, not revoked); hardware (B's free disk at least 3× the home's size, at least 2 GiB of memory, as B reports them); version parity (B's release and schema version equal A's); backup freshness (a backup in the last 24 h and a passed restore drill of it); B follows A at A's epoch. Each refusal in words. | "Promotion pre-checks" (each check in words), the chain's parent |
| 2. Catch-up | A | B's acknowledged sequence reaches A's head (`lag()`), within a bound. | the acknowledged sequence |
| 3. Drain | A | the heartbeat, the hub's own services and Era 2's running work stop; the ledger starts nothing new but the promotion's own; running work gets the bound (60 s) to finish; a step past its commit point (`uncancellable`) is waited for, or the promotion stops; the rest is aborted and handed over (requeued by B's `recover()`); then writes are held at the gate (409, saying why), requests already past the gate finish, the journal's last scan is taken, and the last sequence H is fixed; the log keeps recording, so anything that still lands is either copied by B before the hand-over (H moves up to it) or kept here and said (§8). B acknowledges H. | the drained list, H |
| 4. Transfer | A → B | A signs a handover {from, to, epoch + 1, H, A's address, the stable name}. Devices re-point through the stable name, or the roster. | B: "Hub handed over" (the handover and roster signatures, B's state) |
| 5. Demote | A | A becomes B's live standby: role.json names B, its cursor is H, its epoch e + 1, every device session here ends. | B: "The old hub is the standby" (its first acknowledgement, lag) |
| 6. Verify | A watches B | for the window (30 min; shorter only in a test or the drill on a temp home, §8), every probe asks B, over a request signed by A's key, for its health, signed by B's key: hub at e + 1, taking writes, the stable name leading to it (when Nova moves the name). Its answer is `ok` or `unhealthy`; nothing authenticated is `unknown`, never evidence. Three `unknown` in a row: the person is told once, with the way to take the hub back. At the end, with the last probe `ok`, A sends the probe runs to B. | B: "Promotion verified" (probe runs) |
| Roll-back | A | tier 1, by itself, only after three `unhealthy` in a row **and** B's signed acknowledgement that it stood down (it then holds writes): A copies what B took, promotes at **e + 2** with B as its standby, points the name back, and nudges B. Without the acknowledgement, nothing moves by itself; the person may take the hub back at tier 3 (`take-back`). B sees A at e + 2 (its standby: a successor), steps down, sets aside in a named checkpoint whatever it took that A never copied (and says exactly what), then copies A afresh as its standby. | A: "Checks of … failed", "Rolled back" (A's state, its roster) |

**At no moment do two nodes accept writes while they can reach each other:** A refuses writes from
the hold on, and is a standby after the transfer; B accepts writes only after it promoted; a roll-back
waits for B to stand down. If B's answer to the transfer doesn't settle it, A stays held until B's
signed word does; a restart while held starts held, before the ledger resumes or recovers anything.
The person can choose otherwise at tier 3 (cancel, take back), told plainly what Nova can't know.

**Refusals, each in words:** a phone, browser or computer without the candidacy; a revoked device;
a candidate that isn't the standby; one that can't be reached; too little disk or memory; another
release or schema; no backup in the last 24 h, or one whose drill didn't pass; B behind A's epoch;
a promotion already running; this node isn't the hub.

## 3. Emergency promotion from the latest backup

On a hub candidate that runs Nova (a former standby, or a hub that stepped down) when the hub can't
be reached and this node holds no live copy. `GET /api/v1/mesh/promotion/cold` (tier 0: the sheet)
and `POST /api/v1/mesh/promotion/cold {confirm: true, backup}` (tier 3, this node's own screen).

- **Eligible:** this node's key is in the backup's registry as a trusted hub candidate (or the
  standby), so devices holding a roster from then pin it; no hub answers at the hub's address, the
  stable name or any peer (one that answers is a planned promotion, or M4's, never a cold one); this
  node isn't a live standby (that is M4's "Make this the hub", which keeps everything it copied).
- **The sheet**, before the person confirms: the backup's time and number; **what was lost:
  everything written after that time**, devices paired since needing pairing again; **connectors
  need signing in again**, because backups never hold the vault's key (Decision 5; the key stays only
  where it already was: the old hub, a standby that copied it, their own checkpoints); **what may come
  back** (revocations and forgets after this node's own copy aren't known here); the epoch it will
  take and where that comes from; the backup's seal, or that it couldn't be checked.
- **Then:** the restore drill runs on the backup (`drill()`, unchanged), the backup is staged like a
  checkpoint restore, and Nova restarts. At the start, before the database opens, the staged home is
  swapped in with what restore.ts always keeps from now (this node's `mesh/`: its keys and role; a
  device revoked since stays revoked; forgets since stay forgotten) and the cold marker's changes:
  this node is hub at **max + 1** of every epoch it knows (now's, the backup's, its last promotion's,
  and the newest roster any of its devices showed it, `POST /mesh/seen`), the old hub is a spoke, sessions from the backup end, the vault from the backup can't
  open and Nova says so. The ledger records the drill, the restore and the role as one chain.
- **Devices** accept it because its key is pinned in the roster they hold, and find it through the
  stable name (or the candidates' addresses in the roster); **the old hub**, when it comes back,
  finds a higher epoch from a pinned candidate and steps down.

**The vault, honestly** (the Credential Broker isn't built, `docs/plans/vault-broker.md`): today the
vault's key is in the OS keychain where one answers (`secret-tool`, `security`, Credential Locker),
else in `vault/key` (0600). A planned promotion keeps connectors working: the standby already holds
the vault and its key, delivered sealed to its own key inside the sync stream since M5b, in its own
key store; nothing about that changes, and that key is a vault key, not a device's private key. A
cold promotion has no key to open the backup's vault: it was never in a backup and nothing escrows it,
so connectors are signed in again. Nova's own keys in the vault (the backups' seal, the
encrypted copy's key) are carried only when this node's own vault holds them; otherwise backups made
before can't be checked for Nova's seal here (a limit).

## 4. The stable name

The stable mesh name is `NOVA_MESH_PUBLIC_URL` (devices join at it and keep it as `join_url`). Moving
it is a DNS or tailnet change, which this build never makes (Hard limits). Nova moves it through a
driver: `NOVA_MESH_NAME_CONTROL=<url>` is an HTTP endpoint that takes `{address}` (in the drill, the
loopback forwarder's own control port). The node that becomes hub points the name at itself; a
roll-back points it back. Without a driver, the sheet says the name has to be moved by the person,
and the verification doesn't check it (computers still follow the roster; phones and browsers wait
for the name).

## 6. The drill (gate evidence)

`node scripts/promotion-drill.ts [--record <file>]` and `tests/acceptance/m10g-drill.test.ts`, the same
code (`tests/acceptance/m10g-drill.ts`). Two Nova homes (N1, N2), a stand-in computer (the real boot
agent, `boot.ts join --kind computer`), a stand-in phone (`Joiner`), a loopback forwarder for the
stable name, a backup folder; nothing outside the temp folders. Cases, in order:
1. pre-checks refuse a phone, a computer without the candidacy, and a hub with no fresh backup;
2. a planned N1 → N2 succeeds: no data lost (content hashes), the computer and phone re-pointed via
   the stable name with no new pairing, N1 a live standby, the window passed;
3. a planned N2 → N1 whose verification fails (the stable name doesn't move): N2 hub again by itself
   at epoch + 2, N1 stepped down to its standby;
4. M4's emergency with a live standby (N2 killed, N1 promoted), N2 back and fenced;
5. the old hub returning while the new one is down: the computer refuses its lower epoch;
6. an emergency promotion from the latest backup onto N2, a candidate that isn't the standby: the
   sheet's backup time, what was lost and connectors, no new pairing, connectors needing sign-in;
7. N1 returns and fences itself;
8. throughout, a write probe on both nodes never finds two accepting writes at once;
9. no private key leaves its device: every node's `mesh/identity.json` and the computer's
   `boot/keys.json` are byte-identical before and after; every decrypted sync batch, handover,
   roster and transfer answer (tapped with `NOVA_DRILL_TAP`), every backup and both homes are
   scanned for each private key in every encoding, and none is found;
10. a key that isn't pinned can't take the role, even with a valid signature.

## 8. After the adversarial review of #272

Two blocking findings and seven should-fix, each now a test built on the reviewer's probe
(`tests/acceptance/m10g-review.test.ts`, R1–R9) or a drill case, each seen failing with its fix undone:
1. **Roll-back only on positive evidence** (above, step 6). A node that steps down never discards its
   changes: what the other never copied goes into a named checkpoint first, and the problem lists it
   by kind and key; if it can't be set aside, the node keeps it and doesn't copy over it. A stale
   `promotion.json` at restart is checked against this node's mesh state before any probe.
2. **Epochs that can't tie or trail, and ties that settle:** the emergency epoch is max + 1 over the
   rosters devices showed this node too (a device that finds a node not to be its hub shows it the
   roster it holds, signed by its hub; kept only if a key this node trusts signed it), and the sheet
   says when no device did. **Fencing** steps down at an equal epoch to the smaller device id (one
   fixed rule everywhere); **devices** never follow another hub at an equal epoch.
3. **Transfer outcomes** are settled by the candidate's signed `transfer-status` (above, step 4).
4. **A restart while holding** restores the hold before `ledger.resume()` and `recover()` (and Era 2
   starts no work), so handed-over work doesn't run on both.
5. **Changes after the last sequence:** the gate holds first, in-gate requests finish, the log keeps
   recording, device sessions stop writing their last-seen time while held, Era 2's running work stops
   on `draining`; whatever still lands is copied or kept and said.
6. **A hold with no answer:** released as soon as the candidate says, signed, it didn't take the
   hand-over; the person may cancel at tier 3 (`POST /mesh/promotion/cancel`): the candidate is asked
   once more, and if it can't say, this node carries on two epochs higher, so a candidate that did
   take the role steps down when they meet and keeps what it took.
7. **Device trust:** another hub only at a strictly higher epoch, at most 3 past the epoch known
   unless the current hub signs it, never past 2^31 − 1; a heartbeat answer names the roster's digest
   and the agent takes a changed roster at once, so a revoked candidate is unpinned within a heartbeat.
8. **What a restore can't know** is on the sheet (revocations and forgets after this node's copy).
9. **The connector sentence** says where the key is; the claim register's entry and its backlog case
   (blocked: false by design as first written) follow.
10. **The window and the probe pace** can be shortened only in a test (`NODE_TEST_CONTEXT`) or the
    drill (`NOVA_DRILL=1`) on a temp home; otherwise never under 30 minutes and 5 s.
Minor: the name driver needs `NOVA_MESH_NAME_TOKEN` and https or this machine; an automatic failover
doesn't move the name (it says so; an M4 promotion by the person does, under its tier 3, with no
window: a gap stated in the evidence); the tap runs only in a test or the drill and writes the vault's
key as its digest; the emergency sheet is bound to the backup it showed; no problem is logged once
Nova is stopping; the drill's key scan covers PEM and DER, both hex cases, byte lists, every database
row and everything the processes printed.

## Not in M10g

the device agent (it has no Nova home to become hub with); rehearsing from Settings › Devices on

## Where the ADR didn't fit

- **Step 0** is a refusal with directions, not an automatic re-enrollment: enrolling a standby is a
  pairing with new keys in a new home, made on that machine with its own command, so the hub can't
  do it for the person.
- **The stable name's dead-man's switch** is the promotion's own verification window, not M10d's
  change chain: M10d's targets aren't replicated, and its switch watches device contact on the node
  that applied the change, which stops being hub in the middle of the step. The window watches the
  new hub from the old one, and its roll-back points the name back.
- **The verification is watched by the old hub**, now the standby, because a failed new hub can't be
  relied on to roll itself back; the new hub records the verified result when the old one sends it.
- **The emergency variant needs a Nova home**: a computer with only the device agent holds a pinned
  key but no Nova to run, so it isn't offered there.

## For the coordinator: the plain-language "What changed" entry (not written to the LEDGER here)

**M10g · You can move the hub to another computer, and get it back from a backup**
- What changed: in Settings › Devices, a computer that can become the hub now has "Promote to hub".
  Nova checks first that it is ready (it copies everything, has room, runs the same version, and there
  is a recent backup that passed its test), and tells you plainly if not. Then it hands over: the
  last changes are copied, running work finishes or moves along, new changes wait for a moment, and
  the other computer becomes the hub. The old hub keeps a live copy. For a while afterwards it checks
  the new hub. If the new hub says it isn't working, it takes the role back by itself and tells you;
  if it simply can't reach the new hub, it doesn't guess: it tells you, and you can take the role
  back yourself. Nothing either computer saved is thrown away; anything that couldn't be carried over
  is kept on that computer and listed for you. If
  your hub is gone for good, a computer that could be the hub can take over from your latest backup:
  Nova says first when that backup was made, that anything after it is lost, and that your
  connections (like email) need signing in again. Your devices find the new hub without pairing again.
- What you can now do: move Nova to a better computer without starting over, and recover from losing
  the hub. Each step shows up in Tasks.
- Still unfinished: the computer must already be your standby to be promoted (adding it as the
  standby is a separate step); moving your real network name (DNS or Tailscale) isn't done for you;
  this has only been tried on test computers on one machine, not on your real ones.
