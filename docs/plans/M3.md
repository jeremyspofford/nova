# M3 plan — design system and PWA

Roadmap M3. The packet sources are DESIGN-SYSTEM (all of it), ADR-12, NOVA-SPEC §5, and LOCAL-FIRST §6. The approved look is concepts E–H (`docs/builder-packet/nova-ui-*.png`): round 2 is one design language. One override: the orb has **no face**. Concept E draws eyes and a smile; DESIGN-SYSTEM §1 says "no face, no features, ever", and the written rule wins.

**Gate:**
- swap the design system live with no restart;
- the resize/posture sweep passes;
- blank-profile setup can be completed from the PWA alone.

Rules as before: no runtime dependencies, erasable TypeScript in `src/core`, vanilla JS modules in `ui/` (as today), neutral placeholders, tests for everything. Code outside `src/core` imports only `src/core/index.ts`.

## 1. Tokens and packages (M3a) — `src/core/design.ts`, `design-systems/*.json`, migration `0005_design.sql` if needed

- **Token schema.** It is exactly DESIGN-SYSTEM §2, required in full.
  - Names map to CSS variables by replacing `/` with `-`: `bg/base` → `--bg-base`, `type/h1` → `--type-h1`, `space/3` → `--space-3`, `motion/breathe` → `--motion-breathe`.
  - Type also needs weights and line heights: `type/weight-regular`, `type/weight-strong`, `type/line-tight`, `type/line-body`.
  - Motion needs durations and easings: `motion/duration-fast`, `motion/duration-slow`, `motion/ease`.
  - The schema lives in one place (`src/core/design.ts` exports `TOKENS`), and `ui/js` reads it from `/api/v1/design-systems/schema`, never from a copy.
- **Package format.** A design-system extension (DESIGN-SYSTEM §4, CONTRACTS §4).
  - The full manifest, with `kind: 'design-system'`, `permissions: []`, `secrets: []`, `on_remove` keeping nothing.
  - `tokens{}`, the full set, is the default appearance.
  - `modes: {light?: partial, dark?: partial}` is optional. It exists so today's Appearance setting (light/dark/auto) keeps working.
  - `components{}`: per-component token bindings.
  - `content_rules`: may only tighten DESIGN-SYSTEM §6, never loosen it.
  - `extras[]`: declared signature surfaces.
  - `preview[]`: screenshot paths, which the gate generates.
- **Validation** (successor of `check:themes`):
  - completeness;
  - value syntax per token family;
  - WCAG contrast pairs: text on bg and surface ≥ 4.5, faint ≥ 3, and status colours on card;
  - a reduced-motion guarantee.
  - A package that fails cannot be applied. `npm run check:themes` runs it over every package in `design-systems/`.
- **Built-ins:**
  - **Orb Teal** (default, dark): concepts D/E/H.
  - **Companion Light**: concepts B/F; cream, coral accent, teal orb, serif display.
  - Era 2's four themes (nova, paper, aurora, obsidian) are converted into packages and kept installed; they are the owner's and stay available. Their names map onto the new tokens.
- **Selection.** Profile section `appearance`, with `design_system`, `previous` (for rollback), `mode` (light | dark | auto) and `device_overrides {deviceId: id}`.
  - There is no device registry until M4, so a device id is a random id the PWA keeps in localStorage.
- **API (`/api/v1/design-systems`):**
  - `GET` list (with validation state);
  - `GET {id}`;
  - `GET schema`;
  - `POST` install (a manifest, through the extension host);
  - `POST {id}/validate`;
  - `GET {id}/preview.css` (for a sandboxed frame);
  - `POST {id}/apply {scope: user | device, device_id?}`;
  - `POST rollback {scope, device_id?}`;
  - `GET /design-system.css?device=` returns the active package as CSS variables.
  - Every change emits `design-system` on the event stream.
- **Hot swap.** The PWA swaps one `<style id="ds">` when `design-system` arrives: no reload, no restart.
- **Lint.** `lint:tokens` is updated so components may reference only `var(--<schema token>)`. Raw colours, sizes, font names, radii, shadows and durations are errors. Breakpoints are code (§5), allowed only in the layout file.

## 2. PWA and layouts (M3b) — `ui/`

- **PWA:**
  - `manifest.webmanifest`, icons, and a service worker: app shell cached, the API network-first, and an honest offline state.
  - It is installable. iOS limits are stated where they matter (LOCAL-FIRST §6).
- **Layouts** are chosen by viewport and posture, never by device name (DESIGN-SYSTEM §5):
  - **phone** (< 600 px, or a folded cover screen): Ambient Home, with orb hero, greeting, card stack, and bottom tabs Home · Chat · Tasks · Memory · More.
  - **tablet / foldable inner / half-open** (600–1023 px, or two viewport segments): two panes. When half-open, the conversation is on top and the active card below.
  - **desktop** (≥ 1024 px): Calm Control (G), with a slim rail (orb + ≤ 6 destinations), a centre column, and an optional right column of ≤ 3 quiet cards (Active Tasks, Device Mesh, System Health). The right column is collapsible and off below 1280 px.
  - Posture comes from `navigator.devicePosture`, the `viewport-segments` media features, and `screen.orientation`. A `?posture=` URL hook lets tests emulate it and is documented as such.
  - `<body data-layout="phone|tablet|desktop" data-posture="…">`.
- **Same features in every layout.** Every destination is reachable everywhere:
  - Home, Chat (conversations), Tasks (ledger), Memory, Automations (trigger rules + schedules), Skills (+ connectors), Activity, Health (problems and checks), Settings (identity, privacy, permissions, appearance/design systems).
  - Phone puts the overflow under More.
- **Components** (DESIGN-SYSTEM §7, each with its states):
  - **Orb** (idle / listening / working / speaking / attention / alert / offline). One token-driven component at every size, no face, and it honours reduced motion. Its state comes from real signals: ledger activity → working; approval waiting → attention; open problem → alert; server unreachable → offline.
  - **Cards:** BriefCard, HandlingCard, TaskRow, VerifiedResultCard (with an evidence viewer showing the verification checks), LookingIntoItCard, DeviceRow, DeviceMeshCard, HealthCard, MemoryHighlightCard.
  - **ApprovalSheet**, tiered: tier 3 needs an explicit confirm. It covers ledger tasks and Era 2 tool approvals.
  - **TriggerRow**, with pause and delete.
  - **The rest:** ChatBubble set, Composer, Toast/ProactiveBanner (problems and proactive messages), SettingsRow, EmptyState ("Nothing needs you").
  - Status vocabulary (Quiet / Working / Waiting / Verified / Needs you / Failed), mapped from ledger states in one function.
- **Composer voice.** Browser speech recognition can send audio to a cloud service, so in local-only the voice button is off, and a line says why. It is otherwise enabled only where the browser supports it.
- **Honest surfaces only:**
  - Devices shows "This device" until M4.
  - The Brief card shows an empty state until a brief workflow exists.
  - There is no Smart Home card until a connector exists.
- **Errors in the UI.**
  - Every `problem` event shows a toast, plus the Health destination and the orb's alert state.
  - The Era 2 surfaces keep their in-chat error alerts.
- **Setup in the PWA.** A blank profile opens the setup conversation (`/api/v1/setup`) full-screen in every layout, and it ends on the welcome task's VerifiedResultCard.
- **Era 2 parity.** Everything the current UI can do stays reachable: conversations, the Memory view and its edits, skills and Gmail connect, schedules, Activity, Settings and permissions.
  - Its tests (`tests/*.test.js`) keep passing.
  - `scripts/shots.js` is updated for the new screens.

## 3. Gate tests (M3c) — `tests/ui/*.test.ts`, Playwright (`playwright-core`, already a dev dependency)

- **Chromium:**
  - Locally: `CHROMIUM=<path>`.
  - In CI: an install step for the browser matching `playwright-core`.
  - The suite is skipped with a loud notice when no browser is present locally, but **never** in CI.
- **Live swap.** Load the app and set `window.__boot` once. Then apply another design system over the API and check:
  - the computed `--bg-base` changes;
  - `__boot` is unchanged (no reload);
  - the server pid is unchanged (no restart).
  - Then preview in a frame, apply per device, and roll back.
- **Posture sweep.** Widths 320, 375, 600, 768, 1024, 1280 and 1920, each upright and in each emulated posture (folded, half-open vertical, half-open horizontal). Check:
  - `data-layout` is what §5 says;
  - there is no horizontal overflow;
  - the set of reachable destinations is identical in every layout;
  - the orb is present and has no face.
  - Screenshots are saved as evidence under `docs/screenshots/m3/`.
- **Setup from the PWA alone.** A blank home and a real server process. A click-and-type conversation reaches "setup done", and the welcome task appears as Verified with its evidence viewable.
