## What is built

A workspace is a Docker container on this machine, one per project, behind a `Computer` interface
in `src/core/computer/` (`create`, `exec`, `checkpoint`, `reset`, `destroy`). The first adapter is
`DockerComputer`: it talks to the local daemon through the `docker` CLI, argv arrays only, never a
shell string, always with `-H unix://…`, so a Docker context or a `DOCKER_HOST` can't send it to
another machine.

## Built on what exists (one Nova)

| Need | Reused | New |
|---|---|---|
| Every command is a task | The Work Ledger: a `computer` worker, one lane per workspace | — |
| Approval | The ledger's tiers (`minTier`) and privacy gate (`egressFor` + `permits`) | The rules below |
| Evidence | The verifier's `confirmation` kind: Nova reads its own run record and output file back | The `nova-computer` checker |
| Output screened | The ingest gate, `screen()` with source kind `tool` | — |
| Egress rules | `src/safe-fetch.js`: `publicAddress`, and the private-name rule (now exported) | A CONNECT proxy that applies them |
| Declared hosts | `browser/plan.ts`: `allowed()`, the host syntax | — |
| Isolation of a copy | `changes/sandbox.ts`' idea: an inert copy that reaches nothing | A container with no network |
| Undo | Checkpoints, as `resilience/checkpoints` takes them before a change | An image commit plus a folder copy |
| Processes | `children.ts` (`trackChild`), so none outlives a restart | — |

Workspace state is in SQLite (migration 0014, not replicated: containers live on this machine).
Files are under `<home>/workers/computer/`, which sync doesn't journal and Nova's own checkpoints
skip.

## The container

- The image: `node:26-trixie`, pinned by digest. It has Node, git and a shell out of the box.
  Nothing is installed on top, because that would be a second download. The slim and Alpine
  images have no git.
- Mounts: the project folder at `/workspace`, and nothing else.
- Network: `--network none`, always, whatever the egress declaration. There is no Docker socket,
  no host network, no port published, and no route to the console port, the mesh port, the host
  or the LAN.
- Privilege:
  - it runs as Nova's own uid:gid, never root (if Nova runs as root, 1000:1000);
  - `--cap-drop ALL`;
  - `--security-opt no-new-privileges`;
  - Docker's default seccomp profile;
  - `--ipc private`, `--init`.
- Limits: `--memory 2g --memory-swap 2g --cpus 2 --pids-limit 512 --ulimit nofile=4096`.
- Labels name this Nova's home, by a hash, so one Nova never touches another's containers.

## Egress

The declaration is one of:
- `none`;
- `registries` (the npm, PyPI and crates registries, port 443);
- `hosts` (declared hosts, as browser tasks declare them).

**None** is `--network none`, enforced by the kernel.

**Registries and hosts** still run with `--network none`. Inside the container, a relay listens
on `127.0.0.1:3128` and carries each connection over its `docker exec` stdio to Nova. The relay
runs as `nobody`, so the workspace's own user can't reach into its file descriptors. Nova runs
the proxy:
- CONNECT only, which means HTTPS or another TLS stream; plain HTTP is refused;
- the host must match the declaration;
- the name is resolved by Nova, and every address must be public (`publicAddress`);
- names that only mean something on a private network are refused;
- the socket connects to exactly the address that was checked.

Every attempt, allowed or refused, is kept in the run's record. Nothing else is mounted and no
Docker network is created, so no network configuration changes.

**Local-only** allows no egress:
- the ledger refuses a task whose workspace reaches outside (`egressFor` returns `remote`);
- the computer itself also refuses to open the proxy while the person's default is local-only.

## Tiers

| Action | Behaviour | Ledger `approval_tier` |
|---|---|---|
| A read (`access: read`) in a workspace with no egress | automatic | 0 |
| A write (the default) in a workspace with no egress | do, notify, undo: a checkpoint first, the task shown as handling, undo is a reset to it | 1 |
| Any command in a workspace that can reach outside | ask every time | 3 |
| Create with Nova's own empty folder | act and report | 1 |
| Create on a folder of the person's | ask first | 2 |
| Create with egress | ask every time | 3 |
| Checkpoint | act and report | 1 |
| Reset (and undo) | do, notify, undo: a checkpoint first | 1 |
| Destroy (deletes its checkpoints) | ask every time | 3 |

**Deviation (numbering):** the ADR and the brief call a reversible write "tier 2 (do, notify,
undo)". In this ledger, and in NOVA-SPEC §6, tier 2 means *ask first*: a tier-2 task waits for an
OK before it runs. The behaviour the amendment asks for ("reversible write = do + notify + undo")
is NOVA-SPEC's tier 1 ("act and report… user can undo"). The packet wins, so the behaviour is
built exactly as asked and the ledger records it as tier 1. Recording 2 would have made every write
wait for an OK.

**A read is checked, not trusted.** After a read, Nova compares the project folder (paths, types,
modes, sizes, mtimes) and the container's change list with what they were before. If anything
changed, the read fails as having written, and the person is told what changed and which checkpoint
to go back to.

## Checkpoint and reset

- **Checkpoint:** `docker commit --pause` to an image tagged for this home, workspace and
  checkpoint, plus a copy of the project folder (modes and mtimes kept, symlinks verbatim). It also
  stores a content digest of the folder.
- **Clean:** the checkpoint taken at creation (the pinned image and the folder as it was).
- **Reset:** a checkpoint of the current state first (so a reset can be undone), then the container
  is recreated from the checkpoint's image and the folder is replaced with its copy. After that,
  Nova's own digest of the folder must equal the checkpoint's, or the reset fails.

## API (the console surface)

- `GET /computer`
- `POST /computer/workspaces`
- `GET /computer/workspaces/{id}`
- `POST /computer/workspaces/{id}/exec`, `…/checkpoints`, `…/reset`, `…/destroy`
- `GET /computer/runs/{task}`

Each change is a ledger task, approved and followed through `/tasks`. The ADR and the roadmap ask
for no UI in M10a, so none is built. The API is the console surface (ADR-5).

## Gate tests (each written first, seen failing)

- `tests/core/computer-policy.test.ts`: run arguments, folder rules, egress declarations, tiers (no
  Docker).
- `tests/core/computer-docker.test.ts`: create, exec, output evidence; checkpoint and reset byte for
  byte, both the folder and the container's filesystem.
- `tests/core/computer-isolation.test.ts`: from inside, each escape is attempted, and the same probe
  run with the isolation removed reaches the target (a positive control). The escapes are:
  - the console port;
  - the mesh port;
  - Nova's home;
  - the Docker socket;
  - the host network;
  - an undeclared host;
  - root.
- `tests/core/computer-egress.test.ts`: the proxy allows a declared host and refuses an undeclared
  one, a private address, a private name and plain HTTP; a connection made without the proxy
  doesn't get out.
- `tests/acceptance/m10a-computer.test.ts`: the real server, with a blank profile. Setup, a
  workspace, a command as a ledger task with verified evidence, local-only refusing egress, and no
  egress from Nova.
- The fresh-user test, unchanged, passes.

Tests that need Docker skip with the reason when it isn't there. GitHub's runners have Docker, so
they run in CI and pull the pinned image there.

## Gaps, written down

- No disk quota: overlay2 on ext4 can't set one.
- A read that changes a file the container had already changed since its image isn't seen on the
  container side; the project folder's check is complete.
- Checkpoint folder copies are full copies, not incremental.
- No agent tool drives the computer yet (M10c).
- After a factory reset, containers are removed the next time the computer is used, not during the
  reset.
