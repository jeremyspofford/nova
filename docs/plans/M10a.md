## What is built

A workspace is a Docker container on this machine, one per project, behind a `Computer` interface
in `src/core/computer/` (`create`, `exec`, `checkpoint`, `reset`, `destroy`). The first adapter is
`DockerComputer`: it talks to the local daemon through the `docker` CLI, argv arrays only, never a
shell string, always with `-H unix://…`, so a Docker context or a `DOCKER_HOST` can't send it to
another machine.

## Built on what exists (one Nova)

| Need | Reused | New |
|---|---|---|
| Every command asked for is a task | The Work Ledger: a `computer` worker, one lane per workspace | — |
| Approval | The ledger's tiers (`minTier`) and privacy gate (`egressFor` + `permits`) | The rules below |
| Evidence | The verifier's `confirmation` kind: Nova reads its own run record and output file back | The `nova-computer` checker |
| Output screened | The ingest gate, `screen()` with source kind `tool` | — |
| Egress rules | `src/safe-fetch.js`: `publicAddress`, and the private-name rule (now exported) | A CONNECT proxy that applies them |
| Declared hosts | `browser/plan.ts`: `allowed()`, the host syntax | — |
| Isolation of a copy | `changes/sandbox.ts`' idea: an inert copy that reaches nothing | A container with no network |
| Undo | Checkpoints, as `resilience/checkpoints` takes them before a change | An image commit plus a folder copy |
| Processes | `children.ts` (`trackChild`), so none outlives a restart | — |

Workspace state is in SQLite (migration 0014, not replicated: containers live on this machine).
Files are under `<home>/workers/computer/`, which sync doesn't journal and Nova's own checkpoints
skip.

## The container

- The image: `node:26-trixie`, pinned by digest. It has Node, git and a shell out of the box.
  Nothing is installed on top, because that would be a second download. The slim and Alpine
  images have no git.
- Mounts: the project folder at `/workspace`, and nothing else; its `.git`, when it has one, again
  read-only over itself (see "The project folder").
- Network: `--network none`, always, whatever the egress declaration. There is no Docker socket,
  no host network, no port published, and no route to the console port, the mesh port, the host
  or the LAN.
- Privilege:
  - it runs as Nova's own uid:gid, never root (if Nova runs as root, 1000:1000);
  - `--cap-drop ALL`;
  - `--security-opt no-new-privileges`;
  - Docker's default seccomp profile;
  - `--ipc private`, `--init`.
- Limits: `--memory 2g --memory-swap 2g --cpus 2 --pids-limit 512 --ulimit nofile=4096`.
- Labels name this Nova's home, by a hash, so one Nova never touches another's containers.
- Between commands nothing runs in it but its init and the `sleep` that keeps it up. Before each
  command, and after it, anything else (a process a command detached, say) is stopped by
  restarting the machine, and the machine is checked again; the report says how many were stopped.

## The project folder

- **One workspace per folder.** A folder may not hold, or be inside, another workspace's folder (or
  Nova's home), since that workspace could change this one's folder under it.
- **The approved folder, and only it.** When a folder of the person's is asked for, Nova resolves it
  once: the task stores its real path, device, inode and birth time, and the approval shows them.
  When the task runs, the folder must still be that one (same real path, no link on the way, same
  device, inode and birth time), or the workspace isn't made. The birth time is there because ext4
  gives a new folder a freed inode number again (GitHub's runners showed it); on a filesystem that
  records no births, only the device and inode tell.
- **Still that folder, every time.** Before every mount (a create, a start, a rebuild), every copy,
  digest and reset, the folder is checked again: not a link, its real path its path, the same
  device, inode and birth time. Otherwise Nova refuses to touch it and says so.
- **Copies and digests never leave the folder.** They walk it without following links (a link is
  kept as a link, its target as written), open only regular files (`O_NOFOLLOW`, then checked to be
  the file that was listed), and never open a FIFO, socket or device (noted and left out of the
  copy).
- **`.git` is read-only inside**, every one of them: the top one and any nested (another repository's
  folder, or the `.git` file of a submodule or worktree, which names its git folder), each a real
  folder or file, never a link, which Docker would follow. At most 64; more, or one under a name
  Docker's `--mount` can't carry (a comma, quote or line break), and the machine isn't made. Git on this computer runs what `.git/config` and `.git/hooks` say (a
  `core.fsmonitor` runs on a plain `git status`), so a command inside mustn't change them. The
  person can choose `git_writable` when making the workspace, so commands can commit; that asks
  first (tier 2), even on Nova's own folder.
- **Other files this computer's tools run by themselves** (`.envrc`, `.vscode`, `.idea`,
  `.devcontainer`, `.husky`, `.gitmodules`, and a `.git` a command made), at any depth, aren't
  blocked, since
  changing a project's files is what a workspace is for. A command that changes one is reported:
  *"It changed what tools on this computer may run by themselves: …. Look at them before you run git
  or open the folder in an editor here."*

## Disk

A container's limits don't cover disk: the folder, the checkpoint copies and the machine's own layer
are all this computer's disk. Each is capped (`DISK` in `policy.ts`):

| Cap | Default | Where |
|---|---|---|
| Workspaces | 20 | refused when asked, and when it runs |
| A project folder | 4 GiB | a folder of the person's is refused when asked; no checkpoint is taken of a folder past it (so no write runs); a command that grows it past it is stopped |
| One workspace's checkpoint copies (clean, automatic and named together) | 16 GiB | before each checkpoint, the oldest automatic ones go to make room; if it still wouldn't fit, none is taken |
| The machine's own layer | 8 GiB | Docker's `--storage-opt size` where the storage driver enforces it (tried once with a throwaway machine, since some accept it and ignore it); otherwise its size is checked before each command and while it runs, and a command past it is stopped |

A running command is checked every 5 s. A check that can't be made (a walk that fails, a size Docker
won't give) stops the command, the same as a cap reached; the folder and the machine's disk are
checked separately. Every walk of the folder stops at a path too long for this computer to read by
name (past 4000 bytes on Linux, 1000 on macOS: a command can make one with relative `mkdir` and
`chdir`), saying so; such a folder can't be checkpointed, so writes are refused until a reset, which
asks first and removes it. A reset whose folder is over the cap can't checkpoint what
is there first, so it says so in its title and asks first (tier 2).

## Egress

The declaration is one of:
- `none`;
- `registries` (the npm, PyPI and crates registries, port 443);
- `hosts` (declared hosts, as browser tasks declare them).

**None** is `--network none`, enforced by the kernel.

**Registries and hosts** still run with `--network none`. Inside the container, a relay listens
on `127.0.0.1:3128` and carries each connection over its `docker exec` stdio to Nova. The relay
runs as `nobody`, so the workspace's own user can't reach into its file descriptors. Nova runs
the proxy:
- CONNECT only, which means HTTPS or another TLS stream; plain HTTP is refused;
- the host must match the declaration;
- the name is resolved by Nova, and every address must be public (`publicAddress`);
- names that only mean something on a private network are refused;
- the socket connects to exactly the address that was checked.

- what the tunnel carries must be TLS: a ClientHello whose SNI is the host the CONNECT named (none
  for an address); anything else is dropped before a byte goes on;
- the relay lives for one command, started only once nothing else runs in the machine (so nothing
  can hold its port first, and if something did, the relay fails and the command doesn't run), and
  closed when the command ends;
- on every new connection the proxy asks again: is the person's default still not local-only, and
  is the task still running with its OK?
- memory is bounded: each connection has 128 KiB in flight each way (credit frames on the relay's
  stdio, so neither side buffers more for a reader that doesn't read), at most 64 connections, and
  a refused connection is dropped.

Every attempt, allowed or refused, gets a fixed reason code. The report says only the declared
hosts reached (with counts) and the refusals by code; the hosts as the command asked for them are
untrusted text, kept (the first 200, then a count) only in the run's record, and screened with the
output. Nothing else is mounted and no Docker network is created, so no network configuration
changes.

**Known limits of egress:**
- *Domain fronting through a declared host.* The registries sit behind CDNs (npm's behind
  Cloudflare, PyPI's files behind Fastly). The SNI check makes a tunnel's TLS name the declared host,
  but what is inside the TLS (the HTTP `Host`) can't be read without breaking TLS, so a CDN that
  routes by `Host` would carry a request to another site it serves. Nova doesn't break TLS.
- *Publishing in registries mode.* `registries` allows the registries' hosts both ways: a command
  with a token can publish a package (data out to a public place). The mode reaches outside, so
  every command in it is tier 3; nothing narrower is enforced.
- Encrypted ClientHello (ECH): the proxy reads only the outer SNI, so any ClientHello carrying the
  ECH extension is refused (GREASE ECH included).

**Local-only** allows no egress:
- the ledger refuses a task whose workspace reaches outside (`egressFor` returns `remote`);
- the computer itself also refuses to open the proxy while the person's default is local-only.

## Tiers

| Action | Behaviour | Ledger `approval_tier` |
|---|---|---|
| A read (`access: read`) in a workspace with no egress | automatic | 0 |
| A write (the default) in a workspace with no egress | do, notify, undo: a checkpoint first, the task shown as handling, undo is a reset to it | 1 |
| Any command in a workspace that can reach outside | ask every time | 3 |
| Create with Nova's own empty folder | act and report | 1 |
| Create on a folder of the person's | ask first | 2 |
| Create with egress | ask every time | 3 |
| Create with `.git` writable inside (`git_writable`) | ask first | 2 |
| Checkpoint | act and report | 1 |
| Reset (and undo) | do, notify, undo: a checkpoint first | 1 |
| Reset of a folder over its disk cap (no checkpoint first) | ask first | 2 |
| Destroy (deletes its checkpoints) | ask every time | 3 |

**Deviation (numbering):** the ADR and the brief call a reversible write "tier 2 (do, notify,
undo)". In this ledger, and in NOVA-SPEC §6, tier 2 means *ask first*: a tier-2 task waits for an
OK before it runs. The behaviour the amendment asks for ("reversible write = do + notify + undo")
is NOVA-SPEC's tier 1 ("act and report… user can undo"). The packet wins, so the behaviour is
built exactly as asked and the ledger records it as tier 1. Recording 2 would have made every write
wait for an OK.

**A read is checked, not trusted.** After a read, Nova compares the project folder by content
(paths, types, modes, each file's bytes, each link's target) and the container's change list with
what they were before. Every path in that list is compared by what it is now, read inside: mode,
owner, size, times including its ctime (which no process there can set back) and, for a file up to
1 MiB, its bytes. So a path already changed since the image is still seen changing again. If
anything changed, the read fails as having written, and the person is told what changed and which
checkpoint to go back to.

## Checkpoint and reset

- **Checkpoint:** the machine is paused; then `docker commit` to an image tagged for this home,
  workspace and checkpoint, a copy of the project folder (modes and mtimes kept, links as links,
  FIFOs, sockets and devices left out) and a content digest of the copy; then it is unpaused. So the
  three are one moment's picture.
- **Clean:** the checkpoint taken at creation (the pinned image and the folder as it was).
- **Reset:** a checkpoint of the current state first (so a reset can be undone), then the container
  is recreated from the checkpoint's image and the folder is replaced with its copy. After that,
  Nova's own digest of the folder must equal the checkpoint's, or the reset fails.
- **What "byte for byte" covers:** for the folder, every path, its type, its permission bits, each
  file's bytes and each link's target. Not compared: modification times (the copy keeps them), owners
  (the person's own uid throughout), extended attributes and ACLs, hard links (restored as separate
  files), and FIFOs, sockets and devices (not kept). For the machine's own filesystem (`docker
  export`): path, type, mode, owner, size, link target and bytes, not times. Running processes are
  not kept: a reset makes the machine again.

## API (the console surface)

- `GET /computer`
- `POST /computer/workspaces`
- `GET /computer/workspaces/{id}`
- `POST /computer/workspaces/{id}/exec`, `…/checkpoints`, `…/reset`, `…/destroy`
- `GET /computer/runs/{task}`: the record. A command's raw output (and the egress attempts as it
  asked for them) only when the ingest gate passed it; otherwise the gate's extract and a note that
  the rest is held back. The file on disk is unchanged and is still the evidence.

Each change is a ledger task, approved and followed through `/tasks`. Every command asked for
through the API (or the ledger) is a task; Nova's own processes in a workspace (the egress relay,
the read check's reader, the one-time disk-cap probe) aren't, and the adapter used directly (as its
tests do) runs commands without one. All `/computer` routes go through the console's own checks:
a session (a paired device's, or this computer's console), the X-Nova header and a same-origin
`Origin` for a change, and the `Host` check (tested). The ADR and the roadmap ask
for no UI in M10a, so none is built. The API is the console surface (ADR-5).

## Gaps, written down

- No hard disk quota on overlay2 over ext4 (GitHub's runners) or Docker Desktop's containerd store
  (this machine, which accepts `--storage-opt` and ignores it): there the caps are checked every few
  seconds, so a fast writer can pass one by what it writes in that time.
- A `.git` a command creates (where there was none) is writable inside until the machine is next
  made (a reset or a rebuild); each change to it is reported.
- The folder's identity is checked before each use, by path; between the check and the use there is
  a moment. Nothing can change it in that moment: no other workspace may overlap it, and nothing
  runs in its own machine then (paused, or no processes).
- The read check hashes a machine-side file's bytes up to 1 MiB; a larger one is compared by its
  metadata, including its ctime, which is enough to see any change.
- Checkpoint folder copies are full copies, not incremental.
- No agent tool drives the computer yet (M10c).
- After a factory reset, containers are removed the next time the computer is used, not during the
  reset.
