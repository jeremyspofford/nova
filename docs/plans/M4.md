# M4 plan — device mesh

Roadmap M4. The packet sources are:
- CONTRACTS §5;
- LOCAL-FIRST-AND-DEVICE-MESH §3–§5;
- ADR-3 (two device agents), ADR-11 (hub is a role), ADR-10, NOVA-SPEC §6 (tiers);
- DESIGN-SYSTEM (including the perception principles).

Era 1 is the reference for pairing (`packages/core/src/pairing/{code,limiter}.ts` at `6e2cf142`, ported nearly verbatim) and for the HLC (`packages/core/src/sync/hlc.ts`).

**Gate:**
- pair a phone (QR) and a computer (command) to a fresh hub;
- revoke one;
- kill the hub and promote the standby;
- no data loss, no orphaned trust.

**Rules as before:**
- no runtime dependencies;
- erasable TypeScript in `src/core` and `src/device`;
- vanilla JS modules in `ui/`;
- neutral placeholders;
- tests for everything.

Code outside `src/core` imports only `src/core/index.ts`. A test-only dev dependency, `jsqr`, is allowed so the gate can decode the QR the hub actually draws.

## 0. Trust and transport (the security model; it tightens today's behaviour, never loosens it)

**Today.** Anything that reaches the server controls Nova, and the default bind is loopback only. M4 keeps that console and adds authenticated devices.

**Two kinds of listener.**
- **Console listener.** `NOVA_HOST:NOVA_PORT`, loopback by default, as now.
  - A request is *console* only if all of these hold:
    - it arrives on this listener;
    - its socket peer is loopback;
    - its `Host` is loopback;
    - it has no forwarding headers (`forwarded`, `x-forwarded-*`, `tailscale-*`, `x-real-ip`).
  - A reverse proxy (for example `tailscale serve`) pointed at the console port therefore gets **no** console rights. It is treated as an unauthenticated device.
- **Mesh listener (optional).** It is for paired devices and is configured as one of:
  - `NOVA_MESH_URL=https://0.0.0.0:4320` with `NOVA_TLS_CERT` / `NOVA_TLS_KEY`; or
  - `NOVA_MESH_URL=http://<addr>:<port>` with `NOVA_MESH_TRANSPORT=proxy|network`. This is only for when the person states that a TLS proxy or an encrypted network (a tailnet) carries it.

  Plain HTTP with no such statement is refused at startup, with a plain-words reason. `NOVA_MESH_PUBLIC_URL` is the address devices are told to use; QR codes and commands carry it.

**Every request that isn't console:**
- **Public:**
  - the enrollment routes (§1, rate-limited per client address with the ported `SlidingWindowLimiter`);
  - the `/pair` page and the static assets it needs;
  - `GET /join.sh` and `GET /device-agent.tar` (§2);
  - `GET /api/v1/mesh/hello` (the hub's fingerprint, epoch and name: no person data).
- **Device:** a valid session for a `trusted` device: cookie `nova_session` (HttpOnly, SameSite=Strict, Secure on HTTPS) or `Authorization: Bearer <token>`.
  - `kind: browser|phone` (a person's client) gets what the console gets, *except* approving enrollment requests and promotion. Those stay on the console, or on a client device the person has already marked `can_approve`.
  - `kind: computer` (a spoke) gets only the device routes (heartbeat, inbox, runtime).
  - `kind: standby` gets only the sync routes.
- **Everything else:** 401 for the API. An HTML navigation goes to `/pair`.

The X-Nova + Origin guard still applies to every non-GET from browsers.

**Sessions.**
- How they're made: `POST /api/v1/mesh/session`, carrying `{device_id, time, signature}`, where the signature is Ed25519 over `nova-session-v1.<device_id>.<time>` and the time is within ±60 s.
- How long they last: 12 h, renewable by signing again. The token is stored as a SHA-256 hash.
- Never issued over a transport §0 doesn't accept.

**Revoking a device:**
- sets `trust='revoked'`;
- deletes its sessions;
- closes its open event streams at once;
- emits `device`.

It is tier 3 (explicit confirm every time) and is allowed from any authorized client (CONTRACTS §5). A revoked key can never start a session or enroll again. Enrolling again needs a new key.

## 1. Enrollment (M4a) — `src/core/mesh/{wire,identity,devices,enroll,access}.ts`, migration `0005_mesh.sql`

**`wire.ts` (pure, shared with the device agent through `index.ts`):**
- Era 1's code primitives:
  - Crockford-32 8-character codes, 5-minute TTL, single use, stored as a hash salted with the pairing id;
  - `normalizePairingCode`;
  - commit-then-reveal: `pairingCommitment`, `pairingConfirmationV2` (6 digits shown on both screens).
- Ed25519 raw base64url keys: `verifyDeviceSignature`.
- Canonical JSON.
- `seal(toX25519Pub, fromX25519Priv, bytes)` / `open(...)`: X25519 ECDH → HKDF-SHA256 (info `nova-seal-v1`) → AES-256-GCM. Each device has an X25519 key next to its Ed25519 key, and the X25519 public key is signed by the Ed25519 key in the join request.
- HLC (port).

**`identity.ts`.** The hub's own Ed25519 and X25519 keys live in `home/mesh/identity.json`, mode 0600. They are never in the database, logs, receipts or sync. The fingerprint is the first 20 bytes of SHA-256 of the Ed25519 public key, in base32 groups `ABCD-EFGH-…`.

**Tables:**
- `device`:
  - `id`, `name`, `platform`;
  - `kind` (browser|phone|computer|standby), `role` (client|spoke|standby|hub);
  - `public_key`, `x25519_public_key`, `fingerprint`, `capabilities` (JSON);
  - `trust` (trusted|revoked), `can_approve`, `address` (standby only);
  - `created_at`, `approved_at`, `revoked_at`, `revoked_reason`, `last_seen`.
- `pairing` (one code).
- `join_request` (one device asking, with its state: pending|approved|denied|expired).
- `device_session`.
- `mesh_state`: `epoch`, `role` of *this* node, `hub_id`, `standby_id`.

**Protocol (CONTRACTS §5; one protocol, three front doors):**
1. **`POST /mesh/pairings`** (console or `can_approve`). Returns:
   - `{pairing_id, code, expires_at}`;
   - `url` = `<public>/pair#c=<code>&h=<fingerprint>` (in the fragment, so it is never logged);
   - `command` = `curl -fsS <public>/join.sh | sh -s -- <code>`;
   - `hub_fingerprint`.
2. **`POST /mesh/join`** (public), sending:
   - `{code, public_key, x25519_public_key, claims: {name, platform, kind, capabilities[]}, commitment}`;
   - `x25519_sig`, the Ed25519 signature over the X25519 public key.

   It returns `{request_id, hub_nonce, hub_fingerprint}`. A wrong or spent code is a 400 with no detail, plus rate-limit accounting.
3. **`POST /mesh/join/{id}/reveal`** (public, signed `nova-add-device-reveal-v1.<id>.<time>`), sending `{device_nonce, time, signature}`. It returns `{confirmation}`. The device shows the 6 digits, and the hub's prompt shows the same digits.
4. **The approval prompt.** The hub shows it on the console and on `can_approve` clients, as an event `join_request` and a sheet. It shows the name, platform, kind, requested capabilities, key fingerprint and the 6 digits.
   - `POST /mesh/requests/{id}/approve {confirm: true}` (tier 3, explicit confirm) or `/deny`.
   - Approval creates the `device` record.
5. **`GET /mesh/join/{id}`** (public, signed status poll) returns `pending|approved|denied|expired`. When approved, it also returns `{device_id, roster}`.
6. **Roster.** `{epoch, hub: {id, url, public_key, x25519_public_key}, standby?: {...}, issued_at}`, signed by the hub's identity key. Devices pin the keys of the hub and the standby from it.

**Routes:**
- `GET /mesh/devices` (registry; this device is marked);
- `PATCH /mesh/devices/{id}` (`name`, `can_approve` with tier 3);
- `POST /mesh/devices/{id}/revoke {confirm: true, reason}`;
- `GET /mesh/requests`;
- `GET /mesh/roster`.

**Events:** `device`, `join_request`.

**Health:** the mesh check (devices trusted and revoked, the standby's lag, the epoch).

**Problems:**
- a join refused for rate;
- an expired request;
- a standby that has fallen behind.

**PWA:**
- **Settings › Devices.** The real registry, built from DeviceRow with name, kind, last seen and trust. It has "Add a device" and Revoke (tier 3).
  - Add a device opens a sheet with three front doors:
    - a QR code;
    - the hub address plus the code, as text;
    - the one-line command, with a copy button.
  - The sheet also warns: "Only enter this code at <public URL> on a device you already trust."
- **The approval sheet** is the existing tiered ApprovalSheet, tier 3, with the digits.
- **`/pair`, the joining page:**
  - it reads the fragment;
  - it creates a **non-extractable** WebCrypto Ed25519 key and an X25519 key, kept in IndexedDB;
  - it joins, reveals and shows the digits;
  - it polls, then starts a session and continues to Home.

  It needs a secure context. Where WebCrypto Ed25519 is missing, it says so plainly; it never falls back to an extractable or weaker key.
- **The QR encoder** is `ui/js/qr.js`, written here with no dependencies: byte mode, error correction M, versions 1–10, drawn as an SVG path with a quiet zone, dark on light in every design system.
- **The DeviceMeshCard** shows real devices. "Only this device for now" appears only while that is true.

## 2. Device agent (M4b) — `src/device/{boot,runtime,queue}.ts`; the computer device class

**Two agents, never merged (ADR-3).**

**The boot agent** (`boot.ts`) is small, privileged and rarely changed. It handles:
- **Keys.** The Ed25519 and X25519 private keys live in `<device home>/boot/keys.json`, mode 0600. The device home is `NOVA_DEVICE_HOME`, default `~/.nova-device`.
- **Enrollment.** `node src/device/boot.ts join <hub-url> --code <code> [--name] [--kind computer|standby]` prints the 6 digits and waits for approval.
- **Pinned roster.**
- **Sessions.**
- **A watchdog.** It runs the runtime and restarts it with backoff. Three crashes in 60 s put it in **safe mode**: the runtime stays down, and the boot agent sends a heartbeat that says so.
- **Runtime updates.** A bundle from `GET /mesh/runtime` (`{version, files, sha256}` signed by a pinned hub or standby key) is checked before it replaces `<device home>/runtime/`. A bad signature is refused and reported.
- **Recovery.** `recover` reinstalls the runtime from the hub, and `status` reports the state.

**The runtime agent** (`runtime.ts`) changes often and runs as a child of the boot agent under Node's permission model:
- it can read `runtime/` and `state/`;
- it can write only `state/`;
- it can't spawn child processes or load addons.

It never sees a private key. Boot hands it a session token over IPC and renews it. It does three things:
- **Heartbeat.** `POST /mesh/devices/me/heartbeat {capabilities, version, safe_mode}` updates `last_seen`.
- **Offline queue** (`queue.ts`, `node:sqlite` in `state/`). Events, task requests and memory notes created while the hub is unreachable are kept with idempotency keys. They are flushed in order to `POST /mesh/inbox`, which accepts each key exactly once.
- **Conflict rules:**
  - config is server-wins: a stale base version is rejected and reported to the device;
  - memory is merged with provenance (`recorded_by: device:<id>`);
  - a ledger entry is never lost: queued task requests become tasks, or are refused with a reason that is stored.

**Follows the roster.** It talks to the hub. If the hub is unreachable it tries the standby. It accepts a node as hub only if the roster that names it is signed by a pinned key with an epoch ≥ the one it knows. It never accepts a lower epoch.

**One-line command.** The hub serves `GET /join.sh`, a POSIX `sh` script, and `GET /device-agent.tar` (`src/device`, `src/core/mesh/wire.ts` and what it imports, plus a minimal `package.json`). The script:
- checks for Node ≥ 26 and says plainly if it isn't there;
- unpacks to `<device home>/agent`;
- runs `boot.ts join`;
- installs nothing system-wide.

TLS trust comes from the OS, or from `NOVA_CA_FILE`.

**Decision (ledger).** The device agent is TypeScript on Node, not a port of Era 1's Rust `novad`.
- Rust isn't installed here.
- Node's permission model enforces the rule that the runtime can't modify the boot agent, and a test proves it (`ERR_ACCESS_DENIED`).
- `novad`'s supervisor and signed-module design is the reference.

## 3. Hub, standby and sync (M4c) — `src/core/mesh/{sync,replica,promote}.ts`, migration `0006_sync.sql`

**Sync log.**
- SQLite triggers on every replicated table write to `sync_log(seq, tbl, pk, op, row, hlc)`.
- The replicated tables are profile, task, task_event, memory (and its history), trigger/rule/record/message, extension, device, problem and receipt.
- `device_session`, `pairing`, `join_request`, `sync_log` and `mesh_state` are never replicated, and nor are identity files.
- Home files (workspace, conversations, `MEMORY.md`, schedules, skills: everything outside `src/home.js`'s UNTRACKED list) are journalled by a scan that runs on change and every few seconds: `file_put` with content, and `file_delete`.

**Forgetting holds (standing order 4).**
- `memory.forget` also removes every `sync_log` row that carries the forgotten content.
- It appends a `delete` op.
- The standby applies it through its own `forget`, so its backups are cleaned as well.
- A test scans the standby's whole home for the forgotten words.

**Standby.**
- **How it starts.** A Nova server with a home of its own, enrolled with `boot.ts join … --kind standby --nova-home <dir>`. That writes `<home>/mesh/role.json`, and the standby then starts with `node src/server.js`.
- **Replica mode:**
  - no scheduler, triggers, workers or chat runs;
  - the API answers reads and shows a banner: "This is the standby; <hub> is the hub";
  - writes return 409 with that reason.
- **How it pulls.** It calls `GET /mesh/sync?after=<seq>`: a long-poll, sealed to the standby's X25519 key, and only standby sessions may call it. It applies each batch in one transaction, keeps the hub's `seq`, and acks with `POST /mesh/sync/ack {seq}`, which shows its lag on the hub's Health page.
- The standby's `address` is in the roster.

**Promotion** (ADR-11, a ledger-recorded event).
- **Manual.** `POST /mesh/promote {confirm: true}` on the standby's console (tier 3).
- **Automatic,** only when the person turned it on (`mesh.auto_failover_after_s`, off by default), after the hub has been unreachable that long.
- **What it does:**
  - `epoch + 1`;
  - this node becomes hub (`mesh_state.role = 'hub'`);
  - it signs a new roster;
  - it starts the scheduler, triggers and workers;
  - it runs `ledger.recover()`, so tasks survive the failover;
  - it records a ledger task "Standby promoted to hub", with a `confirmation` evidence item covering the epoch and roster.
- Devices accept the new roster (signed by a key they pinned, with a higher epoch) and start sessions with the new hub. Trust is unchanged because the device registry was replicated.

**Fencing (no split brain).**
- **A demoted hub.** At startup and every 30 s, a hub asks its roster peers for `/mesh/hello`. If one is hub with a higher epoch, this node demotes itself to standby of it. It refuses writes and says why, and its open sessions are closed.
- **Devices** never accept a lower epoch.

## 4. Gate (M4d) — `tests/ui/m4-mesh.test.ts` plus core/integration tests

This runs in the Playwright container: locally through `scripts/ui-test.sh`, and in CI in the UI-gate job.

**Setup.**
- A fresh hub (blank home) with a mesh listener on HTTPS, using a test certificate made with `openssl`.
- Devices reach it at the container's own non-loopback address, so the device path really is remote.

**Steps:**
1. Setup completes. Enroll the **standby**, a second Nova process with its own blank home, by command, then approve it on the console. It syncs.
2. **Phone, by QR.** The hub console (a desktop browser context at localhost) opens Add a device. The test decodes the QR it drew with `jsqr`. A phone-sized browser context opens that URL over HTTPS, joins, and shows 6 digits. The console's approval sheet shows the same 6 digits, and is approved with confirm. The phone reaches Home, authenticated, and makes something (a memory).
3. **Computer, by command.** The test runs the exact one-line command from the sheet in a shell (curl | sh). The boot agent starts the runtime, the runtime heartbeats, and the device shows Online in the registry.
4. Create data on the hub: tasks, a memory, a conversation, a file in the workspace.
5. **Revoke the phone** (tier 3). Its event stream closes immediately, its next request gets 401, and starting a new session with its key is refused.
6. Wait for the standby to catch up. **Kill the hub** with SIGKILL. While the hub is down, the computer queues a task request and a memory note offline.
7. **Promote the standby** from its console, with confirm. The ledger shows the promotion.
8. **No data loss.** Every task, event, memory, profile record, conversation and workspace file from step 4 is on the new hub, compared by content hash. The computer's queued items arrive exactly once.
9. **No orphaned trust:**
   - the phone is still revoked on the new hub and can't start a session;
   - the computer reconnects to the new hub by itself;
   - restarting the old hub makes it fence itself: it doesn't act as hub, and it says why.
10. The blank-profile fresh-user test still passes, and with no mesh listener configured, nothing beyond loopback is reachable.

**Evidence.** Screenshots go to `docs/screenshots/m4/`. A transcript of every step goes to `docs/evidence/m4-gate.md`.

**Manual check for the owner.** Pair a real phone through the real QR. The gate emulates the phone with a browser context; it can't use a camera.

## Order

M4a first: everything else uses its identity, enrollment and sessions. Then M4b and M4c in parallel, on top of M4a's branch. The gate (M4d) comes last.

The preview at 4318 stays loopback-only. No mesh listener is configured on this machine, so nothing is exposed beyond it.
