## 0. The question this plan must settle: who holds the mesh key and carries the sync

The resolution note asks which part of the device agent holds the mesh key, signs the capture
manifests and carries the sync, consistent with Decision 1 and the runtime's no-network rule.

**The answer: the boot agent, in a separate data channel (`src/device/carrier.ts`), not as a verb.**
- The boot agent already holds the device's Ed25519 key (`boot/keys.json`, 0600) and the hub session.
  Nothing changes about who holds a key: the runtime never sees it, and no key moves.
- The carrier **moves data and starts nothing.** It has no `node:child_process` (a test reads its
  source), it talks to exactly two places: the hub, over the boot agent's own session, and the
  capture workload's loopback port, which it takes from the hub-signed manifest of the version that
  is live (never from a request, never a shadow copy). So Decision 1's verb set stays exactly five,
  and the carrier can't be used to run anything.
- **The runtime's no-network rule is kept, not amended.** `RUNTIME_CALLS` stays the same two calls
  (heartbeat, inbox), and a test pins it. The runtime has no part in the capture data path: it never
  sees captured words (they'd pass through a part with a weaker sandbox story for no gain), and the
  manifests are signed where the key already is.
- Why not the runtime: it would need either the key (breaking ADR-3) or a "sign this for me" call
  to the boot agent, which is a signing oracle for whatever the runtime made up; and the derived
  events come from a loopback port, which the runtime may not reach. Why not a verb: verbs are about
  execution, and the resolution note says moving data isn't one.

## 1. The five verbs (Decision 1)

`src/device/workloads.ts`, the boot agent's side. `WORKLOAD_VERBS = install, start, stop, switch,
probe`, frozen.
- **A verb request is `{verb, service, version}` and nothing else.** Any other key (`command`, `args`,
  `env`, `url`, `port`, …) refuses the request: what runs, with which arguments, on which port, is
  in the signed manifest. A verb outside the five is refused by name.
- **install:** the boot agent fetches the manifest itself, over its own session (the runtime never
  hands one over), and verifies it before anything is written: signed by a key the roster allows to
  sign bundles (`bundleKeys`: the hub's and the standby's), for this device, for this platform, a
  command that starts one of the manifest's own files (the file itself, or Nova's Node with it as the
  script), the roles this device holds (`mayRun`). Then every file is downloaded and its SHA-256
  checked; a mismatch writes nothing. A slot per version (`workloads/<service>/<version>/`), made in
  a `.next` folder and renamed into place. It keeps the live version, the previous one and the new
  one; older slots go.
- **start:** re-verifies the slot (signature and every file's hash) at every start, refuses to run
  as root, refuses a capture workload while capture is off on this device (§4), then spawns the
  manifest's command, argv only, no shell, in its own process group, with none of the agent's
  environment (PORT and `NOVA_PORT_<NAME>`, its own HOME and state folder), under the watchdog.
- **stop:** ends its process group.
- **switch:** makes a version live: the old live instance stops (its slot is kept for one-step
  rollback), the new one starts on the stable ports. Switching to the kept previous version is the
  rollback: nothing is downloaded.
- **probe:** a GET of the manifest's health path on 127.0.0.1, on the port the boot agent itself
  gave that instance. Never another host, never a port from a request.

**The runtime decides and reports** (`src/device/rollout.ts`, a runtime file, shipped in the signed
bundle). Its heartbeat answer carries the hub's assignments; it asks the boot agent for verbs over
IPC (`{type: 'verb', id, verb, service, version}`) and reports each workload in its heartbeat
(`workloads[]`: service, version, status, health, since, why). It still runs under the M4b
permission model: no child processes, no network.

## 2. The native update pipeline, 6(b)

Run locally, decided by the runtime, executed by the five verbs, through the hub's same gates:
1. **fetch** and 2. **verify**: `install` (above). `verifyBundle` still takes only `.ts` files for
   the runtime; workloads have their own verifier (`verifyWorkload`), as the ADR asked.
3. **alongside**: per the definition. `full` or `shadow`: started next to the live one on a preview
   port the boot agent picks. A shadow copy is told so (`NOVA_SHADOW=1`), and its output is never
   read: the carrier reads only the live version's port. `none`: nothing starts until the switch.
   `copy` isn't offered for a device (a device has no home to copy).
4. **health**: `probe`, three passes in a row. Then the runtime reports `ready`, which is what the
   hub's Service Manager requires before it offers a promotion.
5. **switch**: only after the promotion at the hub, at its tier (capture is tier 3, every time:
   `promotionTier`, since it has OS permissions). The hub's assignment changes to `live`; the
   runtime calls `switch`, then probes again.
6. **one-step rollback**: failed health after the switch switches back to the kept version by
   itself (tier 1: Nova acts and reports), and a rollback the person asks for (tier 2) is the same
   verb. The kept slot is used: nothing is downloaded or rebuilt.

**Hub side:** `src/core/services/workloads.ts`, a `ServiceDriver` named `device` (the M10e interface:
`available`, `plan`, `apply`, `status`, `switch`, `rollback`). It records assignments (migration
0023's `device_workload`, replicated, so a promoted hub keeps them), signs each device's manifest with
the hub's key, serves the pinned files (read from the definition's `file:` artifact and checked
against its SHA-256 before serving), and turns heartbeat reports into `ServiceStatus`. A core
`ServiceManager` holds it as its **remote** driver: a definition the resolver places on a device
other than the hub goes to it. The hub's own services stay with the supervisor's Service Manager.
Console routes: `GET /services/devices`, `POST /services/devices/deploy`,
`POST /services/devices/{service}/promote`, `POST /services/devices/{service}/rollback`.

## 3. Placement (6(a))

- **Container workloads only onto Linux nodes**: the resolver already refuses an image-only service
  on macOS and Windows. With no K3s driver yet, the device driver also refuses an image-only service
  on any device, saying containers on devices come with the K3s driver (M10j).
- **Native workloads onto any enrolled device whose roles allow it**: a program per platform, the
  device's platform (from its heartbeat's hardware, or its enrollment) picks which one.
- **A thin client never gets one**: refused by the resolver, again by the device driver, and again by
  the device agent (`mayRun`) before it installs anything.
- **Capture only onto `capture-source` devices**: a definition that asks for a capture permission
  (`screen-recording`, `microphone`, `accessibility`) must place by the `capture-source` role (the
  validator refuses otherwise), and the device agent checks the manifest's roles against its own.
- **No credential on a spoke** (Q5): a definition with `secrets` is refused for any device other than
  the hub, saying why (the vault broker isn't built). Nothing in this plan hands a secret to a device.
- iPhones and iPads are thin clients, so they never get a workload (M10f).

## 4. The Screenpipe pilot, on a stand-in

- `src/core/services/screenpipe.ts`: `screenpipeDefinition()`, service `screenpipe`, a program per
  platform, `ports: [api 3030]`, health `/health`, `alongside: none` (the ADR: `shadow` only once two
  copies are shown to run side by side on that OS), roles `capture-source`, `os_permissions`
  `screen-recording` and `microphone`, `egress: none`, `secrets: []`. Promotion is tier 3.
- **Not re-signed (Decision 4):** the hub's signature covers the manifest, which pins the upstream
  artifact's SHA-256. The bytes are served and installed exactly as given; nothing in Nova writes or
  signs a workload's program. A test compares the installed bytes with the original file.
- **The stand-in** (`scripts/stand-ins/stand-in-screenpipe.js`): one self-contained file that speaks
  the parts of Screenpipe's API the carrier reads (`/health`, `/search`, `/frames/{id}`), with made-up
  items the test adds. It captures nothing from the machine. Its delete call is the stand-in's own.
- **Deploying capture never turns capture on.** Consent stays per source and per device, off by
  default: deploying installs it; while every capture source of that device is off, the boot agent
  refuses to start it and stops it if consent is withdrawn; nothing is pulled from it for a kind
  that is off. The hub's intake checks consent again (`Capture.ingest`).
- The device offers its capture kinds (`capture.screen`, `capture.audio`) in its heartbeat once a
  capture workload is installed, so the hub lists the sources, off.

## 5. The capture data path (the design's M10h list)

`src/device/carrier.ts` (device) and `src/core/capture/sync.ts` (hub).
- **Derived sync, store-and-forward:** the carrier pulls the live capture workload's derived events
  for the kinds that are on, after their consent time, numbers them by a device sequence (not the
  clock), and keeps them in `capture/outbox/` (the boot agent's folder, 0700). Private windows are
  dropped there, before they are queued.
- **Signed manifests:** each batch carries `{batch_id, device_id, device_name, source, seq_from,
  seq_to, items: [{id, seq, sha256}], queued, sent_at}`, signed with the device's key
  (`captureBatchMessage` in `wire.ts`). The hub verifies it against the enrolled device record, the
  session's device, the items' checksums and the sequence range before anything is stored.
- **Dedupe and ack:** an item is taken in once by `(source, external id)`; a repeat is answered as a
  duplicate. The hub answers every item; the device drops what was answered, and only that.
- **Offline resume:** what isn't answered stays queued across hub outages and restarts, and goes in
  sequence order when the hub is back: no loss, no duplicate.
- **A full queue pauses and says so** (10 000 items): the carrier stops pulling (the workload keeps
  its own store, so nothing is lost) and says why in its status.
- **Lag is a number:** per device, the hub keeps the last sequence and capture time it answered and
  the queue the device reported (`GET /capture` → `devices`: "synced to 14:32 · 212 queued").
- **Provenance:** every event keeps `provenance` (migration 0023, a replicated column in
  `ADDED_COLUMNS[23]`): origin device and name, capture source, device sequence, batch, device time
  and hub receipt time. Each batch's manifest and signature are kept (`capture_batch`, replicated).
- **Manifest refusal:** from an unknown device, a revoked one, another device than the session's, or
  with a bad signature or checksum: refused with the reason, logged, nothing stored.
- **Tombstones:** forgetting an event that came from a spoke issues a tombstone to that device
  (`capture_device_tombstone`, replicated). The carrier deletes it from its queue and from the
  workload's store, then acknowledges, signed. The forget's report says "deleted everywhere" only
  when every holder has acknowledged; until then it names the device as pending.
- **Raw fetch:** raw stays on the spoke. The person asks for one item, with a reason; that is a Work
  Ledger task naming the item and the reason (worker `capture-raw`). The carrier sends that one item,
  signed and checksummed; the task is verified by Nova's own check of the file against the signed
  checksum.
- **Privacy modes:** the hub says whether it is a cloud site (`NOVA_MESH_SITE=cloud`). In local-only
  mode with a cloud hub, the device plan says sync is refused, so the carrier keeps queuing and says
  why; the hub also refuses such a batch if one arrives. A raw fetch to a cloud hub is refused (the
  per-device opt-in isn't built).

**Not in M10h** (the design's later parts): the raw archive, its storage adapter, verified-transfer
pruning, the 48-hour window, cold tiering, encryption before upload, and a delete made on a spoke
removing the hub's copies.

## 6. Tiers

As the ADR's table: deploying alongside tier 1, but a command no approved version ran asks first
(typed, tier 3 for capture); promotion tier 3 for capture (OS permissions), tier 2 otherwise;
automatic rollback tier 1; a rollback asked for tier 2. A raw fetch is a ledger task the person
starts, with its reason.

## 7. Gate

1. **The five verbs** (`tests/core/workloads-device.test.ts`): refuses an unsigned workload, one
   signed by a key it didn't pin, an artifact whose hash doesn't match, any verb outside the five, a
   request carrying a command, a manifest whose command isn't one of its files, a slot changed after
   install, another device's or platform's manifest, a role it doesn't hold, running as root.
   **The runtime still can't start a process:** the M4b sandbox test, run again with the new runtime
   files, and `RUNTIME_CALLS` unchanged.
2. **The update pipeline** (`tests/core/workloads-rollout.test.ts`): a signed update installs, passes
   health and switches, with a shadow run when the definition says `shadow`; a failing version rolls
   back in one step with no download; `none` starts only at the switch; the same through the real
   sandboxed runtime.
3. **Placement** (`tests/core/workloads-hub.test.ts`): image-only can't go to macOS or Windows (nor,
   without K3s, to any device); native goes to stand-in Linux, macOS and Windows devices whose roles
   allow it; never a thin client; capture only to a capture source; no secrets to a device; the
   device's own check.
4. **The pilot** (`tests/acceptance/m10h-pilot.test.ts`): Screenpipe's definition on the stand-in,
   deployed at tier 3 to three stand-in devices labelled Linux, macOS and Windows; installed bytes
   identical to the artifact (not re-signed); consent off throughout deployment, nothing started or
   pulled until a source is turned on.
5. **The capture data path** (`tests/core/capture-sync.test.ts` and the pilot): sync and dedupe;
   offline resume without loss or duplicate; a tombstone's acknowledgement in the report; a raw
   fetch in the ledger with its reason; local-only with a cloud hub queues; a manifest from an
   unknown or revoked device, or with a bad signature, refused and logged.
6. **Hard limits:** no real Screenpipe or other binary installed anywhere, no real device; temp homes
   and 127.0.0.1 only; the no-Kubernetes tripwire armed.
7. **Every other gate:** the fresh-user test, the regression evals at 100%, the closing-rule claims
   test, `npm run check` and `scripts/ui-test.sh`.
