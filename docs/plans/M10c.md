# M10c plan: coding through chat

**Sources:** `docs/plans/M10.md` (the ADR, its M10c section and Hard limits). AMENDMENT-2026-10-30-C
Part 4 ("Coding through chat: chat is the control plane. Intent → plan in the Work Ledger →
sandboxed coding workers (Relay/Claude Code adapters) in git worktrees → tests → preview →
merge/deploy per approval tier"). ROADMAP M10. ADR-8 (vendor agents are adapters), ADR-9.
CONTRACTS §1 (the task envelope). NOVA-SPEC §6 (tiers: 0 silent, 1 act and report with undo, 2 ask
first, 3 explicit confirmation every time). OPERATING-RULES.

## What is built

A person asks for a code change in chat. The chat agent calls one tool, `code_change`, with the
repository, the branch, the goal, the test command and (optionally) the preview command. That makes
a **coding run**: a plan recorded in the Work Ledger as a chain of tasks for the `coding` worker,
one per step, each with its own tier and its own evidence:

| Step | What happens | Tier | Evidence Nova checks itself |
|---|---|---|---|
| 1. **Write** | Nova copies the branch into a repository of its own, makes a git worktree on a new branch `nova/<run>`, and a coding agent (Claude Code, Codex, Relay, or a chat model through the JSON files contract) changes a plain copy of it. Nova takes the change into the worktree and commits it. | 1: do, notify, undo (the undo removes the worktree and its branch) | `confirmation` (`nova-coding`): the commit is in Nova's repository, the branch points at it, its parent is the base, and its files are the ones Nova recorded |
| 2. **Check** | Nova runs the test command in the worktree, at exactly that commit, then starts the preview command there on `127.0.0.1` and a free port, and checks that it answers. | 2: asks first, showing the diff, because it runs code the agent wrote, as the person | `test_result` (`nova-coding-run:`, Nova's own record of its run); `confirmation` (`nova-coding`) for the preview: Nova's record, the process alive, listening on loopback only |
| 3. **Merge** | Only after step 2 is verified done. The person sees the reviewed diff, the test result and the preview link, and confirms. Nova moves the target branch in the person's repository to exactly the reviewed commit. Nova never pushes. | 3: explicit confirmation every time | `confirmation` (`nova-coding`): Nova reads the person's branch and finds the reviewed commit |

- **Declining** the merge (cancelling its task) leaves the person's repository as it was: nothing of
  the run has been written there, not one object, so the branch is byte-identical and nothing is
  pushed. Nova stops the preview and removes the worktree (the tier-1 undo).
- **A failing test** fails step 2 with Nova's own reason. No merge task is ever made, so a failing
  run never reaches the merge ask. A preview that doesn't answer, or answers on more than loopback,
  fails step 2 the same way.
- **The branch moved** after the review (someone committed to it): the merge refuses to merge
  anything unreviewed. The run starts a new round by itself: Nova merges the new tip into its branch
  in the worktree (step 1 again, as **Update**, tier 1), and steps 2 and 3 run again, asking again.
  A conflict stops the run and says so.

Not reused, on evidence:
- **The provider's own task flow** (`/tasks` with `owner: claude-code`: copy-in from `workspace/`, the
  test-run ask, copy-back into `workspace/`). It works on files in Nova's workspace and copies the
  result back there. A coding run works on a git repository and its result is a commit, never a copy
  into the workspace. Routing a repository through the workspace would put a git worktree where the
  chat agent's `write_file` can write (it may write anything in `workspace/`, including a worktree's
  `.git` file, which says which repository git works on). So the run calls the adapters through
  `workIn`, with the same gates, and does its own diff and test steps on the commit.
- **The change pipeline** (`changes/`). It ships changes to Nova itself (extensions, design systems,
  settings) through a sandbox Nova and a canary. A coding run changes the person's repository; its
  "release" is a branch update. Its pattern is followed: a record, a chain of internal ledger tasks,
  the next one made only once the one before is verified.
- **M10a workspaces** for the tests and the preview. A workspace runs with `--network none` and no
  published port, so a preview inside it can't be reached from the person's browser. Tests and the
  preview run on this computer instead, after the person's OK (tier 2), as M5 already runs a
  provider's test. This is the main known limit (below).

## Where things live

`<home>/workers/coding/` (sync doesn't journal `workers/`, and checkpoints skip it):
- `repos/<key>.git`: Nova's own bare repository per source repository (`key`: a hash of its real
  path). Only Nova's git touches it; it fetches the branch from the person's repository (reading
  only).
- `runs/<run>/tree`: the git worktree on `nova/<run>`, where the commit is made and tests and the
  preview run.
- `runs/<run>/work`: a plain copy of the tree for the coding agent: no `.git`, so the agent never
  has a git directory to change (M8's rule: never a `.git` in a task's folder).
- `records/`: Nova's own record of each test run and preview, read back by its checkers.

## Nova's git

Every git call is argv (never a shell string) with:
- `GIT_CONFIG_NOSYSTEM=1`, `GIT_CONFIG_GLOBAL=/dev/null`, `GIT_ATTR_NOSYSTEM=1`, `GIT_TERMINAL_PROMPT=0`,
  `HOME` an empty folder of Nova's, and no other `GIT_*` variable from Nova's environment;
- `-c core.hooksPath=/dev/null` (no hook runs, the person's included), `-c core.fsmonitor=false`,
  `-c protocol.allow=never -c protocol.file.allow=always` (only local paths, so nothing is fetched
  from or sent to a network), `-c credential.helper=`, `-c core.sshCommand=false`, no signing,
  `-c gc.auto=0`, `-c core.autocrlf=false`;
- `diff` with `--no-ext-diff --no-textconv`.

The person's repository is only ever read (a fetch from it into Nova's repository) until the merge.
The merge is the only write. *As changed by the review of PR #239:* the reviewed commit's objects go
in as a pack made in Nova's repository and unpacked in theirs (no fetch runs in their repository, so
no `insteadOf`, protocol or helper of theirs decides anything), then always
`update-ref <branch> <reviewed> <base>`, a compare-and-swap that fails if the branch moved, whether
or not it is checked out. Only then, and only if the checkout that had the branch still has it, its
files are brought from the base to the reviewed commit (`read-tree -m -u`). Each transport git knows
(`http`, `https`, `ssh`, `git`, `ext`, `ftp`, `ftps`, `fd`) is also refused by name, since a
repository's own `protocol.<name>.allow` outranks `protocol.allow`.

**Known gap:** a checkout in the person's working tree runs the clean/smudge filters their own
`.git/config` defines (Git LFS, say). Nova doesn't turn those off: they are the person's own tools for
their own repository, and turning them off would leave LFS files as pointers.

## The steps in detail

**Starting (`code_change`, `POST /coding`).** The repository must be a folder `checkFolder` allows and
a git repository (`rev-parse --is-inside-work-tree` or a bare one, read with Nova's git), with the
branch (default: the one checked out). The worker must be an enabled coding agent or chat provider.
The test command is required (a run is never reviewed without a test). The run is recorded and step 1
made, at the task's privacy mode: a local-only task with an agent off the devices is refused when it
is made, in the ledger's words.

**Write.**
1. Fetch the branch into Nova's repository; the base is its commit, recorded.
2. A fresh worktree on `nova/<run>` at the base (an earlier attempt's is removed first, so a retry
   starts clean).
3. The plain copy for the agent, from Nova's own walk of the worktree (files and links as links; no
   `.git`).
4. `Providers.workIn(agent, …)`: the brief is the goal, the files and what may change.
5. Nova walks the copy and compares it with the base, by content: added, changed, deleted, mode
   (executable or not), links. Refused, with nothing committed: a path through `.git`, a link whose
   target leaves the folder, a hard link, a FIFO, socket or device, more than 200 files or 50 MB, and
   anything outside what may change. Nothing changed is a failure too ("changed nothing").
   *As changed by the review of PR #239:* a link is followed through every other link in the tree
   (`q -> .` then `p -> q/../../x` leaves it); a file over 50 MB is listed by its size and never read,
   and a walk reads at most 1 GB; what may change is source files, documents and images (by
   extension), never the tests or anything that decides how they run (`runsTests`: any hidden file
   such as `.npmrc`, manifests and lockfiles, `*.config.*`, `tsconfig*`, build files, test-runner
   names), unless the person lists what may change through the API; chat can't widen it, and both
   sheets show the rule in force.
   A diff over 512 KB is not offered for review at all: the step fails.
6. The change goes into the worktree and is committed (`Nova <nova@localhost>`, hooks off). Nova's walk
   of the worktree must then equal its walk of the agent's copy, and `diff --name-status base head`
   must list exactly the changes.

**Update** (a new round after the branch moved): fetch the new tip, `merge --no-edit` it into
`nova/<run>` in the worktree. A conflict aborts the merge, fails the step with the files that
conflict, and ends the run. Otherwise the new head and the new base (the new tip) are recorded.

**Check.** Before running anything: the worktree's HEAD is the head, and Nova's walk of it equals
the commit. Then the test command, through the shell as a person would type it, in the worktree with
`testEnv` (no keys, no tokens, a throwaway home), within its timeout. Its record: command, commit,
exit, the last of its output, duration. A failure is the step's failure. Then the preview, if asked
for: started in its own process group with `HOST=127.0.0.1` and `PORT=<free port>`; it must answer an
HTTP request at `http://127.0.0.1:<port>/` within its timeout (any status below 500), and on Linux
Nova reads `/proc/net/tcp` and `tcp6`: if anything listens on that port on an address other than
loopback, the preview is stopped and the step fails. The preview keeps running until the run ends.

**Merge.** Before anything is written:
- the run is still under review, and its head is the head this task was made for;
- Nova's branch `nova/<run>` still points at it;
- the person's branch is still at the base. If not, the step fails with "the branch moved since
  review" and a new round starts (Update, Check, Merge), which asks again.

Then the objects go in; then, in one step with nothing awaited between, Nova checks the task wasn't
cancelled meanwhile and marks the commit point (the ledger's `committing`). From there a cancel, a
decline or a discard is refused ("Nova is already moving main…"), so the record always says what
git did. Then the compare-and-swap; a branch that moved in that window starts a new round, as above.
A branch that is already at the reviewed commit (an earlier attempt moved it and Nova stopped) is
merged, not failed. Nova reads the branch back. The preview stops; the worktree, the run's records
and, once no open run uses it, Nova's copy of the repository are removed.

**Stopping.** Cancelling any open step ends the run: the preview stops, the worktree goes. Cancelling
the merge step is how the person declines (`POST /coding/runs/{id}/decline` does the same).
`POST /coding/runs/{id}/discard` is the tier-1 undo of the write: it removes the worktree and its
branch while nothing runs.

**After a restart.** A write that was running runs again (it starts clean). A check that was running
waits for the person ("may already have happened"), since it runs the agent's code. A merge that
passed its commit point waits for the person too; one that didn't may run again. A preview doesn't
survive a restart: the run's record says it stopped, and the merge ask says so. A preview's whole
process group goes when the command Nova started exits, and when its run ends or Nova closes; after a
crash, Nova stops a recorded preview group only if its leader is still the process it started (pid and
start time), or only the group is left.

**What the tier-2 OK means.** The tests and the preview run the agent's code as the person, on this
computer: that code can do anything the person can, Nova's own home and files included (its records,
its worktree, its database). Everything Nova promises after that point, the merge of exactly the
reviewed commit included, is only as strong as that decision. The check sheet says so in those
words.

## API

- `GET /coding`: the runs, and which coding agents are on.
- `POST /coding`: start a run (`{repo, branch?, goal, test_command, preview_command?, agent?, editable?,
  privacy_mode?}`); returns the run and its first task.
- `GET /coding/runs/{id}`: the run: its steps and tasks, the reviewed diff, the test record, the
  preview.
- `POST /coding/runs/{id}/decline`, `POST /coding/runs/{id}/discard`.
- The steps are approved and cancelled through `/tasks` like every other task.

All of them go through the console's checks (a session, the X-Nova header, the Host check).

## Chat

- `code_change` (no approval of its own: starting is tier 1, since everything it writes is Nova's
  own; in a run that has read outside content it asks first, as the ingest gate's `GUARDED` steps do).
  It answers with the run, and says the person will be asked before the tests run and before the merge.
- `code_status`: each run's state in words.
- When a run reaches the merge ask, fails, or is merged, Nova tells the person (a proactive message,
  through the trigger engine).

## UI

In Tasks, a coding step that waits for the person opens a sheet of its own:
- **Check:** what the agent changed (each file, +/−, the whole diff one tap down), the commands Nova
  will run, and in plain words that they run the agent's code as the person.
- **Merge:** the reviewed diff, the test result (command, passed, the end of its output), the preview
  link (or that it stopped), what merging does ("moves main in … from abc1234 to def5678: exactly this
  diff; Nova doesn't push"), the tier-3 checkbox before Confirm, and "Don't merge".

## Gate tests (each written first, seen failing)

- `tests/core/coding-git.test.ts`: Nova's git refuses network transports and runs no hook, from the
  person's repository or its own.
- `tests/core/coding.test.ts`: the steps through the ledger with the Claude Code stand-in, on throwaway
  repositories in a temp folder (a bare one as the "remote", and a clone of it as the person's):
  - the reviewed diff, green tests and a running preview, then the merge ask at tier 3;
  - declining: the person's branch, its whole `.git` and the bare remote byte-identical;
  - approving: the branch is exactly the reviewed commit, `git diff base branch` is the reviewed
    diff, the bare remote unchanged (no push);
  - the branch moved after review: no merge, a new round, a new ask;
  - a failing test: no merge task, ever;
  - refused changes: a test file, a path in `.git`, a link out;
  - a preview that listens on every address is stopped and fails the step;
  - Codex's and Relay's stand-ins as the worker.
- `tests/acceptance/m10c-coding.test.ts`: the real server with a blank profile and the egress tripwire:
  a coding request in chat (a scripted chat model calling `code_change`), the steps to the merge ask,
  declining, then a second request approved; the fresh-user test unchanged.
- `tests/ui/m10c-coding.test.ts` (`scripts/ui-test.sh`): the check and merge sheets in Chromium: the
  diff, the test result and the preview link before Confirm, Confirm disabled until the checkbox.

## Test safety

Every repository is made in a temp folder (`mkdtemp(os.tmpdir())`) with a bare repository beside it
as the "remote". No test operates on this repository or any other checkout on this machine, and
nothing pushes. The coding agents are the stand-ins in `scripts/stand-ins/` (scripted, deterministic
edits, never a model). Previews bind 127.0.0.1 on a free port and are stopped in teardown.

## Gaps, written down

- **Tests and the preview run on this computer, as the person**, after their OK (tier 2), and may
  write anywhere the person can, Nova's own home included: the merge's guarantees are only as strong
  as that OK. An agent's
  code can do what the person can. In an M10a workspace they could run without asking, but a preview
  there can't be reached (no network, no published port). Building a port relay over `docker exec`
  (as the egress relay does the other way) is the way to that; not built.
- **The test command may reach the network** (an `npm ci`, say). Nova doesn't stop it on this
  computer; the person sees the command before OK'ing it. The privacy gate covers the agent, not
  the test command.
- **The preview link works on this computer only** (`127.0.0.1`), not from a paired phone.
- **Deploying is not built.** The ADR names "merge or deploy per tier"; M10c merges into a local branch
  (tier 3). Pushing or deploying would also be tier 3 and needs a target the owner names; nothing
  pushes.
- **A merge can't be undone by Nova.** The branch update is tier 3 because it is the person's shared
  branch; going back is a revert by the person.
- **Only fast-forwards to the reviewed commit.** When the branch moved, the new round's merge commit is
  reviewed again rather than rebased.
- **The preview doesn't survive a restart** of Nova; the merge ask says it stopped.
- **The loopback check reads `/proc/net`**, so it is Linux only; elsewhere it says it wasn't checked.
- **The free port is chosen, then handed to the preview**: something else could take it in between,
  and the preview then fails to start (the step fails; nothing is exposed).
- **The loopback check looks twice, when the preview first answers** (the review of PR #239, item 11):
  every TCP listener of the preview's process group, and anything on its port. It doesn't catch a
  listener opened later, UDP, or a process that left the group (`setsid`).
- **A test command that ignores SIGTERM outlives its timeout** until it exits by itself (`runLines`
  sends only SIGTERM on a timeout); found by the review's probe, not one of its items, not changed here.
- **What may change, by default, is decided by name and extension.** A file that changes how tests run
  under a name Nova doesn't know (a custom runner's settings in a `.json` the test command doesn't
  name, say) is caught only because JSON, YAML, TOML and INI need the person's list; a source file can
  still change what the tests import, which is the point of the change and is in the reviewed diff.
- **After a crash, previews are stopped on Linux only** (start times come from `/proc`).
