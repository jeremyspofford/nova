# M5 plan — agents and integrations

Roadmap M5. The packet sources are:
- CONTRACTS §1 (envelope), §2 (receipts), §4 (manifest);
- EXTENSION-MODEL (kinds: agent adapter, automation adapter, connector);
- NOVA-SPEC §6 (tiers);
- LOCAL-FIRST §2 (privacy modes);
- ADR-6 and ADR-8 (vendor SDKs are adapters behind Nova's contracts);
- WORK-LEDGER-AND-VERIFICATION;
- DESIGN-SYSTEM, including the perception principles.

The capability inventory rows are 12, 40, 42–46 and 58.

**Gate:**
- the same brief is executed by two different providers through the envelope;
- the evidence is verified for both;
- a task is taken over and handed back mid-task.

**Hard limits for this milestone (OPERATING-RULES):**
- No external accounts are created and no money is spent. Tests and CI use stand-ins that speak each provider's real protocol (the CLIs' JSON event streams, the OpenAI-compatible HTTP API, n8n's webhooks, Home Assistant's REST and WebSocket APIs).
- One real provider runs locally for evidence: **Ollama**, which is free and already serves a model on this machine.
- A real **Claude Code** evidence run needs the owner's OK first, because it uses their subscription.
- Codex, n8n and Home Assistant aren't installed here. Their adapters are built and tested against stand-ins, and checking them for real is listed for the owner.

**Rules as before:**
- no runtime dependencies;
- erasable TypeScript in `src/core`, vanilla JS in `ui/`;
- neutral placeholders;
- tests for everything;
- code outside `src/core` imports only `src/core/index.ts`.

Era 1 is the reference for:
- the provider contract and its adapters: `packages/providers/src/{types,wire,sse,collect,openai-compatible,mock}.ts` at `6e2cf142`, plain `fetch` + SSE;
- the ACP host: `packages/core/src/acp/*`;
- the vault: `packages/secrets/src/{vault,keychain,select}.ts`;
- browser takeover: `packages/core/src/browser/session.ts`. Era 1 used Playwright at runtime; we drive Chromium over CDP ourselves.

## 1. Providers (M5a) — `src/core/providers/*`, migration as needed

**The registry generalizes `agent_cmd`.**
- **What a provider is:** an extension of kind `agent-adapter` or `automation-adapter` (EXTENSION-MODEL), with the CONTRACTS §4 manifest plus `adapter`:
  - `class`: `coding-agent` | `chat` | `automation`;
  - `transport`: `cli` | `http`;
  - `egress`: `none` | `local` | `remote:<host>`;
  - `capabilities[]`, `config` (command or base URL, model) and `secrets[]` (names only).
- **Each enabled provider is a ledger Worker.**
  - It runs a Brief and returns a Report through the envelope (CONTRACTS §1).
  - It is gated by `permits(privacy_mode, egress)`.
  - Every model or agent call records a context receipt (CONTRACTS §2).
- **Health.** "Installed / not installed / not configured / unreachable", in plain words.

**Built-in adapters (installed, enabled only when configured):**
- **`claude-code`** (coding agent, CLI). `claude -p --output-format stream-json` in the task's workspace. Egress `remote:anthropic`.
- **`codex`** (coding agent, CLI). `codex exec --json` in the task's workspace. Egress `remote:openai`.
- **`openai-compatible`** (chat, HTTP). This is Era 1's adapter, ported: `fetch` + SSE, base URL and model, and a key from the vault when one is needed.
  - **The Ollama profile** defaults to `http://127.0.0.1:11434/v1`. Its egress is `local` when the base URL is loopback or a mesh address, and `remote:<host>` otherwise.
  - **To act on files,** a chat provider gets the brief with a strict JSON reply contract (`{files:[{path, content}], notes}`). Nova applies that reply inside the task's workspace and nowhere else, and checks every path.
- **`custom-cli`.** Era 2's `NOVA_AGENT_CMD` becomes a provider entry, so the existing chat runner keeps working unchanged. Era 2's chat goes through the registry, using the provider the profile names for chat, which defaults to what `agent_cmd` names today.
- **`n8n`** (automation, HTTP). It covers both directions:
  - **Outbound:** POST to a workflow's webhook URL with an HMAC-SHA256 signature and the brief.
  - **The report:** comes back through Nova's existing token webhook (M2) as a callback that carries `task_id`, the result and `confirmation` evidence. Nova checks it.
  - **Inbound triggering** stays M2's webhooks.

**Per-task workspace.** A coding or chat provider works in `workspace/tasks/<task-id>/`, never anywhere else. A brief can name existing workspace files, which are copied in; the results are copied back only after verification passes.

**Verification (Nova checks it itself).**
- `file_diff` is checked against the task workspace.
- `test_result` means Nova runs the brief's declared test command itself in the task workspace, never trusting the provider's claim. It is tier 2: running a command asks first, unless policy allows it.
- `read_back` is checked as now.
- A provider that reports success with evidence that doesn't hold ends `failed`, with the verifier's reason.

**PWA:** Settings › Providers.
- Each provider shows its class, egress, health and configuration. Enable is tier 2.
- Choose the provider for chat, and the default per class. The app recommends one rather than listing options (perception principles).

### §1 as built (M5a, branch `m5a/providers`)

**Modules.** `src/core/providers/`: `registry.ts` (the registry, the workers, the choices, the n8n callback, `/api/v1/providers`), `builtins.ts` (the five built-in manifests and their settings fields), `claude-code.ts`, `codex.ts`, `openai.ts` (Era 1's SSE parser and compatible adapter, cut down), `custom-cli.ts`, `n8n.ts`, `taskspace.ts`, `checks.ts`, `prompt.ts`, `cli.ts`. PWA: `renderProviders` and its sheets in `ui/js/surfaces.js`.

**For the gate (items 1, 2 and 4).**
- **Stand-ins** (`scripts/stand-ins/`, all loopback, none reaches a model):
  - `fake-claude.js` speaks `claude -p --output-format stream-json --verbose` (system init, assistant text and tool_use, user tool_result, result with cost and usage); `fake-codex.js` speaks `codex exec --json` (thread/turn/item events, turn.completed with usage, turn.failed). Both take `--script <file.json>` (steps `say`, `read`, `edit {path, old, new}`, `write {path, content}`, `run`, then `result`, or `error`; `script.js` documents it) and really edit files in the folder they are started in; `--record <file.jsonl>` keeps their argv, folder and stdin. Configure the provider's `command` as `node <abs>/scripts/stand-ins/fake-claude.js --script <abs>/honest.json`; Nova adds the real flags after it.
  - `fake-openai.js`: `startFakeOpenAI({model, reply, key?})` → `{url, requests, close}` (`/v1/models`, `/v1/chat/completions` streamed as SSE or not); `filesReply(files, notes)` makes a JSON-files-contract reply. From the command line: `node scripts/stand-ins/fake-openai.js --model m --reply reply.json` prints its address.
  - `fake-n8n.js`: `startFakeN8n({secret, nova, token, behavior})` → `{url, received, callbacks, close}`; it checks Nova's signature, answers 200, then calls back signed. `behavior`: `done`, `failed`, `silent`, `bad-signature`, `wrong-task`, `no-confirmation`.
  - `tests/support/providers.ts`: `writeCalc(workspace)` (the failing `calc/sum.mjs` and its test), `calcTask(owner, over)` (the brief), `script('honest' | 'liar' | 'wrong' | 'error')`.
- **Setting a provider up:** `PUT /api/v1/providers/{id}/config {config}` (secrets only as `secret://NAME`; for n8n the reply carries the callback token, once), `POST /api/v1/providers/{id}/enable {approved: true}` (tier 2: without it, 403 with what it asks for), `POST …/check` for an HTTP provider's reachability, `PUT /api/v1/providers/choice {for: chat | coding-agent | automation, id}`. `GET /api/v1/providers` has each provider's class, `egress {coarse, receipt, words}`, `health {state, words}` (ready / not_installed / not_configured / unreachable / unchecked) and the choices, current and recommended. Secrets come from `NOVA_SECRET_<NAME>` until the vault (M5b) answers `CoreOptions.secrets`.
- **Submitting a brief to a named provider:** `POST /api/v1/tasks` with `owner: "<provider id>"`, `context_refs: [{kind: "file", ref: "workspace:calc"}]` (copied in), `inputs: {test_command: "node --test calc/sum.test.mjs"}`, `evidence_required: [{kind: "test_result"}, {kind: "file_diff", target: "workspace:calc/sum.mjs"}]`. A declared test command makes the task tier 2 (`POST /tasks/{id}/approve`) unless `PUT /api/v1/providers/policy {task_tests: "allow", confirm: true}`. A local-only task naming a remote provider is refused at once (400: "Claude Code sends data off your devices, and this task is local-only…").
- **Reading the verification:** `GET /api/v1/tasks/{id}`: `verification.checks[].why` ("Nova ran `…` itself in the task’s folder: it passed (exit 0, …)", "Nova compared calc/sum.mjs in the task’s folder with the copy it started from: 1 line added, 1 removed, as reported"); a failed task's `reason` is the verifier's. `GET /tasks/{id}/events` has `copied_back {copied, deleted, skipped}` once the results are in the workspace. `GET /api/v1/receipts?task_id=` is one receipt per call, with the provider's egress (`remote:anthropic`, `remote:openai`, `local`).
- **n8n:** the brief goes out as canonical JSON with `x-nova-signature: t=<s>,v1=<hex HMAC-SHA256 of "<t>.<body>">`; the workflow calls `POST /api/v1/hooks/n8n-callback` with `x-nova-hook-token` and the same signature over the canonical JSON (keys sorted, no spaces) of `{task_id, status, summary, confirmation: {id}}`. In a real n8n, a Code node computes that signature with the `crypto` module.
- **Ollama for real (item 2):** run on this machine, 2026-10-30, with `qwen3-coder:30b`: the calc brief ended **done**, verified (Nova's test run passed, the diff checked), receipt egress `local`; a chat call answered "2 + 3 = 5." (the first call took 100 s, loading the model).

**Deviations, with reasons.**
- **A provider extension can't ship code.** Its manifest's `adapter.implementation` names one of the five built-in implementations and gives it settings; Nova runs nothing an extension brings (the extension host's rule since M1).
- **Nova's test run happens in the worker, before the verifier reads its record**, because checkers are synchronous: the provider finishes, Nova computes the diff, runs the declared command in the task's folder and records the run (`workers/providers/runs/`). The report's `test_result` names that record (`nova-run:<id>`); the checker reads it back and refuses it if the files changed since. A provider's own claim about tests is never evidence.
- **Baselines live outside the workspace** (`workers/providers/tasks/<id>/`), so a provider can't rewrite what its diff is checked against; the task's folder is removed after a successful copy-back and kept after a failure, for inspection. A file changed in the workspace while the task ran is not overwritten: it is named in a problem.
- **The test-command approval is the task's approval**: a worker can now ask for a minimum tier (`minTier` on `LanedWorker`).
- **Settings and choices live in the profile's new `providers` section** (replicated like the rest of the profile); the generic profile route refuses them, so every change is checked. The n8n callback token is kept as a hash there.
- **Chat:** `custom-cli` (agent_cmd) stays Era 2's own path in `src/agent.js`; only another chosen model goes through the registry's `chat()`. `chat-run` tasks follow the chosen model's egress.
- **Health never runs a command** (it looks the program up on PATH), and **no check reaches a remote address under local-only** (the egress tripwire caught one in testing).

**Known gaps.** Real Claude Code and Codex runs, a real n8n workflow: the owner's checks. A chat model gets one call per attempt (no back-and-forth with test output). Claude Code is started with `--permission-mode acceptEdits` and file tools only by default; Bash is the person's to add (`allowed_tools`). A CLI agent runs as the person's user: the task's folder is where it is told to work, not a sandbox (Codex's own `workspace-write` sandbox is used). Verification that fails reruns the provider (the ledger's three attempts). Nova's test-run records, baselines and n8n callbacks live in `workers/providers/` on the node that ran the task and aren't synced, so a task that fails over mid-run starts again (settings and choices are in the profile and do replicate).

## 2. Connectors and the vault (M5b) — `src/core/{vault,connectors/*}.ts`

**The vault** (inventory row 58; Era 1 port).
- **Storage:** secrets are encrypted at rest (AES-256-GCM) in `home/vault/`, mode 0600.
- **The key:** held by the OS keychain when one is available (`secret-tool` / Keychain / Credential Manager). Otherwise in `home/vault/key` (0600), and the person is told plainly that the key sits next to the vault on disk.
- **References:** `secret://<name>`.
- **Out of history:** the vault is untracked in the home's git, a test proves it, and it is redacted from logs, receipts and sync.
  - On a standby it replicates, sealed. Connectors that need it work again after a failover, which closes M4's note about `connectors/`.
- **Migration:** Era 2's plaintext connector secrets move into the vault and are deleted.

**The connector kind.** It has a manifest and owns its auth through the vault, its sync, and its events, which become M2 event triggers. Removing a connector revokes its secrets and subscriptions (EXTENSION-MODEL).

**Gmail.** Era 2's Gmail (OAuth PKCE and IMAP app password) is repackaged as a connector extension, with the same behaviour: it reads, drafts and organizes, and never sends or deletes. Its secrets move into the vault, and mail events become triggers.

**Home Assistant connector.**
- **Setup:** a base URL plus a long-lived token, kept in the vault.
- **Reads entity states** (tier 0).
- **Calling a service is tier 2,** because "changing devices/home state" asks first (NOVA-SPEC §6). Domains the person marks are tier 3.
- **State changes** arrive over HA's WebSocket API as `event` trigger records.
- **Egress** is `local` for a LAN or mesh address.
- **Testing** uses a stand-in HA server (REST + WebSocket) in the test support.

**PWA:** Settings › Connections. Connect, status, what it can do in plain words, disconnect.

## 3. Browser work with human takeover (M5c) — `src/core/browser/*`

- **A browser worker** drives Chromium over CDP: `--remote-debugging-pipe` or a port bound to loopback, using Node's built-in WebSocket client and no Playwright at runtime.
  - **Where Chromium comes from:** `NOVA_CHROMIUM` or a known install path. Health says plainly when there isn't one. The dev host here can't start Chromium; it runs in the Playwright container and in CI.
  - **What a browser task is:** steps a provider or a scripted plan chooses (navigate, fill, click, read).
  - **Egress** is declared per task as allowed hosts, and enforced by intercepting requests with CDP `Fetch`. Anything else is blocked and recorded.
  - **Page content is data, never instructions:** nothing from a page changes the task's brief or permissions.
- **Takeover (Era 1 parity: pause, resume, frame stream).**
  - **Who can take over:** the person can, at any time. The worker also requests it when a step needs a human (a login, a challenge); the task goes to `waiting` / Needs you.
  - **Live view:** the PWA shows CDP screencast frames over the core event stream, or a dedicated SSE stream.
  - **Input:** the person's pointer and keys go through `Input.dispatch*`.
  - **While taken over,** the worker does nothing.
  - **Hand-back** resumes the plan from the page's current state.
  - **The ledger** records `takeover_started` and `takeover_ended`, with who did it and for how long.
  - **Access:** only the console and `can_approve` clients can take over. A screenshot or frame is never cached by the service worker.
- **Evidence:**
  - `screenshot`, stored in the task's folder;
  - `url` with an expected-content check, where Nova re-fetches the page itself (inside the declared hosts) or reads the final DOM through a fresh CDP read;
  - a `confirmation` from the system the page talks to, when there is one.

### §3 as built (M5c, branch `m5c/takeover`)

**Modules.** `src/core/browser/`: `cdp.ts` (the CDP client over `--remote-debugging-pipe`), `chromium.ts` (finding and starting Chromium, a fresh profile per task), `plan.ts` (the step plan, declared hosts, where a plan's data goes), `session.ts` (one task's browser: request holding, the refusing proxy, screencast, input, takeover), `worker.ts` (the ledger worker and the live sessions), `evidence.ts` (the `screenshot` and `url` checkers, Nova's own re-fetch), `routes.ts` (the API). PWA: `ui/js/takeover.js`, and `takeoverPanel`/`takeoverState` in `ui/js/components.js`.

**For the gate (item 3).**
- **The test site:** `scripts/form-site.js`. Standalone, `node scripts/form-site.js [port]` serves it on 127.0.0.1 and prints the address. In a test, `startFormSite()` returns `{url, host, port, records, hits, drafts(), codeFor(id), close()}`. The flow is `/start` (`?person=0` leaves out the person's step; `?delay=ms` slows the first answer) → `/form/<id>/details` (`#name`, `#email`, `#newsletter`, `#next`) → `/form/<id>/check` ("A person must do this step": a code drawn in a picture, `#code`, `#confirm`; the code is in `drafts()`) → `/form/<id>/plan` (`#plan`, `#note`, `#review`) → `/form/<id>/review` (`#submit`) → `/done/<record>` (`#status` "Received"). `records` (also `GET /records`) is the site's own record of what was sent, `person_checked` included; `hits` is every request it saw. `/leaky` reaches an undeclared host three ways (an image, a fetch, a WebSocket).
- **The server:** `NOVA_CHROMIUM=<path>` (else `CHROMIUM`, else known install paths; `GET /api/v1/browser` and Health say plainly when there is none) and, in a container, `NOVA_CHROMIUM_SANDBOX=0`. `tests/ui/m5c-support.ts` has `browserEnv()`, `formPlan(site, {person, delay})`, `browserTask(plan)` and `waitTask()`.
- **Submitting:** `POST /api/v1/tasks` with `owner: "browser"`, `evidence_required: [{kind: "screenshot"}, {kind: "url"}]` and `inputs: {allowed_hosts: ["127.0.0.1:<port>"], steps: [...], verify: {expect: [...], url?}}`. Steps: `navigate {url}`, `fill {selector, value}`, `select {selector, value}`, `click {selector}`, `wait {selector}`, `read {selector, expect?}`, `person {why, done_when?}`; any step may carry `label` and `timeout_ms`. A plan that names a host outside its own list, or a remote host on a local-only task, is refused when it is delegated (400, with the reasons).
- **Taking over from a test:** over the API, `POST /api/v1/browser/tasks/{id}/takeover`, then `/input` (`{type: click|move|scroll, x, y}` with x and y as fractions of the picture, `{type: text, text}`, `{type: key, key}`), then `/handback`; `GET /api/v1/browser/tasks/{id}` is the live state and `/frames` the event stream (`state`, `frame`). In the PWA: Home's Needs-you card (or Tasks) → the task → the sheet's one standout, **Take over**; click on `#sheet .takeover-frame`, type with it focused (or in the `.takeover-type` field), then **Hand back**. `tests/ui/m5c-takeover.test.ts` does exactly this, aiming at the page by measuring it in a browser of its own at Nova's size (1280×800).
- **The ledger:** `step {n, of, what}`; `needs_person` (active → waiting, Needs you, the reason "Needs you: <why>"); `takeover_started {by, who, requested, asked?, step, url}`; `takeover_ended {by, who, duration_ms, how}`; `person_done` (waiting → active); `blocked_request {host, by, via, kind}`; `popup_closed`. `by` is `console` or `device:<id>`.
- **Evidence:** `workers/browser/<task>/final.png` in the home (the task's folder: outside every workspace a provider can write to, and untracked in the home's history); `final-read.json` beside it holds Nova's two fresh reads of the final page (a re-fetch inside the declared hosts, and the final DOM). The checkers compare them with `inputs.verify.expect`.

**Deviations, with reasons.**
- **The ledger** gained what a worker that waits for a person needs: `waiting → active`, and `needsPerson`, `personDone` and `note`. `retry` refuses while the worker still runs. After a restart, a task that waited for the person starts again from the beginning, because its browser is gone.
- **A worker's egress can depend on the brief** (`egressFor(brief)` on the Worker interface): a browser task on a loopback or private host is `local`, so a local-only task can use the local site; anything else is `remote`. The ledger checks it at creation and at every gate.
- **The `url` checker reads what Nova read**, because checkers are synchronous: before it reports, the worker re-fetches the page and reads the final DOM into the task's folder, and the checker compares those with the brief. A report's own claim is never read.
- **A second wall behind CDP Fetch:** Chromium's proxy setting sends whatever Fetch can't see (WebSockets) to a local proxy that refuses it, except for the declared hosts. Chromium's own calls home end there too; they are recorded (`by: "browser"`) but left out of the task's summary and the live view.
- **The takeover view is a sheet**, opened from the task, not a new route: wide on a desktop, full width on a phone, where the page is drawn at a readable size and scrolls.
- **No `confirmation` checker** for the form site: the proof that the site holds the submission is Nova's re-fetch of the site's own record page (`/done/<record>`), and the tests read `records` themselves.

**Known gaps.** Screen (desktop) control isn't built. There is no prompt-injection classifier: a plan's steps never come from a page, so page text has nothing to steer, but a provider that chooses steps from page text (later) will need one. A browser task interrupted by a restart starts over, so a plan that already sent a form could send it again. Verification that fails requeues the task (the ledger's rule), which reruns the whole plan.

## 4. Gate (M5d) — `tests/ui/m5-*.test.ts` plus integration tests

1. **One brief, two providers.** The brief is "make the failing test in `calc/` pass". It goes through the envelope to:
   - (a) `claude-code`, a stand-in CLI that speaks its stream-json and edits files;
   - (b) `openai-compatible`, a stand-in OpenAI-compatible server that returns the JSON files contract.

   For each, Nova runs the declared test itself, checks the diff, and the task ends Verified with evidence. Receipts show each provider's egress, and a local-only task refuses the remote provider and says why.
2. **The same, for real, locally (evidence, not CI).** `openai-compatible` against the Ollama on this machine.
   - Claude Code for real only with the owner's OK.
   - If the local model can't solve the brief, the gate records that honestly, as a failed task with the verifier's reason, and then uses a simpler brief. It never fakes a pass.
3. **Takeover and hand-back mid-task.** A browser task fills a multi-step form on a local test site, in Chromium in the container.
   - At the step marked "a person must do this", the worker requests takeover and the task shows Needs you.
   - The person, in the PWA, takes over: they see the live frame and click or type through the step, then hand back.
   - The worker finishes. Nova verifies the site's final state itself.
   - Both takeover events are in the ledger.
   - Also tested: a voluntary takeover in the middle of an agent step.
4. **n8n** round trip against a stand-in: a signed outbound call, then a callback that carries evidence.
5. **Home Assistant** against a stand-in: a state read, a tier-2 service call with confirm, and an event becoming a trigger record.
6. **Fresh-user test still passes.**

**Evidence:** screenshots in `docs/screenshots/m5/`, and a transcript in `docs/evidence/m5-gate.md`.

**Manual checks for the owner:**
- real Claude Code (with OK);
- Codex if installed;
- a real n8n workflow;
- a real Home Assistant.

## Order

M5a, M5b and M5c run in parallel. Each keeps its edits to shared files (`src/core/index.ts`, `src/server.js`, `src/core/extensions.ts`, `docs/LEDGER.md`) small and additive. The gate (M5d) comes last. Migrations: each piece that needs one numbers it `0009` on its own branch (migrations must be gapless, so a piece can't test with a later number), and the integrator renumbers them at merge.
