# M7 plan — governed self-modification and resilience

Roadmap M7. The packet sources are:
- ADR-9 (sandbox → tests → health gates → versioned release → canary → automatic rollback; every change is a commit, every deploy a tagged, reversible version);
- EXTENSION-MODEL (lifecycle; the foundry);
- NOVA-SPEC §6 (self-modification deploys and core/security/permission changes are tier 3, confirmed every time) and §7 (supervised processes, health checks, automatic restart, repair playbooks; backups with a tested restore; hub failover);
- LOCAL-FIRST §5 (nightly backups and restore drills as gates);
- OPERATING-RULES: the pipeline's gates may never be weakened to make a change pass, and the running instance is never edited live.

**Gate:**
- Nova ships a real change to itself through the pipeline;
- a sabotaged change is caught by the gates and rolled back automatically.

Plus the roadmap's backup/restore drill and chaos pass, each with repair playbooks.

**Hard limits:**
- No accounts and no spending.
- No cloud backup target: the "optional encrypted cloud copy" is an encrypted copy to any folder the person names. A remote target is for the owner to choose later.
- Chaos runs only against test homes, stand-ins and processes the tests start. It never touches the owner's preview or homes.

Rules as before: no runtime dependencies, erasable TypeScript, neutral placeholders, tests for everything.

## 1. The change pipeline (M7a) — `src/core/changes/*`

**A change** is one versioned record, `{id, kind, target, artifact, proposed_by, tier, version, content_hash}`.
- `kind`: `extension` | `design-system` | `config` | `template` | `trigger-rules`.
- `proposed_by`: `person` | `foundry` | `provider:<id>`.

It moves through fixed stages. Each stage is a ledger event with evidence:
1. **Sandbox.** The change is applied to an isolated copy, never the live home: a scratch home built from a `VACUUM INTO` snapshot plus the needed files. A sandbox Nova process starts on it.
2. **Tests.**
   - The change's own tests: an extension ships tests; a template, its dry runs; a design system, its validation and contrast checks.
   - Contract checks: manifest, permissions review, egress, privacy.
   - The relevant part of Nova's own checks, run against the sandbox.
3. **Health gates.** The sandbox's `/health` and a smoke probe set: the change's own probe plus fixed core probes (setup state, ledger, memory, an approval, privacy refusal). They all pass, or the change stops here with the reason.
4. **Versioned release.**
   - The artifact and its hash are recorded.
   - The previous version is kept.
   - It is committed to the home's change history: files, never secrets.
5. **Approval** at the change's tier.
   - Extensions keep their own review; broad permissions are tier 2+.
   - **Self-modification deploys** (anything the foundry or a provider proposed) and anything touching core, security or permissions are **tier 3, confirmed every time** (NOVA-SPEC §6). Approval comes after the sandbox results, which are shown with it.
6. **Canary.** The change goes live in a limited scope:
   - a design system on one device;
   - an extension enabled for a canary window, and only for its first triggers;
   - a config key with a watch window.

   **Verification probes run over the window:**
   - health;
   - problems opened since the change;
   - the change's own probe;
   - error rate on the touched area.
7. **Promote, or roll back automatically.** Any probe that fails in the canary window restores the previous version on its own. That is recorded in the ledger as a task ending Failed with the probe's reason, and a problem is opened in plain words. Rolling back a live change by hand is always available (tier 2).

**Gates can't be weakened.**
- The pipeline's gate definitions are core: no change can alter them; a change that tries is refused.
- A change can't skip a stage.
- Canary windows and probe sets have minimums.

**The foundry** (EXTENSION-MODEL): Nova authors its own extensions for a need the person states.
- **Who writes them:** M5's providers, with the local model by default, inside the sandbox. The foundry never writes to core.
- **What it produces:** a trigger-rule pack, a decision template, a skill pack or a design-system variant, each with its manifest, tests and a health probe.
- **How it is installed:** disabled, and only through the pipeline.

**PWA: Settings › Changes.**
- the change list with its stage, evidence per stage, and the canary in progress with its probes;
- one standout: the tier-3 "Ship it" when a change waits for you;
- Roll back.

## 2. Supervisor and code releases (M7b) — `src/supervisor/*`

**A supervisor process runs the Nova server as a child** (NOVA-SPEC §7).
- **Restarts:** on a crash it restarts with backoff. A crash loop goes to safe mode: the server is held, the reason is written, and the last good release is offered.
- **Health checks** run on a schedule. Failures open problems with **repair playbooks**:
  - plain-words steps for the person;
  - automatic safe repairs where they are safe: restart a worker, requeue, resync the standby, reconnect a connector, restart the runtime agent.

**Code releases** (ADR-9: "every deploy is a tagged, reversible version").
- **Release slots:** `<releases>/<version>/` are git worktrees of a tagged commit, with a `current` pointer.
- **Deploying is tier 3:**
  1. the release's test suite;
  2. a sandbox start on a copy of the home;
  3. smoke probes;
  4. the switch;
  5. a canary window on the live home;
  6. automatic rollback to the previous slot when health fails in the window.
- **Database:** an upgrade's pre-migration backup (M1) is kept. A rollback across a migration restores that backup only when nothing was written since. Otherwise it refuses, says why, and keeps the newer release running with the problem open. It never silently loses data.
- `scripts/preview.sh` stays as it is: the owner's preview flow is a standing order.

## 3. Backups, the restore drill, and the chaos pass (M7b)

**Nightly hub backups:**
- a consistent `VACUUM INTO` snapshot plus the home's files (not the vault key, and not `mesh/` private keys);
- written to a local target the person names, with retention;
- optionally an encrypted copy (AES-256-GCM, key in the vault) to a second folder.

Forgetting holds in backups, as M2 established.

**The restore drill** runs as a scheduled ledger task, and on demand:
1. restore the latest backup into a scratch home;
2. start a sandbox Nova on it;
3. verify:
   - `PRAGMA integrity_check`;
   - the migration checksums;
   - the content hashes against the backup's manifest;
   - that forgotten items are absent;
   - a smoke probe.

The result is evidence on the task. A failed drill is a problem with its playbook.

**The chaos pass** (`tests/chaos/*`, plus the supervisor's playbooks). Each scenario covers detection, a plain-words problem, the playbook's automatic repair where safe, and a test:
- **Providers:**
  - the local model down mid-call;
  - a CLI agent crash and a hang;
  - a provider returning garbage.
- **The hub:**
  - a crash, so the supervisor restarts it;
  - a crash loop, so it goes to safe mode;
  - a dead hub, so M4 failover takes over.
- **The network:**
  - the standby partitioned from the hub;
  - a device offline (M4 queue);
  - DNS failing;
  - a slow link.
- **Disk:**
  - full, while writing the database, the vault or a backup;
  - the backup target missing.
- **Clock:** a jump forward or back (triggers, sessions, retention).

**As built, after review (§2–§3).** The details are in the ledger (2026-10-30, M7 review fixes).
- A forget reaches every folder Nova ever backed up to. A folder that isn't there owes it, with a
  problem saying so, until it is back; it is carried in before any backup, prune or drill. The
  drill checks every kept backup for forgotten things.
- Only backups Nova recorded and sealed count; strays are reported and left alone. Backups are
  0700/0600, in a folder only the person can write. Choosing it is tier 2.
- The encrypted copy opens with a recovery key shown once (tier 3 to see again), on any machine.
- Crash and hang problems close once Nova runs again; Nova never restarts itself as a repair.
  Asked-for restarts are limited and count toward safe mode.
- A release reports where the data stood before its work ran, so going back never undoes it.
- `base` is pinned to a commit at start. The control socket wants what the person typed. A
  same-user program can still speak to it as the CLI would (residual, in the ledger).

## 4. Gate (M7c) — `tests/acceptance/m7-*.test.ts` (+ `tests/ui/` for the Changes screen)

1. **A real change shipped by Nova.**
   - **The request:** the person asks for something small and real, such as a trigger rule pack for a daily wind-down reminder.
   - **The authoring:** the foundry writes it with the local-model stand-in in CI (with the real Ollama in an opt-in run), in the sandbox.
   - **The path:** it passes tests and health gates, waits for the person's tier-3 OK (which shows the sandbox evidence), canaries and is promoted.
   - **The result:** it works live, its reminder fires on the test clock, and the ledger shows every stage.
2. **Sabotage caught by the tests.** A change with a broken test or an invalid manifest stops in the sandbox and is never offered for approval.
3. **Sabotage caught in the canary, rolled back automatically.** A change that passes the sandbox but fails live: an extension whose probe fails under live data, or a design system whose live contrast check fails on one device. It is rolled back within the window, the previous version is restored, the ledger shows Failed with the probe's reason, a problem is opened, and nothing else changed.
4. **A change that tries to weaken a gate** is refused.
5. **A code release through the supervisor.**
   - **A good release:** a tagged release with a harmless change deploys (tier 3), canaries and stays.
   - **A sabotaged release:** one that breaks health after the switch is rolled back automatically to the previous slot, with the data intact.
6. **The restore drill passes,** and a corrupted backup is caught by it.
7. **The chaos pass passes,** with repair playbooks.

**Evidence:** `docs/evidence/m7-gate.md`.

## Order

M7a and M7b run in parallel. Each keeps its edits to shared files small and additive. Each numbers a migration `0011` (the integrator renumbers). The gate (M7c) comes last.
