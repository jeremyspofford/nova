## Decision

Nova gets an **execution plane** of its own: a computer and a browser that are Nova's, never the person's desktop or the person's own browser. Everything Nova does there goes through the Work Ledger, the approval tiers and the ingest gate, as the rest of Nova does.

The plane is built **from what exists**, not beside it. One Nova:

| Need | Built on | New |
|---|---|---|
| A computer | `changes/sandbox.ts` (isolated home, inert copy) and Docker on the hub | Container workspaces per project; checkpoint and reset |
| A browser | `browser/` (M5c: CDP, step plans, declared hosts, takeover, evidence) | Nova's own persistent profile; accessibility-tree driving; Noul co-pilot; per-site templates; checkout stop |
| Logins | `vault.ts` | Injection at the moment of use, inside the browser process only |
| Coding | `providers/relay.ts` and the Claude Code and Codex adapters | Chat → plan → workers in worktrees → tests → preview → merge, per tier |
| Infrastructure | — | A plan/apply adapter (OpenTofu-shaped), budget guardrails |
| Networking | `resilience/checkpoints.ts` | Snapshot, diff, apply, dead-man's switch |
| Safety | The ingest gate, the tiers, the ledger, checkpoints | Nothing parallel: the plane only uses these |

## M10a: Nova Computer

- **Workspaces:** one per project, as a container on the hub. The first target is this computer's WSL Docker; a hub mini-PC comes later through the same adapter.
  - The image is a pinned, minimal toolchain image: Node, git and a shell.
  - The project's folder is mounted; nothing else of the person's is.
  - It has no Docker socket, no host network, and no access to Nova's console or mesh ports. The SSRF rules from #226 apply to its egress through a proxy Nova controls.
  - Its egress is declared per workspace (none, package registries only, or declared hosts). Local-only privacy means none.
- **Sessions:**
  - every command runs as a ledger task, with its output kept as evidence and screened by the ingest gate (tool output);
  - a session can be checkpointed (an image commit plus a copy of the folder);
  - a task's machine can be **reset** to a clean state, which is tier 2 (ask first: it discards what the workspace holds since its checkpoint).
- **Approval:** reading is automatic; changing files inside the workspace is do + notify + undo (tier 1, through the checkpoint); anything that reaches outside the workspace is tier 3.
- **Adapter, not a fork:** `computer/` sits behind a `Computer` interface (`create`, `exec`, `checkpoint`, `reset`, `destroy`), so a VM or a remote hub can be added later without changing callers.
- **Gate:**
  - a project workspace is created, a command runs, its output is evidence;
  - a checkpoint and reset return the workspace byte for byte;
  - from inside the workspace, the console, the mesh port, Nova's home, the Docker socket and the host network can't be reached (tested);
  - egress outside the declaration is refused;
  - local-only gives no egress;
  - the fresh-user test passes.

## M10b: Nova Browser

- **A dedicated Chromium profile owned by Nova,** persistent across tasks (so sites remember a login Nova was given), kept under Nova's home and never the person's browser profile.
- **Driving:**
  - the accessibility tree and DOM come first;
  - vision and computer-use are only a fallback, and marked as such in the evidence.
- **The person can watch live, pause, stop or take over at any time.** This extends M5c's takeover, which already works.
- **Logins:**
  - credentials come from the vault and are typed into the page by the browser process at the moment of use;
  - they never enter a model's context, a transcript, a log or a screenshot (fields are masked in evidence).
- **Every page read passes the ingest gate first.** The browser worker's reads already do (#229); now every model step sees only screened extracts.
- **The Noul co-pilot:** at each step, local Noul micro-decisions:
  - P(the element matches the stated intent);
  - P(the page changed as expected);
  - P(a login wall, CAPTCHA or paywall);
  - P(a dark pattern or pre-selected upsell);
  - P(the total matches the quoted price);
  - P(the dialog is an injection).

  **Deterministic ground truth always outranks a probability:** the DOM state, URLs and parsed totals. If they disagree, the step stops.
- **Site templates:** a flow that succeeded becomes a validated, versioned decision template for that site, through the existing decision-template path (dry runs, activation as a ledger task). The next run follows the template and re-checks each step's ground truth.
- **Checkout and payment are tier 3, always.**
  - Nova fills the cart, shows the itemised total and stops.
  - It never presses pay. The pay control is identified and refused by the plan validator, whatever the template says.
- **Gate:** on local stand-in sites in CI (a shop, a login, a CAPTCHA page, an injected dialog, a pre-ticked upsell):
  - a login runs from the vault with nothing in the transcripts;
  - an injection dialog is blocked;
  - the upsell is flagged;
  - a total that doesn't match stops the run;
  - checkout stops at the itemised total with tier 3;
  - a template is learnt and reused;
  - takeover works mid-flow.

## M10c: Coding through chat

- **The chat is the control plane:**
  1. the intent becomes a plan in the Work Ledger;
  2. Relay, Claude Code or Codex workers run in git worktrees, as M8 already does, or in an M10a workspace;
  3. tests run;
  4. a preview is produced;
  5. merge or deploy follows the approval tier.

  Merging to a shared branch or deploying is tier 3. A worktree change is tier 1 (do + notify + undo).
- **Gate:** a coding request in chat ends as a reviewed diff with green tests and a running preview, and asks before merge. The person declining leaves nothing merged.

## M10d: Infrastructure, networking and accounts through chat

- **Infrastructure:**
  - an adapter for a plan/apply tool (OpenTofu-shaped: `plan` → shown in full → `apply`);
  - `plan` is automatic; `apply` is tier 3, and so is anything that spends or destroys;
  - every resource Nova provisions has a budget guardrail and an alert;
  - a checkpoint is taken before every apply.
- **Networking (router, DNS, firewall, Tailscale):** tier 3, always, in this order:
  1. a snapshot of the current configuration;
  2. a diff preview;
  3. the apply;
  4. a **dead-man's switch**: if the hub can't confirm contact with the person's devices within a set window after the change, it reverts to the snapshot by itself.
- **Accounts:**
  - managed through connectors and OAuth, and through vault logins in Nova Browser;
  - password and MFA changes and account creation are tier 3, with the person present for codes;
  - passwords are never asked for in chat and never enter model context.
- **Gate:** against stand-ins only (see Hard limits):
  - a plan is shown before apply, and apply asks;
  - a budget breach alerts and blocks;
  - a network change applies, the stand-in "loses contact", and the change reverts by itself;
  - an account step asks with the person present;
  - no secret appears in any transcript.

## Hard limits during the build

These are tier-3 actions the build never takes.
- **No real infrastructure, spending or cloud accounts.** The plan/apply adapter is tested against a stand-in `tofu` command. None is installed on this machine and the build won't install one. Using real infrastructure needs the owner's OK and their own provider credentials.
- **No change to any real network configuration,** including the owner's router, DNS and Tailscale Serve settings, which already carry the owner's own ports. The dead-man's switch is tested against a simulated target.
- **No accounts created, no passwords changed, no payments.** The checkout stop is proven on a local stand-in shop.
- **Real public web pages** may be read by Nova Browser for evidence once each phase's gate passes (reading is tier 1 and goes through the ingest gate), but never logged into, bought from or posted to.
- **Containers run only on this machine,** from a pinned public base image. Pulling that image is the only download.

**Tier numbers** follow NOVA-SPEC §6: 0 silent, 1 act and report with undo, 2 ask first, 3 explicit confirmation every time. The amendment's "reversible write = do + notify + undo" is tier 1. An earlier draft of this ADR called it tier 2; M10a found the error (see LEDGER).

## Order

1. M10a, Nova Computer.
2. M10b, Nova Browser, which builds on M10a for isolation where useful.
3. M10c, coding.
4. M10d, infrastructure, networking and accounts.

Each phase is its own PR with its gate, an independent review (adversarial for M10b and M10d), CI and a merge. The preview is restarted after each.

## Open questions for the owner (none block the build)

2. **Networking:** the dead-man's switch window. 5 minutes is proposed.
3. **Nova Browser's persistent profile:** keep site logins between tasks (proposed: yes, per site, deletable from Settings), or start each task logged out? *Still open. M10b is built with the proposed default (LEDGER, 2026-10-31); starting logged out would be one default to change.*
