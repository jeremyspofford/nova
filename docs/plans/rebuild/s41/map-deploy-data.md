Read-only. Every claim carries `path:line`. Written 2026-09-21 against

## 1. `install` (root) and `deploy/install.sh`

### 1.0 The two files

`install` (root, 21 lines) is a thin wrapper: it resolves its own directory,
checks `deploy/install.sh` is present and executable, and `exec`s it with all
args (`install:13-21`). It exists only so the documented command
(`./install`) is the command that runs — `install:2-8`.

The real script is `deploy/install.sh`, 1141 lines, `set -euo pipefail`
(`deploy/install.sh:8`), declared bash-3.2 compatible: no associative
arrays, no `${var,,}`, no `mapfile` (`deploy/install.sh:7`).

### 1.1 Phases, in order (`cmd_install`, `deploy/install.sh:1078-1123`)

1. `preflight` (`deploy/install.sh:322-329`) — `check_docker`, `check_compose`,
   `check_openssl`, `check_disk`, `check_ports`, `decide_inference`, each a
   `die` (exit 1) on failure (`deploy/install.sh:58,62-90,96-103,120-130`).
2. `detect_hardware` (`deploy/install.sh:808-863`) — writes
   `data/hardware.json`, decides the GPU overlay and the `inference` profile.
3. `generate_secrets` (`deploy/install.sh:912-927`).
4. `decide_tailnet` (`deploy/install.sh:537-614`) — reads/writes `.env`, may
   prompt on a TTY, may refuse (`refuse_tailnet`, `deploy/install.sh:520-535`).
5. `record_compose_files` (`deploy/install.sh:956-966`) then
   `record_compose_profiles` (`deploy/install.sh:990-1009`) — both write
   `.env`, and explicitly run **after** every `-f`/`--profile` decision above
   and **before** anything is pulled, built or started
   (`deploy/install.sh:1082-1089` states the ordering rule).
6. `compose_up` (`deploy/install.sh:1013-1016`) — `docker compose
   "${COMPOSE_ARGS[@]}" up -d --build`.
7. `wait_for_health` (`deploy/install.sh:1025-1054`, timeout 240s, polled
   every 2s, measured against the clock not a sleep count — comment at
   `deploy/install.sh:1029-1034` explains why) then `print_status`
   (`deploy/install.sh:1066-1074`).
8. On any unhealthy service: dump its last 20 log lines and `die`
   (`deploy/install.sh:1093-1105`).
9. `check_inference_compute` (`deploy/install.sh:746-806`) — reads ollama's
   own `msg="inference compute"` log line and refuses success unless it says
   the expected library; see §1.5.
10. Final message: `"Nova is up. Open http://127.0.0.1:3000..."`
    (`deploy/install.sh:1108`), plus conditional notes for
    `NOVA_SKIP_INFERENCE` (`:1109-1111`) and the tailnet DNS name
    (`:1112-1122`).

`cmd_update` is a stub that logs and exits 1 (`deploy/install.sh:1125-1128`,
`install:9`: "arrives in a later slice").

### 1.3 `.env` generation

`generate_secrets` (`deploy/install.sh:912-927`): copies
`deploy/.env.example` → `deploy/.env` if absent (`:913-916`), fills every
`SECRET_KEYS` entry that is still blank, then `chmod 600` **unconditionally**
on every run — not only when something was generated — so an idempotent
re-run still enforces owner-only permissions (comment,
`deploy/install.sh:921-926`).

### 1.4 Secrets: which exist, where they live

Generated by the installer, in `deploy/.env` (mode 600, gitignored —
`.gitignore:52` names `deploy/.env` explicitly): `POSTGRES_PASSWORD`,
`CORE_TOKEN`, `CORE_GATEWAY_TOKEN`, `CORE_MEMORY_TOKEN`, `SEARXNG_SECRET`
(`deploy/install.sh:29`). A stale `INSTANCE_SECRET` line may still exist in
an old `.env` — dead config, deliberately never removed
(`deploy/install.sh:20-25`).

Supplied by the operator, in `.env`, never generated: `TS_AUTHKEY`
(`deploy/install.sh:275-276,577-604`; non-reusable key recommended since it
lingers in the file), `NOVA_PUBLIC_GATE_TOKEN` (opt-in,
`deploy/.env.example:14-20`).

Stored **in postgres**, not in `.env` — these are the ones a plain "tar
`.env`" backup would miss entirely:
- `core_signing_key.private_key_hex` (`nova_core` db) — the ed25519 key core
  signs device envelopes with. Exactly one row, `id smallint PRIMARY KEY
  CHECK (id = 1)`, generated once per install and never rotated in place
  (`services/core/migrations/011_devices.sql:13-23`).
- `providers.api_key` (`nova_gateway` db) — every cloud provider's API key
  and every linked engine's bearer token
  (`services/gateway/migrations/003_providers.sql:22`); a non-builtin
  `adapter='ollama'` row is constrained to always carry one
  (`providers_engine_link_has_token`,
  `services/gateway/migrations/009_engines.sql:144-148`).

Not yet present: `network_credentials` (the tailnet credential table) — grep
across `services/*/migrations/*.sql` finds no such table. It arrives with
S43a (`rulings.md:61-62`); it does not exist today, so nothing carries it
yet either way.

### 1.5 The subnet decision (172.18 is pinned)

**Not decided by install.sh at all today.** The subnet is a hardcoded
constant in the compose file, not a runtime decision:
`deploy/docker-compose.yml:332-334`:
```
subnet: 172.18.0.0/16
ip_range: 172.18.0.0/17
gateway: 172.18.0.1
```
The comment at `deploy/docker-compose.yml:316-320` says why: it matches "the
network the live instance already has," dynamic allocation confined to the
lower half (`ip_range` /17), fixed addresses (`NOVA_WEB_ADDR`,
`NOVA_TAILSCALE_ADDR`) in the upper half where the allocator never reaches.
Changing IPAM on an existing network is not applied in place — a one-time
`down && up -d` is required, and a foreign container attached to the network
blocks the recreate (`deploy/docker-compose.yml:322-328`, restated in
`deploy/README.md:233-238`).

This is a documented collision on the S41 migration target: 172.18/16 is
already `docker_default` on the mini PC (`map-requirements.md:96`,
`hub-p0-measurements.md:50` table row `Docker networks`). `decide_subnet`
(requirement #12/#23) does not exist to resolve this — building it, and
threading `${NOVA_SUBNET}`/`NOVA_SUBNET_GATEWAY` through
`docker-compose.yml:332-334` so it stops being a hardcoded literal, is S41
scope, not something already done.

### 1.6 Health checks

`HEALTH_CHECKED_SERVICES="postgres core gateway memory web searxng"`
(`deploy/install.sh:33`), extended with `ollama` when the bundled engine
starts (`deploy/install.sh:850`) and `tailscale` when the tailnet profile is
on (`deploy/install.sh:610`). Each service's own `healthcheck:` block is the
underlying probe (see §2 per-service). `container_health`
(`deploy/install.sh:1018-1023`) reads `docker inspect
.State.Health.Status`; `missing` when no container id, `unknown` when
inspect fails to report health. Waited on by `wait_for_health`
(§1.1 step 7), then re-read by `unhealthy_services`
(`deploy/install.sh:1056-1064`) to decide whether to `die`.

A second, harder check runs only after every container is healthy:
`check_inference_compute` (`deploy/install.sh:746-806`). Motivation
(`deploy/install.sh:678-693`): every healthcheck is green whether the
bundled ollama landed on GPU or CPU (`ollama list` passes either way), so a
GPU-less silent success was previously indistinguishable from a real one
until a chat turn timed out (measured 2026-09-04). It polls
`docker compose logs ollama` up to `INFERENCE_COMPUTE_TIMEOUT=60`s
(`deploy/install.sh:718`) for the last `msg="inference compute"` line
(`last_inference_compute_line`, `deploy/install.sh:730-732`) and compares its
`library=` value against `EXPECTED_INFERENCE_LIBRARY`
(set in `detect_hardware`, `deploy/install.sh:832-835`, from
`inference_library_for_driver`, `deploy/install.sh:706-711`, currently mapping
only `nvidia` → `CUDA`). An unreadable log, an absent line, or a mismatch are
all refusals (`deploy/install.sh:768-806`) — never a pass.

### 1.7 Migration running

Not run by `install.sh` or `docker-compose.yml` directly. Each service
(`core`, `gateway`, `memory`) runs its own `run_migrations` at process
startup — `services/{core,gateway,memory}/app/migrations_runner.py:67-85`,
an identical copy in each service (comment,
`services/core/app/migrations_runner.py:1-6`: "edit this copy, then paste it
verbatim over the other two. Do not let the three drift."). install.sh only
waits for the resulting healthcheck to go green; it never invokes a
migration command itself. See §4 for the tracking table shape.

### 1.8 Idempotence

Stated in the script header: `"# Nova v4 installer. Idempotent: safe to
re-run."` (`deploy/install.sh:2`). Mechanisms actually making that true:
`ensure_secret` no-ops when a key is already set
(`deploy/install.sh:901-906`); `record_compose_files`/
`record_compose_profiles` compare before writing and log "already lists…"
on a no-op (`deploy/install.sh:959-961,1003-1005`); `decide_inference`
recognizes and reuses this stack's own already-running ollama rather than
refusing on a busy port from a prior run (`bundled_ollama_running`,
`deploy/install.sh:186-218`, invoked at `:268-274`); `decide_tailnet` treats
an existing `TS_AUTHKEY` or an already-logged-in state volume as "nothing to
do" (`deploy/install.sh:577-585`); `compose up -d --build` is itself
idempotent. There is no dedicated idempotence test in `install_test.sh`
beyond the "re-install: the port is busy because WE are on it" case
(`deploy/install_test.sh:94-103`) and the full-path `run_install` harness
(§5) run twice is not exercised — no test asserts a second `cmd_install` run
produces byte-identical `.env`.

### 1.9 Places the script assumes Linux

Deliberately bash-3.2, and mostly portable. One genuinely Linux-specific
read, **with an existing macOS fallback**, not a bare assumption:
`detect_ram_mb` (`deploy/install.sh:629-639`) reads `/proc/meminfo` when
readable (`:630-631`), else falls back to `sysctl -n hw.memsize`
(`:632-635`, the macOS/BSD path), else prints `0` (`:637`).

Everything else checked is either already portable or explicitly branches:
`port_holder` tries `lsof` then falls back to `ss`
(`deploy/install.sh:105-118`) — `ss` (iproute2) is Linux-only and silently
contributes nothing on a host that lacks it, but `lsof` (checked first) is
the macOS-present path, so the function degrades rather than assumes.
`detect_gpus_json`/`detect_gpu_runtime` both gate on `command -v nvidia-smi`
(`deploy/install.sh:642,671`) and print `[]`/`false` when absent — correct
on a GPU-less macOS host, not a Linux assumption. `df -Pk`
(`deploy/install.sh:93`, POSIX flags) and `mktemp` with a template
(`deploy/install.sh:882`, portable BSD/GNU form) are used throughout rather
than GNU-only flags. No `sed -i`, `readlink -f`, `stat -c`/`stat -f`,
`useradd` or `apt`/`systemctl` **call** appears — the two systemctl/apt
mentions found are inside human-facing log strings, not executed
(`deploy/install.sh:87,313`).

Net: the script does not currently *break* on macOS by construction, but it
has never been run there (§5 — CI's `installer` job is `ubuntu-latest` only,
`.github/workflows/rebuild-ci.yml:51`) and requirement #20 (`deploy/backup.sh`
+ `install.sh` "bash-3.2 portable") together with #27 (CI on `macos-15`)
imply this has not actually been verified, only written defensively.

### 2.2 Named volumes (declared, `deploy/docker-compose.yml:336-351`)

Six: `v4_pgdata`, `v4_models`, `v4_memdata`, `v4_workspace`, `v4_ollama`,

### 2.3 Which services write persistent state

`postgres` (the three databases), `core` (workspace scratch files),
`memory` (the notes), `gateway` (downloaded model files under `/models`),
`ollama` (pulled model blobs), `tailscale` (node identity/certs). `web` and
`searxng` write nothing persistent — `searxng`'s only volume is its
read-only config mount.

### 2.4 GPU overlay composition (`deploy/docker-compose.gpu.yml`, 58 lines)

Two service overrides, merged only when `docker info` reports the NVIDIA
runtime (`deploy/install.sh:829-835`):
- `ollama.deploy.resources.reservations.devices` — `driver: nvidia, count:
  all, capabilities: [gpu]` (`deploy/docker-compose.gpu.yml:24-31`).
- `gateway.deploy.resources.reservations.devices` — the identical
  reservation (`:50-57`), purely so the gateway container can run
  `nvidia-smi` for live VRAM reads (`app/devices_vram.py`, referenced in the
  comment at `:33-49`) — no CUDA workload runs in gateway itself.

Composition mechanics: `install.sh` appends `-f
"$GPU_COMPOSE_FILE"` to `COMPOSE_ARGS` (`deploy/install.sh:830`) and writes
the **absolute** path into `.env`'s `COMPOSE_FILE` (§1.2) so a later bare
`docker compose up` (no `-f`) still merges it — a bare `-f
docker-compose.yml` on the command line would silently drop the overlay,
which is exactly the incident the comment at
`deploy/docker-compose.gpu.yml:14-21` and `deploy/install.sh:929-939`
describes (2026-09-04, GPU silently lost, every healthcheck stayed green).
This is also why `check_inference_compute` (§1.6) exists as a second,
independent check.

## 4. Exhaustive persistent state

### 4.1 Named volumes (repeat of §2.2, for completeness)

`v4_pgdata`, `v4_models`, `v4_memdata`, `v4_workspace`, `v4_ollama`,
`v4_tailscale` — six, all in `deploy/docker-compose.yml:337-351`.

### 4.2 `nova_core` — tables (`services/core/migrations/*.sql`, `grep -n
"^CREATE TABLE"`)

State a restore must carry (identity, content, durable settings, audit):
`people`, `sessions`, `conversations`, `messages`, `turns`, `turn_spans`,
`settings`, `skills`, `skill_uses`, `action_classes`, `consents`,
`governance_events`, `timers`, `timer_firings`, `core_signing_key`
(**credential**, §1.4), `pairing_codes`, `devices`, `device_audit`,
`agents`, `notices`, `notice_mutes`, `attachments`, `queued_messages`
(`services/core/migrations/002_core_schema.sql:4,16,24,35,47,57,69`;
`025_skills.sql:19,66`; `004_action_classes.sql:18`; `005_consents.sql:16`;
`006_governance_events.sql:12`; `019_timers.sql:20,59`;
`011_devices.sql:19,31,40,79`; `021_agents.sql:27`; `022_proactive.sql:37`;
`032_notice_mutes.sql:14`; `034_attachments.sql:14`;
`024_queued_messages.sql:22`).

Operator-facing measurement history, not a live cache but not identity
either — `eval_runs`, `eval_suite_runs`
(`010_eval_runs.sql:16`, `016_eval_suite_runs.sql:24`): whether these belong
in the "must carry" set or can be treated as regenerable is a design
question this map does not settle — they are pure history (no live process
reads them to decide anything), so losing them loses a record, not a
capability.

### 4.3 `nova_gateway` — tables (`services/gateway/migrations/*.sql`)

State: `providers` (**credential**-bearing via `api_key`, §1.4),
`routes`, `spend_caps`, `provider_prices`, `engines` (settings columns
`lifecycle`, `serving`, `hold_s` are state; `last_ready_at`/`last_tags`/
`last_facts` are a live cache by the table's own design comment —
"a database restored onto another machine would otherwise carry a GPU it
does not have," `services/gateway/migrations/009_engines.sql:99-102`)
(`002_backend_and_probes.sql:4` — `backend_config`, **dropped** by migration
003, `003_providers.sql:94`, so it no longer exists; `003_providers.sql:12`;
`006_routes.sql:9,14`; `005_usage.sql:47,58`; `009_engines.sql:103`).

Cache / re-derivable: `engine_models` — "what `/api/show` said about each
model on each engine," keyed by digest, refreshed live
(`009_engines.sql:124-134`). `probes` — measurement rows the fit/speed logic
reads, but `compute` is explicitly never backfilled or guessed
(`009_engines.sql:38-39`) and the table's own comment says fit only reads
numbers "measured on the same compute" — a probes history restored onto a
different machine is inert for that machine's own fit decisions, though it
remains true history for the machine it was measured on.
`provider_walls` — the migration 009 comment calls this explicitly
"a transient refusal, not history" and deletes rows on rename rather than
preserving them (`009_engines.sql:22-23,61`).

Ledger (arguably state, arguably history, but never a cache — it is money):
`usage_events` (`005_usage.sql:14`) — the owner's spend record.

### 4.4 `nova_memory`

The database itself holds **no tables beyond `schema_migrations`** — stated
directly in the service's own docstring: "Postgres (nova_memory) stores
nothing here beyond Task 1's schema_migrations table... The DB seam exists
for a later slice to use, it is simply unused by S1's memory service"
(`services/memory/app/store.py:20-23`). `services/memory/migrations/001_init.sql`
(4 lines) creates only `CREATE SCHEMA IF NOT EXISTS app;` — no
`CREATE TABLE` anywhere in this service's migrations (confirmed by grep,
zero matches).

The real state is **on disk**, under `MEMORY_ROOT` (`/data/memory` in the
container, `DEFAULT_ROOT`, `services/memory/app/api.py:48,73`), which is the
`v4_memdata` volume (`deploy/docker-compose.yml:104`):
- `people/<person_id>/journals/YYYY-MM-DD.md`,
  `people/<person_id>/topics/<slug>.md` — the actual notes, one markdown
  file per journal-day or topic, YAML frontmatter + body, written atomically
  (tmp file + fsync + `os.replace`) (`services/memory/app/store.py:1-18`).
  **This is state a restore must carry.**
- `.embeddings/<model>.jsonl` — a **cache**, by the code's own comment: kept
  "beside the notes... but OUTSIDE people/, so it is not walked by
  `iter_all`... and not swept into `/export`'s tar of a person's files,"
  rebuildable from the notes at startup cost (measured: ~6.5 minutes per
  100x the owner's current corpus) but skipped entirely when the cache file
  is present (`services/memory/app/embedding.py:664-688`). Whether a backup
  carries this file is immaterial to correctness — it regenerates — but it
  sits inside `v4_memdata`, so a volume-level tar (as opposed to a
