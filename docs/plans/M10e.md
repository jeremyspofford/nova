# M10e plan: the Service Manager and the supervisor driver

**Sources:** `docs/plans/M10-orchestration.md` (the orchestration ADR: Point 1, "With the K3s driver
off", "The service definition", Point 4, Hard limits, Order), merged with the owner's decisions.
The owner's words: `docs/builder-packet/INPUT-2026-10-31-SERVICE-ORCHESTRATION.md` and
`INPUT-2026-10-31-ORCHESTRATION-DECISIONS.md`. ADR-1, ADR-4, ADR-9. NOVA-SPEC §6 (tiers: 0 silent,
1 act and report with undo, 2 ask first, 3 explicit confirmation every time). OPERATING-RULES.

## What is built

Nova gets a **Service Manager**: one place that knows which services Nova runs, at which version,
and how healthy each one is. It talks to services through a **driver**. M10e builds the default
driver, the **supervisor driver**: services run as plain programs under the supervisor, with no
Kubernetes anywhere.

- **The definition format** (`src/core/services/definition.ts`): one JSON file per service and
  version, the ADR's format. It is validated in plain words. Both drivers will read the same file;
  the K3s driver (M10j) is not built, and nothing here renders Helm values.
- **The `ServiceDriver` interface** (`src/core/services/driver.ts`): `available`, `plan`, `apply`,
  `status`, `switch`, `rollback`, as the ADR names them. A third driver needs no caller changes.
- **The Service Manager** (`src/core/services/manager.ts`): validates a definition, picks the driver
  (the supervisor unless a definition can only run elsewhere), and moves a version through the
  stages in order: started alongside (tier 1), its contract tests and health, then promotion
  (tier 2, or 3 for the console and anything with secrets or OS permissions), soak, and rollback.
- **The supervisor driver** (`src/supervisor/services.ts`) generalises the supervisor from one child
  to many. The console is one service among them, `nova-console`, whose artifact is the git tag it
  already used; its deploy path is unchanged. Every other service is a plain program the
  supervisor keeps running with the console's own rules: restarts that back off, held after three
  crashes in a minute, health polled, a restart after failed health.
- **The console's definition** (`src/core/services/console.ts`): the supervisor starts the console
  from it (its command, its health path and how often it is checked).
- **The no-Kubernetes tripwire** (`scripts/tripwire.sh`): `npm test`, the UI gate (in CI and in
  `scripts/ui-test.sh`) run with stand-in `kubectl`, `helm`, `flux` and `k3s` first on `PATH`. Any
  call is recorded and fails the run. `KUBECONFIG` is unset. The run's log says the tripwire was
  armed, and at the end that it never fired.

## Built on what exists (one Nova)

| Tiers | NOVA-SPEC §6, the supervisor's typed confirmation for tier 3 | The ADR's table: alongside is tier 1, promotion tier 2 or 3, a rollback asked for tier 2 |

Not reused, on evidence:
- **The change pipeline** (`changes/`) to deploy services. Its sandbox is a copy of Nova and its
  canary watches Nova's own probes. A service's alongside start, contract tests, switch, soak and
  rollback are the supervisor's, as they are for the console's releases (ADR-9 through the
  supervisor, as M7b built it).

## The stages for a service, on the supervisor driver

| Stage (ADR Point 4) | Supervisor driver | Tier |
|---|---|---|
| sandbox | the new version's slot is installed (a regular file, at most 256 MB, read without blocking, SHA-256 checked) and started alongside: `full` on its own loopback ports; `shadow` the same on a scratch copy of its state; `copy` on a copy of its state; `none` not started until the switch. Deploying a command no approved version has run (the first, or a changed one) asks first, showing the exact argv | 1, or 2/3 for a new command |
| tests | its `contract_tests` against its own port. A version that fails them is never offered | 1 |
| health | its health check, passing three times in a row | 1 |
| approval | `service promote <service> --confirm <service>@<version>`, typed | 2, or 3 |
| canary | the stable port is pointed at the new version, then a watch window of health probes. Until then the live version's stable ports are untouched; any failure, at any stage, puts them back and says what is true (if the old version doesn't start again, the service is held, with a problem) | 1 for the automatic rollback |
| promote | the old version is stopped and its slot kept for `soak_s`. Failed health or a crash loop during the soak rolls back in one step: the kept slot starts again, no download | 1 |
| after the soak | the old slot is removed, and the record says so | 0 |

A rollback the person asks for (`service rollback <service> --confirm rollback`) is tier 2. A held
service is started again with `service recover <service>`: tier 1, as it starts the same approved
version and nothing new (the console's own `recover` takes no confirmation either).

Every change to a service (deploy, switch, rollback, recover), every restart after a crash or failed
health, and the end of a soak wait their turn in one queue per service: none is refused, dropped or
run under another. A crash is counted the moment it happens, even during a change. Restarts for
failed health count toward holding, as crashes do.

## What runs: the command rule

In the ADR's terms (Point 6: "the command a workload starts with is part of its signed manifest,
never an argument to a verb"), what the supervisor driver runs is the pinned artifact and nothing
else:
- a program's command starts the artifact itself (`<name> …` or `./<name> …`, `<name>` being the
  last segment of its url), or Nova's own Node with the artifact as its script (`node <name> …`);
  the words after it are the program's own arguments;
- never another program on PATH, an absolute or `../` path, a shell, or an interpreter option or
  inline code (`-e`, `--eval`, `--input-type`, `--require`, `--import`) before the artifact;
- checked by the validator, by the driver's plan (whoever hands it a definition), and again at every
  start: the file run is a regular file inside the version's slot, links resolved, with the pinned
  SHA-256. The program lives in the slot's `bin/`, apart from its `definition.json`;
- the plan shows the exact argv, and deploying a command no approved version of the service has run
  asks first, typed (tier 2, or 3 for anything with secrets or OS permissions).

The stable port is a TCP forwarder on `127.0.0.1` owned by the supervisor, pointed at whichever
version is live. A service binds `127.0.0.1` on the ports the driver gives it (`PORT`, and
`NOVA_PORT_<NAME>` for each named port).

## The definition and its chart mapping

The format, its validation and the mapping to the `nova-service` chart's values are the ADR's ("The
service definition"). The mapping is documented there and in `src/core/services/definition.ts`,
and nothing renders it until M10j. Two additions, both needed by the code as it is:
- **`artifact.release`** `{ tag, command }`: the console's artifact is a git tag of Nova's own
  repository, which neither `image` nor `program` describes. Only `nova-console` may use it.
- **`contract_tests`** are `http:<path>` (a GET that must answer 2xx on the new version's port), or
  the console's own `release-tests` and `smoke`. The ADR's `probe:<name>` has no probe registry yet
  and is refused by name.

The validator refuses, in plain words, the ADR's four cases (a floating service with state; an
image-only service pinned to a macOS or Windows device; a placement no device's roles allow; a
secret written as a value) and every malformed field.

## What the supervisor driver refuses in M10e, saying why

- An **image-only** service: running containers for services is not built (the ADR's Docker rule
  for the supervisor driver needs image pulls the hard limits don't allow).
- A service with **secrets**: handing vault secrets to a plain program is not built.
- A placement that isn't **this hub**: other devices are M10f (roles, the resolver) and M10h (native
  workloads).
- An artifact `url` that isn't `file:`: downloading programs is M10h's signed-artifact path.
- `resources.memory_mb` larger than this machine's memory.
- A port below 1024 (the validator), or one Nova uses itself: the console's configured port, the port
  it answers on now, and the device door's, from Nova's configuration (so a port the console frees
  for a moment while it restarts is still refused).
- A program that isn't a regular file (a link, a pipe, a device) or is larger than 256 MB.

## Gate

The ADR's gates for what M10e builds (Point 1; "With the K3s driver off"; "The service definition";
Point 4 on the supervisor driver):
1. The console runs from its definition, through the supervisor driver, with today's restart,
   safe-mode and canary tests unchanged and green.
2. A second, plain-program service (a stand-in) is deployed alongside, promoted, soaked and rolled
   back: a failed contract test is never offered; failed health in the canary rolls back by
   itself; a failure during the soak rolls back in one step with no new install.
3. The driver interface is exercised by a shared contract test that the supervisor driver passes
   (and the K3s driver must pass in M10j).
4. A validator test for each refusal; a snapshot test of the supervisor's plan for one definition.
5. The whole suite and the UI gate run in CI with the tripwire armed, and its log shows it never
   fired. The tripwire's own test shows it fires.
6. Every test service binds 127.0.0.1 on a free port and is stopped in teardown, its process group
   included; a test checks that none is left behind.
7. The fresh-user test passes.
8. The review of PR #247: one test per finding (`tests/supervisor/services-review.test.ts`, the S5
   and SIGHUP cases in `services-cli.test.ts`), each seen failing with its fix reverted.

## Not in M10e

**The `service` change kind is deferred.** The ADR's Order lists it in M10e, but its artifact is the
definition plus the rendered Helm values and its gate is GitOps (`services.git`, M10j/M10k); this
phase's brief excluded Helm. In M10e a service is deployed through the supervisor with typed
confirmations, as console releases are.

The `service` change kind and `services.git` (its artifact is the definition plus rendered Helm
values, and its gate is GitOps: M10j/M10k); device roles and the resolver (M10f); hub promotion
(M10g); native workloads on devices (M10h); the map and Settings › Services (M10i); the K3s driver,
chart and fakes (M10j); GitOps and switching drivers (M10k).
