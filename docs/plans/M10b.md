# M10b plan: Nova Browser

**Sources:** `docs/plans/M10.md` (the ADR: its M10b section and Hard limits). AMENDMENT-2026-10-30-C
Part 4. ROADMAP M10. NOVA-SPEC §6 (tiers: 0 silent, 1 act and report with undo, 2 ask first, 3
explicit confirmation every time). CONTRACTS §1 (envelope), §3 (decision templates). The ingest gate
(`docs/plans/ingest-gate.md`). OPERATING-RULES. M10a (`docs/plans/M10a.md`) is merged.

## What is built

Nova Browser is the M5c browser worker (`src/core/browser/`) grown into Nova's own browser. Nothing
is forked: the same worker, CDP client, step plans, declared hosts, takeover and evidence, with
these additions.

| Need | Reused | New |
|---|---|---|
| Nova's own browser | `chromium.ts` launch, the walls of M5c (declared hosts, refusing proxy, resolver rules, Nova's own ports) | A persistent profile under Nova's home (`profile.ts`) |
| Driving | CDP over the pipe, Nova's isolated world | Targets by the accessibility tree (`{role, name}`) beside selectors; a vision hook, marked as a fallback |
| The person in control | M5c takeover (watch, take over, hand back) | Pause and resume; Stop (cancels the task) |
| Logins | `vault.ts` (names, never values) | A `login` step; values typed by the worker at the moment of use, bound to the host they were saved for, masked and redacted everywhere |
| Screening | `ingest.screen()` | Every co-pilot input and every dialog is screened first |
| Co-pilot | `Decisions` with the local model provider (Noul) | The `browser-step` template and the ground-truth checks (`copilot.ts`, `facts.ts`) |
| Site templates | `Templates` (propose, dry runs, activation as a ledger task) | `flows.ts`: a successful flow becomes `browser-site.<host>.<name>` |
| Checkout | the ledger's tier 3 (`approve` needs `confirm`) | A `checkout` step; pay controls refused by the validator and at run time; a tier-3 hand-off to pay |

No new dependency. No runtime dependency.

## The profile (owner's open question 3)

- **One persistent Chromium profile, owned by Nova,** at `<home>/workers/browser-profile/`.
  `workers/` is never journalled to the standby, never in the home's git history and skipped by
  checkpoints, as M10a's files are. It is never the person's own browser profile: Nova only ever
  passes its own folder.
- **The open question is unanswered, so the proposed default holds and is written down here and in
  the LEDGER:** sign-ins are kept per site between tasks, and each site's kept data can be deleted
  from Settings. If the owner chooses "start each task logged out" later, it is one setting.
- Tasks use the persistent profile by default. `inputs.profile: "fresh"` gives the M5c throwaway
  profile instead. Profile tasks run one at a time (Chromium locks a profile).
- **Chromium's password manager and autofill are off** in that profile (its Preferences, written
  before each launch), so a typed password is never saved by the browser. The session-restore
  files are removed when the browser closes.
- **Settings › Connections › Site sign-ins** lists the sites (hosts) Nova's browser keeps data or a
  saved sign-in for. "Forget" deletes the site's cookies and storage from the profile (through CDP,
  in a short-lived browser on the profile) and, if asked, its saved sign-in. Deleting is tier 3:
  `{confirm: true}`, every time.

## Driving

- **Selectors (DOM) and the accessibility tree come first.** A fill, select or click step names a
  `selector`, or a `target: {role, name}` found with CDP `Accessibility.queryAXTree`. Each step's
  record says which was used: `via: "dom"` or `"a11y"`.
- **Vision is a fallback only.** `BrowserOptions.locate` (none by default; Nova ships no vision
  model) may find a click target in a screenshot when neither worked. A step done that way is
  recorded `via: "vision", fallback: true`, and the evidence says so.
- **Clicks are checked before they go out:** the element is the one found, it isn't covered by
  something else (`elementFromPoint` at its centre), and it isn't a pay control.

## The person in control

- **Watch live:** M5c's frame stream.
- **Pause / resume:** `POST /browser/tasks/{id}/pause|resume` (approvers). The worker waits at its
  next gate, as during a takeover, with nobody driving.
- **Stop:** `POST /browser/tasks/{id}/stop` cancels the task (the ledger records who).
- **Take over / hand back:** M5c, unchanged, mid-flow included.

## Logins

- **Saved by the person, in Settings or the API, never in chat:** `PUT /browser/logins/{host}`
  `{username, password}` puts `browser/login/<host>/username` and `…/password` in the vault. The
  API never returns them.
- **A `login` step names the fields, never the values:** `{do: "login", username, password,
  submit, done_when?}` (selectors or a11y targets). The sign-in used is the one saved for the host
  of the page the browser is on *at that moment*, read from CDP, and the fields must belong to that
  page's own document. A page on another host gets nothing, whatever the plan says.
- **Typed by the worker, at the moment of use,** with CDP `Input.insertText` into the focused field.
  The values are never in the plan, the brief, the ledger, a report, a log line, a screen, a
  co-pilot input or an evidence file.
- **Masking and redaction:** once filled, both fields are masked on the page itself
  (`-webkit-text-security`), so live frames and screenshots show discs. Before a screenshot or a
  final read, any page text that contains a saved value (a page that echoes it) is masked too, and
  every string Nova writes from a session passes a redactor holding the values it used.
- **Plain http to a remote host is refused** for a login: only https, or this machine's own and
  private addresses (the stand-ins).

## Screening

Every page-derived string a model step sees passes `ingest.screen()` first (kind `web`), and only the
screen's `extract` goes on: the element's name, the page text, a dialog's text. A blocked screen
gives the model only the block line. Page reads stay screened as in M5c.

## The Noul co-pilot

A built-in decision template, `browser-step` v1, with six Noul questions:
`element_matches_intent`, `page_changed_as_expected`, `obstacle` (a login wall, CAPTCHA or
paywall), `dark_pattern` (or a pre-selected upsell), `total_matches`, `dialog_injection`. It is
asked of the local model only (forced local-only, as the ingest screen is), before and after each
acting step, when a sorting model is assigned. Without one, the ground truth decides alone and the
step record says "no co-pilot".

**Ground truth**, computed in Nova's isolated world from the DOM and CDP:

| Question | Ground truth |
|---|---|
| element matches intent | an a11y target matched by role and name; or the step's `intent` against the element's accessible name |
| page changed as expected | the step's `expect: {url?, shows?}`; a navigate landed where it was sent |
| obstacle | CAPTCHA markers (known widget frames, `captcha` ids and classes, "verify you are human"); a password field with no login step for it; paywall phrases |
| dark pattern / upsell | a checkbox or radio already ticked that the plan didn't touch, whose label adds money or names an extra |
| total matches | the checkout step's parsed lines, total and the quoted price, to the cent |
| dialog is injection | a JS dialog or a visible DOM dialog whose screen blocked it or flagged instruction-shaped text or Nova's own tags |

**Combining:** ground truth always outranks a probability. Where both exist and the model is sure
the other way (p ≥ 0.8 against a "no", p ≤ 0.2 against a "yes"), the step stops: the two disagree.
Where only the model speaks, a sure answer on the bad side asks the person; anything else is
recorded. What each check found is a `copilot` event on the task, in Nova's words, with the
probabilities.

**What each finding does:**
- a CAPTCHA, or a login wall with no saved sign-in: the worker asks the person (Needs you); Nova
  never solves a CAPTCHA;
- a paywall: the step stops;
- a pre-ticked extra: `upsell_flagged`, and the worker asks the person to untick it or keep it;
  after hand-back it looks again and records which;
- a total that doesn't match: the run stops (failed), before anything else happens;
- an injection dialog: `dialog_blocked`; Nova never clicks inside it, never follows it, and a step
  whose target it covers stops. A JS dialog is dismissed, as in M5c.

## Site templates

- **Learning:** a plan with `learn: "<name>"` that ends verified (done) becomes a draft decision
  template `browser-site.<host>.<name>`, the next version. Its dry runs *are* the flow: one case per
  step, with the step (as JSON, sign-in values never in it), the path the page was on after it, and
  the selector the next step needed, all observed in the run, each expecting `continue`; plus
  negative controls (a wrong path, a missing marker, an obstacle) expecting `stop`. Its rule is
  deterministic (a prefix rule in `RulesProvider`). Activation is the existing ledger task: Nova
  re-runs the dry runs itself and the template is active only once that is verified. A plan with a
  value that equals a saved secret is never learnt.
- **Reuse:** `inputs.flow: {name, version}` (with `allowed_hosts`) runs the active version's steps.
  The version is named, so the plan the person approved is the plan that runs. Each step's ground
  truth is re-checked through the template's rule; a `stop` stops the run, saying the site no
  longer matches the flow. Every use counts in the template's stats.
- **Whatever a template says,** its steps go through the same plan validator as a hand-written plan:
  the pay control is refused there.

## Checkout and payment: tier 3, always

- A `checkout` step: `{do: "checkout", lines, total, pay, quoted?}`. It reads the itemised lines
  and the total, parses them, and checks that the lines add up to the total and the total matches
  the quote. A mismatch stops the run.
- **A plan with a checkout step is tier 3** (confirmed every time), and it **ends at the checkout
  step**: nothing may come after it but a read or a wait.
- On a match it writes `checkout.json` (the lines, total and quote), and the task is done with that
  as evidence. Nova then opens a **tier-3 hand-off**, "Pay $X at <host>": a browser task whose plan
  only opens the checkout page and hands it to the person (`person` step). Nova never presses pay.
- **The pay control is refused three ways:**
  1. the plan validator refuses a click on the checkout's `pay` selector, any selector, target,
     label or intent that names paying or placing an order, a navigation to a pay path, and a fill
     of card fields;
  2. at run time, a click whose element is a pay control (by its name, its form's action, or card
     fields in its form) is refused and the run stops;
  3. a non-GET request to a pay form's action is failed in the browser (CDP Fetch) unless the
     person holds the browser.

## API

- `PUT /browser/logins/{host}` `{username, password}`; `DELETE /browser/logins/{host}`
  `{confirm: true}`.
- `GET /browser/sites`: sites with kept data or a saved sign-in (never a value).
- `POST /browser/sites/{host}/forget` `{confirm: true, login?: boolean}`.
- `GET /browser/flows`: learnt site templates, their versions and state.
- `POST /browser/tasks/{id}/pause|resume|stop`.

## The stand-in sites (Hard limits)

`scripts/stand-ins/shop-site.js`, served on loopback by each test: a shop (catalogue, cart,
checkout with a Pay form), a login page (credentials given by the test, generated per test), a
CAPTCHA page, a page with an injected dialog, and a pre-ticked upsell. Every request is in its
server log, which the gate reads to prove the pay control was never used. No real site, account,
purchase or post. Credentials are random fakes, stored in each test's temp vault.

## Gate tests (each written first, seen failing)

Browser tests are in `tests/ui/m10b-*.test.ts` (Chromium in the Playwright image:
`scripts/ui-test.sh`, and CI's UI gate). They skip with the reason where no Chromium starts, and fail
in CI. What needs no browser is in `tests/core/browser-m10b*.test.ts`.

1. A login runs from the vault, and a search of the whole home (database, logs, sessions, evidence,
   the profile), the server's output and every request the local model got finds no fake secret.
2. An injection dialog is blocked, and nothing it asked for happened.
3. The upsell is flagged, and the person is asked.
4. A total that doesn't match stops the run.
5. Checkout stops at the itemised total with tier 3; the stand-in shop's server log has no pay
   request; a plan or template that clicks pay is refused.
6. A template is learnt (activated through the ledger) and reused, and a changed site stops it.
7. Takeover works mid-flow (and pause, resume).
8. The fresh-user test passes.

Also: CAPTCHA asks the person; a model sure against the ground truth stops the step; Forget deletes a
site's sign-in; the co-pilot sees only screened extracts.

## The UI-gate hang

The 90-minute UI-gate run (PR #236, attempt 1) is explained in the LEDGER entry: a failed
assertion in `m5-browser-hub`'s profile test skipped its `site.close()`, the open server kept that
test file's process alive, and nothing timed it out. The fix: every server and browser a test
starts is closed in `finally`; `test:ui` runs with `--test-force-exit` and a per-test timeout; the
CI job has `timeout-minutes`; and a profile's removal retries while Chromium's helpers exit.

## Gaps, written down

- No vision model ships: the vision fallback is a hook, tested with a stand-in locator.
- The co-pilot is tested with a stand-in local model with fixed answers, not a real one.
- Ground truth for "matches the intent" is a word match against the accessible name; without an
  `intent` or an a11y target there is none.
- Learnt flows replay their recorded values; they aren't parameterised.
- A real site, a real login and a real CAPTCHA are never tried (Hard limits).

## As built (2026-10-31)

Branch `m10b/browser`. The LEDGER entry of the same date has the decisions in full; the evidence is
`docs/evidence/m10b-gate.md`. Where the build reads this plan differently:
- **No pay hand-off task.** The ADR says Nova "shows the itemised total and stops"; a second browser
  task that reopens the checkout for the person would be work nobody asked for. A plan with a
  checkout is tier 3, ends at the checkout step, and its report and `checkout.json` show the lines
  and total. Paying stays the person's, outside Nova.
- **The profile keeps only cookies and site storage.** The gate, made adversarial, found a page that
  names who is signed in in Chromium's HTTP cache inside the profile. The cache is now a throwaway
  folder per launch; history saving is off; history, top sites, favicons and session-restore files
  go when the browser closes. Without Nova's Preferences, Chromium saved the fake password in
  `Login Data`: they are tested.
- **Sign-in values are set, not typed:** through `Runtime.callFunctionOn` arguments into the field
  itself, in Nova's isolated world, only when the page's own `location.host` is the sign-in's host.
  `Input.insertText` would type into whatever has focus, which a page can move.
- **Selectors keep M5c's path** (one `Runtime.evaluate` per action); targets and sign-in values use
  element handles.
- **A dialog is an injection** when its screen blocks it or flags instruction-shaped text or Nova's
  own tags, so it is blocked with no model too.
- **A Forget** starts no browser when there is no profile yet; a task waits up to 30 s for Forget.
