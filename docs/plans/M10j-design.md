# M10j implementation design: optional K3s driver

This implements the already owner-approved orchestration ADR, not a new product decision. Binding sources are `docs/plans/M10-orchestration.md` (Points1–5,7–8 and phase M10j), the vault-broker ordering in `docs/plans/vault-broker.md`, and the packet operating rules. M10i merged as #280 at `f831cf3a`; its exact tested tree is the baseline. The standing order authorizes continued execution without another plan-confirmation pause. A genuinely new rendered component still requires its existing design-first owner gate. #275 remains parked until findings B; no code or merge on that PR is authorized by this document.

## Outcome and boundary

M10j adds the optional container driver, the repository's one `charts/nova-service` chart, test-only kubectl/helm/flux fakes and simulated cluster, truthful cluster observations, control-plane loss behavior, and a per-cluster credential boundary. Native programs continue through the supervisor/device drivers, never pods. Default Nova remains fully functional without Kubernetes or configured clusters. M10k owns backend switching/onboarding, services.git/Flux ownership, cold-second-site activation and the existing deferred service change-kind/GitOps integration.

Full M10j completion requires its credential gate. The broker's P1a/P1b/P1c sequence precedes new kubeconfigs/deploy keys; P1a #275 is still owner-gated and not merged. Chart/simulation/driver/ledger work can proceed against a narrow injected tool-launch port. Production credentialed operations remain unavailable without the eventual reviewed broker adapter. No legacy vault.ts fallback, copied broker implementation, raw credential in core, or fake production credential mode is allowed. A green uncredentialed checkpoint is not a passed full phase gate.

## Components and builder choices

1. **Pure values and chart.** A renderer consumes validated service definitions for one service plus explicit live/kept versions, replicas and resolved placement context. Its output is closed JSON values: service identity/ports, current live selector and per-version image repository/digest, probes, placement/roles/resources, state-volume references and replica counts. The chart manages one Deployment/preview Service per retained version and the stable Service selecting only the live version. Names/selector tokens must remain valid and collision-resistant for every service/version the existing validator accepts; untrusted labels never become YAML/template directives. Raw credential values are never values, annotations or manifests. Unsupported safe execution/storage semantics are refused, not guessed. The first task can implement and snapshot this independently of credentials.
2. **Tool boundary and simulation.** Driver code emits a fixed, bounded set of namespace-scoped argv/JSON operations through an internal `ClusterTools` port. No public arbitrary tool/argv/manifest bridge. Test implementations start only the committed fake programs in disposable homes. The fake cluster keeps nodes, pods, stable selectors, volume/state references, readiness and control-plane reachability in a state file; a loopback fixture exposes the selected synthetic version so the existing shared driver contract observes actual routing. Fakes validate commands and chart/schema inputs independently; they are not evidence that real Helm/K3s accepted or ran the chart. Default production has no runner and never invokes a Kubernetes tool.
3. **K3s driver.** Implement the existing six-call ServiceDriver and its expected-state contract. Status is cached observation state; async refresh preserves actual observation time. One serialized mutation lane per cluster/service checks expected live/previous immediately before effects. Apply has no production traffic; only genuinely ready candidates promote. Contract failure, canary failure and soak failure retain/restore the prior version without rebuild/download. Health/readiness is not inferred from a desired manifest or accepted acknowledgement. Existing definition/placement/role/Linux checks remain authoritative. Stateful copy, shadow and singleton modes may not share a writer or be called ready without their required proof: the plan must identify supported safe semantics and refuse the rest explicitly, rather than weakening the ADR health gate.
4. **Queued operations and core integration.** Use actual WorkLedger internal workers/tasks for operations waiting on the control plane, not another durable operation registry. Fixed cluster routes create the appropriate approval tier and preserve the approved target; arbitrary API/device task creation cannot forge the internal worker. Before effects, an unavailable control plane reports blocked/not-started under the ledger's existing dispatch rules. Reconnect retries only a still-approved unchanged target; a possibly committed effect is reconciled from evidence, never blindly repeated. Existing ServiceManager definitions/tiers remain the authority while the already-deferred change-kind/GitOps work remains M10k. Changes record definition/values evidence and truthful task outcomes.
5. **Observations and network guard.** Connect actual configured cluster observations to M10i's trusted seam. Stable device IDs join node reports with device heartbeats; explicit cloud sites alone create cloud-site nodes. Retain both reasons/times, use the worse signal and preserve independent service failure provenance. Lost control-plane access makes cluster data last-known/unknown, not an invented service outage; heartbeats continue. No rescheduling during loss. Network-changing cluster operations delegate to M10d's existing snapshot/diff/tier3/dead-man authority, through an explicitly bound target; service-selector promotion retains the ADR service tier. No raw network command or new network authority. A real loopback stand-in must lose acknowledgement and prove snapshot restoration through the existing module.
6. **Broker-backed credentials.** The eventual adapter takes only cluster ID/ref and fixed operation metadata. Kubeconfig value, materialization, program digest check, redaction, cancellation cleanup and file permissions belong inside broker/launcher authority. Core cannot read a kubeconfig in order to sanitize it. Each tool gets only its cluster's one-call credential; ambient config/home/proxy/plugin settings never supply authority. Kubeconfig exec plugins and external-file/endpoint substitution need target-side validation or equivalent containment across kubectl, Helm and Flux. The production adapter and full canary-secret gate wait for the merged broker foundation; test-port coverage must never be relabeled as that proof.

Cluster records contain only public metadata/ref names, in atomic plain files: id, name, control-plane address, home/cloud site, active/cold state, node/device association and credential/network-target references. Registering credentials, joining nodes or enabling a driver is tier3. There is no automatic discovery, installation, bootstrap, cloud activation or new Settings choice in this phase. The console remains under its existing supervisor by default.

## Proof required

- Definition/values snapshots, schema lint through the fake Helm, hostile names and chart-shape safety, each placement/refusal and no secret values in artifacts.
- The unchanged shared service-driver contract plus contract/canary/soak failure and expected-state concurrency cases.
- Simulated control-plane loss with real WorkLedger waiting/unchanged approval, continuing heartbeat health, no reschedule, stale cluster ages, recovery and ambiguity-safe cancellation/restart.
- Existing M10d dead-man module exercised against the simulated cluster network target.
- Eventually real broker/launcher integration in temporary homes: per-cluster canaries absent from core output/files/logs/ledger/transcripts/repo/state, 0600/0700 one-call file removed, wrong-cluster/binding/replay/ambient config/exec-plugin attempts refused. No owner credentials.
- Independent adversarial review, exact-head full CI, same-PR plain-language LEDGER and preview restart/verification before merge. No full phase merge until all mandatory gates are genuinely met.

## Hard limits and documentation checks

No real K3s/Helm/Flux installation or invocation, real cluster/cloud VM/spend, image/model pull, real device workload, network/tailnet/DNS/router/Serve change, owner data/keychain, clone-root mutation, old-owner worktree, #207 or #208. Use the current task-owned isolated checkout on `codex/m10j-k3s`; no extra worktree is needed. New types used outside core export through core/index.ts. No runtime dependency or external UI script.
