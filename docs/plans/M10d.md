# M10d plan: infrastructure, networking and accounts through chat

**Sources:** `docs/plans/M10.md` (the ADR: its M10d section and "Hard limits during the build").
AMENDMENT-2026-10-30-C Part 4 ("Infrastructure through chat: … plan output shown before any apply;
apply (spending, destructive) is Tier-3. Budget guardrails + alerts on anything Nova provisions. A
checkpoint is taken before every infra/network change. Networking changes (router/DNS/firewall/
Tailscale): Tier-3, with config snapshot, diff preview, and a dead-man's switch … Account management:
via connectors/OAuth and vault logins in Nova Browser. Password/MFA changes and account creation are
Tier-3 with the user present for codes. Passwords are never requested in chat and never enter model
context."). ROADMAP M10. ADR-8 (vendors are adapters), ADR-9. CONTRACTS §1. NOVA-SPEC §6 (tiers: 0
silent, 1 act and report with undo, 2 ask first, 3 explicit confirmation every time). OPERATING-RULES.

Everything here is tested against stand-ins only. No OpenTofu, provider, cloud account, router,
DNS, firewall or Tailscale setting is touched, installed or read by the build or its tests.

## What is built

Three things the chat can start, each a chain of internal Work Ledger tasks like a coding run
(M10c): every step has its own tier and evidence Nova checks itself, and the next step's task is
made only once the one before is verified done.

### 1. Infrastructure: plan → shown in full → apply

An **infrastructure project** is a folder of the person's with a plan/apply tool's configuration
(OpenTofu's `.tf` files), registered by the person (API, never chat) with a **monthly budget**, a
**price sheet** (what each resource type costs a month) and the names of its provider secrets in the
vault. A run on it:

| Step | What happens | Tier | Evidence Nova checks itself |
|---|---|---|---|
| **Plan** | `tofu init`, then `tofu plan -out=<Nova's own file>`, `tofu show -json` and `tofu show` of that saved plan. Nova prices every resource change from the price sheet and adds it to what the project's resources already cost. | 1 (automatic: it changes nothing; reading the provider is the only reach) | `confirmation` (`nova-infra`): the saved plan file is there, its sha256 is the one recorded |
| **Apply** | Only for a plan inside the budget. The person sees the plan **in full** (the tool's own text), each resource change with its price, the month's total against the budget, and confirms. Nova checks the plan file's hash and the budget again, takes a **checkpoint** (Nova's home, `checkpoints.auto`, and a copy of the tool's state file), then `tofu apply <that saved plan>`. | 3, every time (it spends, or destroys) | `confirmation` (`nova-infra`): Nova reads the tool's state back (`tofu show -json`) and finds each planned resource there (or, for a destroy, gone) |

**Budget guardrails and alerts.** Every resource Nova provisions belongs to a project with a budget,
and is recorded with its monthly price.
- A plan with a resource change Nova **can't price** (its type isn't in the price sheet) is never
  offered for apply: Nova can't keep what it can't price inside a budget.
- A plan that would take the month's total **over the budget** is never offered for apply. Nova
  **alerts**: a problem (Problems, health) and a message to the person.
- At **80 %** or more, the apply is offered, the ask says so and the person is told; once applied, the
  project's own level raises the alert (a problem and a message), once per level.
- The **apply checks the budget again** at the moment it runs (another apply may have run since).
- On the heartbeat, Nova re-prices each project's recorded resources with its current price sheet
  and alerts when one goes over (once per level, not every beat).

Destroying is the same chain with `tofu plan -destroy`, so it is tier 3 too.

### 2. Networking: snapshot → diff → apply → dead-man's switch

A **network target** is something whose configuration Nova may change (a router, DNS, a firewall, a
tailnet's policy), registered by the person with an adapter and a token in the vault. A change is a
**JSON merge patch** (RFC 7386) of the target's configuration, proposed in chat. In this order:

| Step | What happens | Tier | Evidence |
|---|---|---|---|
| **Prepare** | Nova reads the current configuration and its version: the **snapshot**, kept in Nova's own folder with its sha256. It applies the patch to it in memory and makes the **diff**. Nothing outside changes. | 1 | `confirmation` (`nova-network`): the snapshot file is there with its hash |
| **Apply** | The person sees the target, the snapshot's time and the diff, and the switch's window, and confirms. Nova reads the configuration again (it must still be the snapshot: a compare-and-swap on the version), takes a **checkpoint** of its home, writes the new configuration (with `If-Match` on the snapshot's version), reads it back, and **arms the switch**. | 3, always | `confirmation`: Nova reads the target back and finds exactly the new configuration |
| **Revert** | Made by Nova itself when the switch fires: it writes the snapshot back (with `If-Match` on the version it applied) and reads it back. | 1 (the person's tier-3 confirmation of the change included it; it puts back what was there) | `confirmation`: Nova reads the target and finds exactly the snapshot |

**The dead-man's switch.** After the apply, the hub waits for **contact with one of the person's
devices**: if none is confirmed within the window, Nova reverts to the snapshot by itself, records
it, raises a problem and tells the person. A change whose contact is confirmed is kept.

- **The window** is 5 minutes by default (the ADR's proposal; it is still the owner's open question
  2), a setting (`mesh.contact_window_s`, 60 to 3600).
- **"Contact confirmed"** is built on the device mesh as it is: a request that reaches the hub's
  **mesh listener**, authenticated with a **trusted device's session** (the access policy already
  checks this on every request, and `Devices.touch` already marks it), **started after the switch
  was armed**, from a device that was **trusted at the moment of the apply** and is a phone, a
  browser or a computer (not the hub itself, and not the standby, which is infrastructure). Any
  such request counts: a device agent's heartbeat, the PWA opening a page, its event stream
  reconnecting. `Devices` now emits `heard` for each one (before its 30-second write throttle), and
  the switch listens. A request to the console listener (the hub's own screen) never counts: it
  proves nothing about the network. An event stream opened before the change doesn't count either:
  only a new request does.
- **No device, no change:** a change can't be prepared while no such device is paired, since its
  contact could never be confirmed. The person is told to pair their phone first.
- **Restarts:** the deadline and any confirmed contact are in the database. After a restart, a
  change past its deadline with no contact reverts; one before it waits for the rest of its window.
- A revert that finds the configuration changed since Nova's apply (someone else changed it) does
  **not** overwrite it: it stops, raises a problem and tells the person.
- The person can undo a kept change: `POST /network/changes/{id}/revert` makes the same revert step
  at tier 3 (it is a network change of its own).

**Secrets in a configuration.** A router's configuration holds passwords and keys. A value under a
key that looks secret (`password`, `psk`, `secret`, `token`, `private_key`, `api_key`, …) is masked
in every view: the diff, the chat's answer, the ledger. A patch that sets one is refused: secrets
aren't changed from chat. The snapshot and the new configuration must keep the real values (the
revert writes them back), so they are **sealed** in Nova's own folder (`workers/network/<change>/`,
AES-256-GCM, 0600, not in backups, sync or checkpoints) with a key of the change's own kept in the
vault (`network/<target>/change/<change>`); both go when the change is done with. (The gate's secret
search found the first build keeping them in clear.)

### 3. Accounts: connectors, and vault sign-ins in Nova Browser

- **Connectors and OAuth**, as built in M5b: connecting a service puts its tokens in the vault from
  Settings, never from chat. M10d adds no connector.
- **Account steps in Nova Browser**, new steps in its plans:
  - `new_password`: Nova makes a new password itself (in the hub's process, never shown), types the
    saved password into the current-password field and the new one into the new and confirm
    fields, sends the form, and keeps the new password in the vault once the page shows it took.
  - `create_account`: Nova types the account name given (an email address or a user name, not a
    secret) and a new password it makes itself, sends the form, and saves both as the site's
    sign-in once the page shows it took. Not where a sign-in is already saved.
  - `code`: a code only the person has (a text message, an authenticator, an email). Nova asks for
    them and hands them the browser; they type it themselves; Nova never reads or types a code.
  - A plan that has any of these declares `account: {change: create | password | mfa, site}`;
    `mfa` needs a `code` step.
- **Tier 3, always, with the person present.** An account plan is tier 3 whatever else it holds,
  and it runs only within 10 minutes of the person's confirmation: one left waiting longer stops
  before opening a browser and asks again. Codes are typed by the person through takeover.
- **Passwords never in chat or model context.** The `account_change` tool has no place for a
  password, and the plan validator refuses a `fill` into a field that looks like a password or a
  code ("Nova never types a password or a code from a plan"); the browser refuses a `fill` into a
  password field at the moment of use too. Every value a session used (the saved sign-in, the new
  password) is masked in everything Nova writes for the task, and the outbound guard already knows
  the vault's values. The system prompt says it plainly: never ask the person for a password or a
  code in chat.
- **A change that may have gone through:** the new password is kept in the vault, aside
  (`…/password-pending`), before the form is sent. If the page then doesn't show the change took,
  the task waits for the person ("may already have happened") and the old password stays in use;
  `POST /browser/logins/{site}/pending` with `{keep: true, confirm: true}` makes the new one the
  site's password, `{keep: false, confirm: true}` drops it.

Not reused, on evidence:
- **M10a workspaces for the tool.** A workspace has no network, and a plan reads the provider. The
  tool runs on this computer, as the person would run it, with only the declared secrets.
- **The browser worker for networking.** Router pages differ by vendor; an adapter speaks to an
  interface instead (ADR-8). A vendor whose only interface is a web page would be an adapter that
  drives Nova Browser; not built.

## Adapters (ADR-8)

- **Plan/apply:** `PlanApplyTool` (`init`, `plan`, `show`, `apply`, `state`). One adapter, OpenTofu
  (`tofu` on PATH; Terraform's CLI is the same shape and would be the same adapter with another
  command). Tested only against `scripts/stand-ins/fake-tofu.js`, put on PATH in a temp folder.
- **Network targets:** `NetworkTarget` (`read` → `{config, version}`, `write(config, ifVersion)`).
  One adapter, `http-config`: a JSON configuration at an address, read with GET and its `ETag`,
  written with PUT and `If-Match`, a bearer token from the vault. That is the shape of a tailnet
  policy API and of many routers' JSON APIs, simplified. Plain http only to this machine (a token
  never crosses a network in clear). Tested only against `scripts/stand-ins/fake-netconfig.js`, a
  loopback server whose configuration is a file in a temp folder.

## API

- `GET /infra`, `POST /infra/projects`, `GET /infra/projects/{id}`,
  `PUT /infra/projects/{id}/secrets/{ENV}` (a value into the vault; never shown again),
  `POST /infra/runs` (`{project, destroy?}`), `GET /infra/runs/{id}`, `POST /infra/runs/{id}/decline`.
- `GET /network`, `POST /network/targets`, `PUT /network/targets/{id}/token`,
  `POST /network/changes` (`{target, patch, title?}`), `GET /network/changes/{id}`,
  `POST /network/changes/{id}/decline`, `POST /network/changes/{id}/revert`.
- `POST /browser/accounts` (an account plan as a browser task), `POST /browser/logins/{site}/pending`.
- Steps are approved and cancelled through `/tasks`, like every other task.

## Chat

- `infra_plan` (`{project, destroy?}`): starts a run; answers with the run and that the person is
  asked, with the plan in full, before anything is applied. `infra_status`.
- `network_change` (`{target, patch, title?}`): answers with what the diff changes (counts and keys,
  masked) and that the person confirms it in Tasks, and how the switch works. `network_status`.
- `account_change` (`{change, site, steps, verify}`): a browser plan for an account step; answers
  that the person confirms it in Tasks and must be there for any code, and that Nova never asks for
  a password in chat.
- All three are `GUARDED`: in a run that read outside content, they ask before they start.

## Test safety

Every folder is made under `mkdtemp(os.tmpdir())`. The plan/apply tool is the stand-in on a PATH a
test makes; the network target is a loopback stand-in over a file in a temp folder; account flows
run against a loopback stand-in site. No test runs `tofu`, `terraform`, `tailscale`, `iptables`,
`nft`, `ip` or `resolvectl`, or touches the running preview, its ports or any other checkout. Tokens
and passwords are made per test with `randomBytes`.

## Gaps, written down

- **Prices are the person's price sheet, not a bill.** Nova estimates from it; it reads no
  provider's billing, so spend that doesn't come from resources Nova recorded isn't seen.
- **The tool runs on this computer**, with the provider's network reach; local-only privacy refuses
  a project unless the person declares its provider local.
- **The tool works in the project's folder**, as the person would: `tofu init` writes `.terraform/`
  and its lock file there, and the state (with a local backend) is there. Only the saved plan is in
  Nova's own folder.
- **The state copy isn't a rollback.** Nova keeps the state file as it was before each apply; putting
  infrastructure back is another plan and apply.
- **Projects and targets are registered through the API**, not yet from a Settings page.
- **One network adapter**, JSON over HTTP. No vendor's own interface (a router's web page, the
  Tailscale API's HuJSON) is spoken yet; each would be an adapter.
- **Contact needs a paired device that makes a request inside the window.** A phone asleep with the
  PWA closed doesn't; the change then reverts. That is the safe failure, but it may revert a good
  change: the person can make it again with the PWA open.
- **The account steps' Settings view** for a pending password is the API only.
