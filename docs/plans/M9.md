# M9 plan: Feel & Polish

This plan covers roadmap item M9. The packet sources are:
- ROADMAP-AND-GATES M9;
- AMENDMENT-2026-10-30-C Part 2 (binding; its numbers are gates);
- DESIGN-SYSTEM §1 (the binding "Progress and waiting" rules), §2 (token-only components, `lint:tokens`) and §5 (layouts and postures);
- UX-RESEARCH-2026-10-30 §1, §2 and §7 (the pass criteria);
- OPERATING-RULES.

The gate, in the roadmap's words: Core Web Vitals at p75 on the main views at phone and desktop widths; the progress rules on every waiting state; animation tokens; contrast in every theme and state; 44 pt / 48 dp hit areas; the four foldable and responsive tests, in order; all in CI with the measurements in the PR; and the fresh-user test.

## What exists (from Part 1 and before)

- **The browser gate.** `tests/ui/*.test.ts` drive the real PWA against the real server in the Playwright image (`scripts/ui-test.sh`), Chromium and WebKit.
  - `posture-sweep.test.ts` checks 7 widths × 4 postures. Postures are emulated with the `?posture=` hook only: no hinge geometry exists anywhere.
  - `ui-fixes.test.ts` and `ui-review.test.ts` (Part 1) check timestamps at 4.5:1 in the browser, one scroller per view, and Settings in two layouts.
- **Contrast.** `LIVE_CHECKS` and `CONTRAST_PAIRS` in `src/core/design.ts` check token pairs (body text 4.5:1, outlines 3:1) in every built-in look. Nothing checks the states a control is drawn in: hover, focus, selected, disabled, error or placeholder.
- **Motion.** Six motion tokens. `lint:tokens` requires durations and easings to be tokens, but:
  - the values run 120–450 ms;
  - nothing limits what animates. Today `background-color`, `color`, `border-color`, `filter`, `text-decoration-color` and `left` animate in places, and the settings "found" mark animates a background over ~1.7 s;
  - reduced motion is honoured through the core's `REDUCED_MOTION` tokens and a base rule.
- **Waiting states.** Each part draws its own: "Loading…" text in every Settings part, "Checking…", a pulsing dot for Thinking (named only to screen readers), "Running ⟨tool⟩…", "Running now…", a real byte bar for model downloads (no estimate), "Exporting…".
  - Home and Tasks draw before their data arrives ("Nothing needs you", "No tasks yet"), then redraw: a layout shift, and an empty state that isn't true.
  - Memory, Skills and Activity draw nothing until their data arrives.
  - Nothing follows the 1 s / 10 s bands.
- **Hit areas.** Icon buttons are 40 px in Orb Teal; small buttons 32 px; the chat's Copy and Regenerate are smaller still. The top LEDGER entry carried 44 pt / 48 dp to M9.
- **Layouts.**
  - The right column starts at 1280 px, so 1024–1279 px is a single column with empty sides.
  - The conversation column is 720 px (about 80ch).
  - Text sizes are px tokens, so a person's larger text setting changes nothing.
  - Nothing keeps the reader's place across a resize, fold or unfold.
  - A real hinge can be emulated in the Docker Chromium (`Emulation.setDeviceMetricsOverride` with a `displayFeature`): that gives real `horizontal-viewport-segments` / `vertical-viewport-segments` media and `env(viewport-segment-*)` values. Checked on this machine.

## How each gate item is measured in CI

Every item is a test that runs in `npm run check` (unit, lint) or in `scripts/ui-test.sh` (browser). Main views: **Home, Chat, Tasks, Settings, Memory**. Widths: **phone 390×844** (touch, mobile) and **desktop 1280×820**. The foldable tests add the postures and widths named below.

1. **Core Web Vitals at p75** (`tests/ui/m9-vitals.test.ts`).
   - A seeded profile (a long conversation, tasks in every state, memories) on the real server.
   - Each run is a fresh page in a new browser context. Per view × width there are **12 runs**, and p75 is the nearest-rank 75th percentile (the 9th of 12).
   - An init script installs `PerformanceObserver`s with `buffered: true`:
     - `largest-contentful-paint`: the last entry before the first input;
     - `layout-shift`: entries with `hadRecentInput` set (within 500 ms of input) are dropped; CLS is the largest session window (1 s gap, 5 s cap), as web-vitals computes it;
     - `event` with `durationThreshold: 16`: INP is the longest interaction, grouped by `interactionId` (fewer than 50 interactions, so no outlier is dropped).
   - Real interactions per view, driven through Playwright's input (trusted events):
     - typing into the composer and the search box;
     - opening and closing a task;
     - opening a Settings category;
     - opening a memory to edit and leaving it;
     - a tap on a navigation item, so the next view's render counts too.
   - Asserts CLS ≤ 0.1, INP ≤ 200 ms and LCP ≤ 2500 ms at p75. The table of numbers is printed and copied into the evidence.
   - **Skeletons** (`tests/ui/m9-skeleton.test.ts`): the API is held with `page.route`. The test checks:
     - nothing shows before 1 s;
     - the skeleton shows by 2 s;
     - every skeleton block's rect equals the final block's rect (±0.5 px);
     - no layout shift is recorded across the swap.
2. **Progress rules.**
   - `ui/js/wait.js` is the one place the bands live. It holds pure functions, unit-tested in `tests/m9-wait.test.js`:
     - the band for an elapsed time;
     - real-unit progress, with no percentage without a total and never 100% before done;
     - a general estimate only from a measured basis ("about a minute"), never a countdown;
     - no stall at 99%.
   - A static test checks the code:
     - every timer in `ui/js` is listed with its reason (poll, debounce, expiry, long press), and none delays a result;
     - every waiting state uses `wait.js`;
     - nothing replays text.
   - The browser test (`tests/ui/m9-progress.test.ts`) uses `page.clock` and held routes:
     - a view's load, chat Thinking and a running step: nothing under 1 s, an indicator from 1 s, real units and an estimate after 10 s;
     - a finished answer appears whole;
     - streamed text arrives only as real deltas;
     - a failed send puts the words back with the reason;
     - a memory edit says "Saved" only after the server does, and a failed one keeps the person's text.
3. **Animation.**
   - Token validation (`src/core/design.ts`, unit-tested):
     - transitions and finite animations are 150–300 ms;
     - easing curves don't overshoot (y in [0, 1]);
     - the two loop tokens (breathe, pulse) are state loops, exempt from the 150–300 range but stopped under reduced motion.
   - `lint:tokens` gains three rules:
     - a transition or keyframe may change only `transform`, `translate`, `scale`, `rotate` and `opacity` (`visibility` only as an instant step);
     - finite durations come from the transition and duration tokens only;
     - finite keyframes are monotonic (no bounce).
   - The browser test (`tests/ui/m9-motion.test.ts`) drives real actions on every main view at both widths and reads `document.getAnimations()`:
     - every finite animation is 150–300 ms and changes only those properties;
     - under `prefers-reduced-motion` no loop runs and every transition is ≤ 1 ms.
4. **Contrast** (`tests/ui/m9-contrast.test.ts`). This builds on Part 1's in-page measure (the nearest painted background, the page gradient's two ends).
   - Coverage: all six built-ins, in every look they have (light and dark where a package has modes) × the main views.
   - Text is measured in each state, at 4.5:1, or 3:1 for large text (24 px, or 18.66 px bold):
     - at rest;
     - on hover (a pointer over each kind of control);
     - focus-visible (keyboard focus; the ring is held to 3:1 against what is next to it);
     - selected (`aria-current`, `aria-pressed`, `aria-selected`, checked);
     - disabled;
     - error and warning;
     - placeholder (`::placeholder`).
   - Icons in buttons, including disabled ones, are held to 3:1.
   - The token-level checks stay as they are; this adds the drawn states.
5. **Hit areas** (`tests/ui/m9-targets.test.ts`).
   - At phone width, every visible interactive control on each main view is checked, and in the open states: the drawer, More, a Settings category, the sheet, the composer with text.
   - The check uses `document.elementFromPoint` over a 5×5 grid in a 44×44 box centred on the control (clamped inside the viewport). Every point must hit the control, its label, or something inside it. This measures the real hit area, pseudo-element extensions included, and fails where neighbours overlap.
   - Links inside running text are exempt, as in WCAG 2.5.8's inline exception (stated in the evidence).
6. **Foldable and responsive** (`tests/ui/m9-fold.test.ts`), in this order:
   1. **State survives** fold → unfold → resize → back, through `setViewportSize` and a real hinge emulation. The test checks:
      - the conversation keeps the message at the top of the screen in place (within 2 px of its offset);
      - the composer draft is intact;
      - an unsaved Settings field keeps its text and its focus;
      - the open category stays open;
      - the view and the URL don't change.
   2. **No stretched single column**: at 840, 1024, 1280 and 1920 px:
      - prose blocks are measured in `ch` of their own font, and must be 45–75ch;
      - a second pane is on screen, beside the main column.
   3. **Nothing under the hinge**: book posture (a vertical hinge, 24 px, at 1200×800) and laptop posture (a horizontal hinge at 800×1200).
      - No text, control, image or orb overlaps the hinge on any main view.
      - The same holds with the drawer, More, the sheet and a toast open.
   4. **200% text**, at phone and desktop widths: the browser's default font size is doubled through CDP (`Page.setFontSizes`, as a person's text-size setting does). On each main view:
      - no sideways scrolling;
      - no text clipped by its box;
      - no control overlaps another;
      - every destination is reachable.
7. **The fresh-user test**: `tests/acceptance/fresh-user.test.ts` and `tests/ui/setup-pwa.test.ts`, unchanged.

## What changes

- **Waiting: `ui/js/wait.js`.**
  - Every view and part that waits uses it:
    - nothing before 1 s;
    - a skeleton (a full view) or a spinner (one part) from 1 s;
    - after 10 s, the real units (parts loaded, steps done, bytes) and a general estimate where there's a measured basis.
  - Home and Tasks stop drawing an empty state before their data is in.
  - **Skeletons** are drawn from the view's last real layout on this device: each block's height is kept in `localStorage` after a real render, so the skeleton has the final geometry. With no layout kept, there is no skeleton, just a spinner line.
  - **Chat.**
    - The phase is named on screen ("Thinking", "Running ⟨tool⟩", "Writing") from 1 s.
    - After 10 s, the turn shows its steps done and the time so far.
    - Model downloads gain "about N minutes left" from the measured rate.
  - **Optimistic UI.**
    - A memory edit shows the new text at once, "Saving" while it is out, and "Saved" only when the server says so.
    - On failure the text goes back, the toast says why, and "Edit again" keeps what was typed.
    - A chat message that hasn't reached the server after 1 s says "Sending".
- **Motion.**
  - Package values move into 150–300 ms: `duration-fast` to at least 150, `duration-slow` to at most 300.
  - Hover and selection colour changes become instant.
  - The orb's state change becomes an opacity crossfade.
  - The "found" mark becomes an opacity fade of an overlay.
  - The style guide's motion demo moves with `translate`.
- **Hit areas.**
  - Icon buttons are 44 px, or 48 px on touch.
  - Small buttons keep their look and get a 44 px hit area from a pseudo-element.
  - Chat actions, switches, choices, chevrons and the composer's buttons are sized to pass.
- **Contrast.** Fixes to whatever the state audit finds: likely the disabled, placeholder and faint-text states. Package values change only where a token fails; both starters change together.
- **Layout.**
  - The right column starts at 1024 px, so every expanded width has a second pane.
  - Prose is capped at 70ch.
  - With a real hinge, the panes sit in their own segments via `env(viewport-segment-*)`, and overlays (sheet, drawer, More, toast) keep to one segment.
  - Type tokens are emitted in `rem`, so a person's text size applies.
  - The reader's place in the scroller is kept across any resize.
- **Unchanged.** Both starter packages stay structurally identical. Nothing new is decorative.

**Avoided files:** `src/runner.js`, `src/context.js`, `src/tools.js` (the ingest gate's).

## Order

1. Motion: validation, lint and package values; the motion browser test.
2. Hit areas.
3. Contrast states.
4. Progress and `wait.js`, with skeletons.
5. Web Vitals.
6. Foldable 1–4.
7. Evidence, the ledger, the inventory and the PR.

**Where it differs from the plan:**
- **Skeleton timing.** A skeleton or waiting line is drawn at once but unseen until the wait is 1 s old. It is driven by CSS and by `--wait-left`, which a redraw carries, not by a timer.
- **The right column starts at 1024 px.** On a desktop, Settings' sidebar takes its room.
- **The tablet's columns** are now "main at least 45ch, the context pane the rest, up to its width", instead of 3fr / 2fr.
- **Start-up.** The shell now shows only once its layout and first view are set. Found by the Web Vitals test.
- **The sheet's backdrop** is no longer blurred. Found by the Web Vitals test (INP).
- **Two defects the tests found:**
  - a dropped first piece of a streamed reply (the progress test);
  - focus taken from a Settings field by late data (the foldable test).
- **Package values changed only where the stricter checks failed:**
  - motion: all six built-ins;
  - contrast: Orb Teal and Aurora.
