# M2 plan — triggers, memory, triage

Roadmap M2 (`docs/builder-packet/ROADMAP-AND-GATES.md`). Builds on the M1 core (`src/core/README.md`). Same rules: erasable TypeScript run by Node, `node:sqlite`, no new runtime dependencies, `node:test`, neutral placeholders only, every module injected from `src/core/index.ts`, nothing outside `src/core` imports anything but `index.ts`.

**Gate:** an event trigger and a heartbeat job each produce ledger tasks; a proactive message traces to its trigger record; local-only mode never calls a remote provider (verified by egress log).

## 1. Decision Model Provider and templates (ADR-7 System 1, CONTRACTS §3) — `src/core/decide.ts`, migration `0002_triggers.sql`

- `interface DecisionProvider { id: string; egress: Egress; decide(t: Template, inputs: Record<string, unknown>): Promise<Decision> }`.
- `Decision = { template_id, version, answers: Record<questionId, Answer>, confidence: number /* 0..1 */, provider: string, escalate: boolean, why: string }`. System 1 never writes user-facing text: `why` is a log/receipt string only.
- Template (`decision_template` table, key `template_id` + `version`): `situation`, `inputs` (name → `'string'|'number'|'boolean'`), `questions[]`: `{id, type: 'choice', options: string[] (1..255; the validator rejects a choice without 'unknown')} | {id, type: 'score', min, max}`, `escalation: {confidence_floor}`, `stats: {uses, agreed, disagreed}`, `state: draft|active|retired`.
  - The packet's third question type, "Noul", is undefined; it is **not** implemented and is listed as an open question in the PR.
- **Cache-miss authoring:** `templates.get(id)` returns the active version or `null`. On a miss the caller gets `null` and falls back to System 1.5 rules, never to a per-request schema. Authoring is `templates.propose(def)` → `validate` (schema check) → `dryRun(cases)` → `activate`. Activation is a ledger task whose evidence is a `test_result` the verifier re-checks by re-running the dry runs. This adds a `test_result` checker registered for `template:<id>@<v>`.
- **`RulesProvider`** (egress `none`) is the local implementation. **`JevProvider`** is a stub with the same interface, egress `remote`, that throws `not configured`. Its real API needs owner-provided docs and an account, so it is escalated, not guessed.
- `decide()` wraps a provider:
  - a result below the confidence floor, or an `unknown` answer, sets `escalate: true`;
  - in local-only mode only egress `none`/`local` providers are used;
  - every call updates the template's `stats.uses`.

## 2. Trigger engine (NOVA-SPEC §4, CONTRACTS §6) — `src/core/triggers.ts`, same migration

- **`trigger_rule` table (the visible registry):**
  - `id`, `name` (plain words), `class` (`proactive|event|heartbeat`), `source` (event: `webhook:<name>`; heartbeat: `cron`), `cron` (heartbeat), `action` JSON, `dedup_window_s`, `cooldown_s`, `paused`, `hook_token_hash`, `created_by`, `created_at`, `updated_at`.
  - `action` is either `{kind:'task', task: TaskInput minus origin}` or `{kind:'message', text}`.
- **`trigger` table (one record per firing):**
  - `trigger_id`, `rule_id` (nullable for reactive), `class`, `source`, `payload_ref` (a sha256 of the payload; the payload is not stored).
  - `triage` JSON `{decision: act|queue|silent|drop, reason, model: {provider, template_id, version} | null}`.
  - `dedup_key`, `cooldown_until`, `ledger_task_id`, `message_id`, `at`.
- **`message` table (proactive contact):** `id`, `at`, `text`, `trigger_id NOT NULL REFERENCES trigger`, `delivered_at`, `read_at`. Every proactive message has a trigger.
- **`Triggers.fire({class, source, rule?, payload, dedup_key?})`** runs, in order:
  1. Record the trigger.
  2. **Dedup:** the same `dedup_key` within the rule's window → `drop`, with the reason "same as <earlier trigger>".
  3. **Cooldown:** `now < cooldown_until` → `silent`, with the reason.
  4. **Triage:** the `triage.v1` template through `decide()`. Profile policy applies: quiet hours (`policy.quiet_hours = {start:'22:00', end:'07:00'}`) turn proactive messages into `queue`, and `proactive_off: string[]` lists disabled categories.
  5. **Act:** `task` → `ledger.create({... origin: {kind:'trigger', ref: trigger_id}})`; `message` → insert the message.
  6. Set `cooldown_until`.
  7. Emit `trigger`.
- Batching: an event arriving within `dedup_window_s` of an *open* (queued or waiting) task from the same rule is linked to that task (`queue`, "added to <task>") rather than creating a second one.
- **Reactive:** `POST /api/v1/tasks` records a `reactive` trigger and links it to the task.
- **Heartbeat:** `Triggers.tick(now)` runs due cron rules once per due time (claim-once, keyed by `rule:<id>@<due ISO>`). Missed runs within 6 h catch up once; older ones are recorded as `drop` with "missed while Nova was off". The core starts a 30 s timer (unref'd) in `start()`. The cron math comes from `src/cron.js` (import from core is allowed in this direction; port to TS later).
- **Webhooks:** `POST /api/v1/hooks/{name}`.
  - Authenticated by `x-nova-hook-token` (compared against the stored sha256, in constant time), **not** by `X-Nova`, so automations can call it. This is the one exception in the API guard, and it is tested.
  - The token is shown once, at rule creation.
  - Unknown hook → 404. Bad token → 403. Paused rule → recorded as `drop`.
- **API (visible registry, no invisible automations):**
  - `GET/POST /triggers/rules`, `PUT /triggers/rules/{id}`, `POST /triggers/rules/{id}/pause|resume`, `DELETE /triggers/rules/{id}`.
  - `GET /triggers?rule=`, `GET /triggers/{id}`.
  - `GET /messages`, `POST /messages/{id}/read`.

## 3. Long-term memory v1 (NOVA-SPEC §7, CONTRACTS §7) — `src/core/memory.ts`, migration `0003_memory.sql`

- **`memory` table:**
  - `id`, `kind` (`timeline|entity|fact|preference|decision|commitment`).
    - `commitment` is Era 2's existing kind, kept and mapped.
  - `content`, `source`, `observed_at`, `recorded_by` (`nova|person|import|<worker>`), `confidence` (0..1, nullable = not stated), `scope` (book/space, default `personal`).
  - `supersedes`, `superseded_by`, `expires`, `user_state` (`confirmed|unreviewed|corrected`), `created_at`.
- **Write paths and lifecycle:**
  - `remember()` creates `unreviewed` records (Nova) or `confirmed` records (person).
  - `correct(id, content, by)` writes a new record that `supersedes` the old one. The old record stays readable and is marked superseded: history is never rewritten.
  - `confirm(id)` marks a record as confirmed.
  - `forget(id)` is **real deletion** of the record and every record in its supersedes chain. It leaves an audit event without the content.
  - Expired records drop out of `active()`.
  - Nothing below confidence 0.5 is presented as fact: `active()` marks those records `low_confidence: true`.
- **`search(query, {scope, limit})`** does term overlap (port `terms()` from `src/memory.js`). It returns records plus the retrieval list, for receipts.
- **Export (ADR-4, plain files):** `export()` writes `exports/memory-<stamp>/memory.json` (all fields) and `memory.md` (human-readable, grouped by kind), and returns the paths. Exposed as `GET /memory/export`, which does the write and returns the paths, and `GET /memory?kind=&scope=&state=`.
- **Context receipts (CONTRACTS §2), `receipt` table:**
  - Fields: `id`, `at`, `task_id` (nullable), `session_id` (nullable), `provider`, `model`, `purpose`, `privacy_mode`, `egress` (`local` or `remote:<name>`).
  - `context_items` is JSON `[{kind: 'memory'|'file'|'skill'|'session'|'standing', ref, sha256}]`.
  - `receipts.record(...)`, `GET /receipts?task_id=&session_id=`.
  - The egress log is `GET /receipts?egress=remote`.

## 4. Integration (done after 1–3 land)

- **Era 2 chat:** every model call records a receipt. Its context items are the standing files (each hashed), the recalled notes, the skills loaded and the session.
- **Era 2 memory:**
  - At start, `MEMORY.md` entries are imported once into core memory. Ids, sources and times are kept, and the file is hashed.
  - Writes from `<remember>` / `<forget>` / the Memory view go to core.
  - `MEMORY.md` is re-rendered from core after each change.
  - A hand edit to the file (hash mismatch) is imported as corrections or additions by the person.
  - Day notes stay files for now; they are the `timeline` kind, imported in M3.
- **Era 2 schedules:** each scheduled run becomes a heartbeat trigger plus a ledger task owned by the `chat-run` worker.
  - The worker's egress is the model's; its evidence is a `confirmation` that Nova checks itself by finding the delivered handoff in the session log.
  - This removes the second record of background work noted at M1. Helpers follow the same pattern.

## 5. Gate test — `tests/acceptance/m2-triggers.test.ts`

A real server process, a blank profile set to local-only, and the egress tripwire. The test:
1. Creates a webhook rule and a heartbeat rule (`* * * * *`, with the tick time injected through a test-only `POST /triggers/tick` that exists only when `NOVA_TEST_CLOCK=1`).
2. Fires the hook twice. The second firing is deduped.
3. Ticks. Both firings produce ledger tasks that end done and verified.
4. Fires a proactive `message` rule. The message's `trigger_id` resolves to its trigger record.
5. Checks local-only: there are no remote receipts, the egress log is empty, and the remote `JevProvider` was never called.
