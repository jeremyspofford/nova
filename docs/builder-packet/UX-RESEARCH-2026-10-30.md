# Perceived Performance & UX Psychology for a Local-First Personal AI Agent OS

*Scope: chat interface, task/work ledger, settings, themes, PWA on desktop / phone / foldable. Verdicts: **ADOPT** = honest, fits a trusted agent · **ADAPT** = use only in the honest form named · **REJECT** = deceptive / engagement-bait in the form named. Evidence flags: Strong = replicated / standard / primary guideline; Moderate = single well-run study or convergent practitioner research; Weak/Contested = lab-only, mixed replication, or blog-inflated.*

## Summary — the one rule that resolves most of this

**Show real work, early, in place — and never manufacture work, time, or progress.**
Almost every legitimate perceived-performance technique is a version of *visibility of system status* (NN/g Heuristic #1): acknowledge instantly, show what is actually happening where the result will appear, and let the user start reading/using partial real output. Almost every rejected technique is the same visual trick detached from reality: a bar that does not measure anything, a delay added to look thorough, ribbing/easing engineered to distort time, a checklist engineered to nag. For a *trusted, local-first* agent the asymmetry is decisive — the honest form gets nearly all of the benefit (Buell & Norton's transparency effect works with *real* transparency), and discovery of one fake — view-source, a ledger timestamp, an offline test — destroys the trust the trick was meant to build, and contradicts the product's own work ledger.

Three numbers to build to: **0.1s / 1s / 10s** response limits (Nielsen); **INP ≤200ms, CLS ≤0.1, LCP ≤2.5s at p75** (web.dev); **4.5:1 contrast, 44pt/48dp targets** (WCAG / HIG / Material).

## Findings

### 1. Progress indicators

| Technique | Mechanism (one line) | Evidence / source | Verdict |
|---|---|---|---|
| Immediate acknowledgement (<0.1s pressed state, optimistic paint) | Removes "did it hear me?" uncertainty, the largest component of felt wait | NN/g: "Always give some type of immediate feedback… Without any visual change most users will assume the action was not registered and try again." Response limits 0.1s instant / 1s flow / 10s attention — https://www.nngroup.com/articles/progress-indicators/?ref=checklist.design (verified live, 2026-10-30); https://www.nngroup.com/articles/response-times-3-important-limits/ (index). **Strong** | **ADOPT** |
| Determinate / percent-done bar, with step text ("Updating address 3 of 50", "Indexing 412 of 1,900 notes") | Converts an open-ended wait into a bounded, controllable one; user can decide to wait or do something else | NN/g: percent-done is "the most informative type," use for ≥10s; a Univ. of Nebraska-Lincoln study cited there found a moving progress bar → higher satisfaction and willingness to wait ~3× longer than no indicator. Same NN/g URL above (verified live). **Strong for "show it", Moderate for the 3× figure (single study)** | **ADOPT — only when % is computed from real units of work** (files, tokens, steps). If units are unknown, do not invent a % |
| Indeterminate spinner / looped animation | Signals "working, duration unknown" — better than silence, gives no time information | NN/g: reserve looped animation for **2–10s**; <1s it is distracting/flashing; >10s users "cannot be sure if the system is still working" and abandon. Same URL (verified live). **Strong** | **ADOPT within 2–10s, for a single module** (a card, a tool call), never as a full-screen answer for a long agent task |
| Skeleton screen (content-shaped placeholders) | Pre-builds the mental model of the arriving page; page appears to be "gradually transitioning into its final format," and prevents layout jump | NN/g Skeleton Screens 101: full-page loads only, **<10s, not <1s** (flash), frame-only skeletons (header/footer, no content wireframe) explicitly **not recommended**; animated shimmer can distract / create accessibility problems; cited primary study Mejtoft, Långström & Söderström 2018, *Proc. ECCE*, DOI 10.1145/3232078.3232086 — https://www.nngroup.com/articles/skeleton-screens/?lm=cookie-permissions&pt=article (verified live). **Moderate** — note: blog claims of "skeletons cut perceived load 20–30%" found in search results are **not** in NN/g and should not be quoted | **ADOPT** for ledger / settings / history list loads with a known shape; **REJECT** frame-only skeletons and skeletons for a *process* (upload, export, sync — use a bar/step list, per NN/g) |
| Paused / stalling bar, esp. sprint-to-99%-then-hang | Expectation set by early speed is violated at the end; the stall is what is remembered (see Peak-End, §3) | NN/g: "if the progress moves quickly only to hang on the last percentage remaining, the user will become frustrated and the benefits… will be negated." Harrison et al. 2007 *Rethinking the Progress Bar* (UIST): pauses — especially late — rated worst of all behaviours — https://www.researchgate.net/publication/220876993_Rethinking_the_progress_bar (index). **Strong (convergent)** | **REJECT the pattern; engineer against it** — buffer the estimate, weight the bar by measured step cost, and if a step is genuinely long, subdivide it visibly instead of freezing |
| Accelerating (slow-start, faster-end) bar | Ends are weighted; finishing faster than the early pace implies beats expectation | NN/g (wait animations only): "Start the progressive animation slower and allow it to move faster as it approaches the end… Exceeding customer expectations always creates more satisfaction." Harrison 2007 likewise preferred accelerating/"power" curves. **Moderate, and note the direct conflict:** for *survey/form* progress NN/g notes the opposite (fast-start/slow-end reduces drop-off — that is goal-gradient exploitation, §3). **Weak/Contested as a universal law** | **ADAPT** — honest form only: this is what you get *for free* if you initialise/bookkeep first and stream results as they complete, and if your estimate is conservatively padded. **REJECT** deliberately re-mapping a known-linear % through an easing curve to distort felt duration |
| Animated ribbing / pulsation engineered to shrink felt time | Backward-moving stripes raise apparent velocity (induced motion), compressing perceived duration ~11% at identical real duration | Harrison, Yeo & Hudson 2010, *Faster Progress Bars*, CHI — backwards, decelerating ribbing reduced perceived duration **11%** (p<.001 in matching task; 5s bar felt like a 5.61s plain bar) — PDF: https://attachments.are.na/7067419/94c1d92c0c5ba0d2f91d6ce376f62461.pdf?1588136738 (index). Later work is mixed: *Scientific Reports* 2022, "Malleability of time through progress bars and throbbers" https://link.springer.com/article/10.1038/s41598-022-14649-1 (index) confirms step-frequency effects but the accelerating-vs-decelerating literature disagrees (Harrison 2007 vs Kim & Xiong 2017 vs Kuroki & Ishihara 2015). **Real but lab-only, short bars, contested direction** | **REJECT as a deliberate time-distortion.** A subtle indeterminate shimmer on a skeleton is fine because it signals liveness; designing stripe direction/speed *in order to* make a wait feel 11% shorter is perceptual manipulation with no information content |
| Optimistic UI (paint the user's own action instantly, reconcile/roll back on failure) | Collapses perceived latency to ~0 for the common success case; user is never blocked on a round-trip they don't care about | Practitioner-convergent, no single canonical RCT; grounded in the 0.1s instant-response limit above and in NN/g's immediate-feedback rule. Works because a local-first agent's writes are in fact usually already durable locally — so here it is often **not even optimism, it is the truth** (local write succeeded; sync is a separate, separately-reported state). **Moderate** | **ADOPT — with the honest split:** show *"Saved on this device"* instantly; show sync/remote confirmation as its own status, never conflate the two. Rollback must be visible, non-destructive, and explain itself (toast + undo), not a silent disappearance of the user's message/task |
| Real streaming response (tokens / tool steps as they are produced) | Time-to-first-content collapses; reading time overlaps generation time, so total wait is partly *used*, not endured | Strongly convergent practitioner + NN/g response-time logic; one controlled study on presentation speed: *Thoughtful, Confused, or Untrustworthy* (n=297, reviewed at https://www.themoonlight.io/tw/review/thoughtful-confused-or-untrustworthy-how-text-presentation-influences-perceptions-of-ai-writing-tools, index) — medium speed (~600 wpm in that study) was most comfortable / highest perceived quality; too-slow felt confused, unnatural orders (backwards/random) least trustworthy. **Moderate; the study is about simulated co-writing, not production LLMs** | **ADOPT — this is the single highest-value technique for the chat surface.** Stream real tokens, and interleave real tool/ledger steps ("Searched notes · 3 hits", "Wrote task #…") as they happen. Pace rendering to readability and coalesce to animation frames (see jank, §2) rather than painting per token |
| Fake streaming / client-side typewriter over a completed response | Simulates generation that is not happening; adds real delay to buy a feeling | No supporting primary evidence found; it is detectable (offline, view-source, instant regenerate) and, for structured output (tool calls, ledger entries, cards), risks painting invalid/partial structures. Blog discussion explicitly calls this a "streaming illusion" — https://recipyapp.com/blog/streaming-illusion-ai-chat-interfaces-2026 (index, opinion source — flagged as such) | **REJECT.** If the model/API gives you the answer whole, show it whole (with a short fade if a hard paint is jarring). Never hold a finished answer hostage to an animation |
| Showing real work — operational transparency (live checklist of actual searches, files read, tools run) | People use visible effort as a proxy for thoroughness/value and reciprocate it; uncertainty falls | Buell & Norton 2011, *The Labor Illusion*, Management Science 57(9):1564–1579, DOI 10.1287/mnsc.1110.1376 — 5 experiments (travel, dating): with operational transparency people could *prefer a longer wait to an instant result with identical output*; perceived effort → reciprocity mediated the value gain — https://pubsonline.informs.org/doi/10.1287/mnsc.1110.1376 (index). Buell, Kim & Tsay 2017 extended it (open-kitchen field data). **Strong for the effect** | **ADOPT — in its literal form.** An agent genuinely *does* multi-step work; a collapsible, timestamped work trail in the ledger is transparency, not theatre, and it doubles as an audit record. Default to a one-line summary, expand on demand (progressive disclosure) so transparency doesn't become noise |
| Artificial delay + fake "checking / searching…" animation (TurboTax / Facebook security-check pattern) | Manufactured effort exploits the same labor illusion after the work is already done | Documented, not hypothetical: *The Atlantic* (2017) reverse-engineered TurboTax's "double-checking" animation — fixed duration, same for every user, **not communicating with the server at all** once started; framed via Adar et al. 2013 "benevolent deceptions," whose own ground rules were: prefer non-deceptive solutions, the deception must measurably improve the product, and users *if asked* would prefer it — https://voussoir.net/writing/advertixing/atlantic_fake_progressbars.html (index, reproducing The Atlantic). **Strong that it occurs and "works" short-term** | **REJECT — categorically, for this product.** A personal agent holds the user's files, money-adjacent tasks and private notes; a discovered fake "checking" animation retroactively poisons every real check it ever reported. If an instant result feels untrustworthy, the honest fix is a real, inspectable result (sources, diff, ledger entry), not a pause |
| General time estimate ("about a minute", step counts) instead of false precision | Bounds uncertainty without staking credibility on a number the system cannot keep | NN/g: "Provide a general time estimate. (Don't try to be exact…) 'About 3 minutes remaining'… Always allow for extra time." Progress-indicators URL above (verified live). **Strong (guideline)** | **ADOPT.** Prefer steps completed/total and elapsed time over countdowns for agent tasks, whose step costs are genuinely variable |

**Rule of thumb (NN/g, verified live):** <1s — no indicator · 2–10s — spinner (single module) or skeleton (full page) · >10s — determinate bar / step list + general estimate · any length — immediate acknowledgement first.

### 2. Perceived performance beyond progress

| Technique | Mechanism | Evidence / source | Verdict |
|---|---|---|---|
| Progressive rendering / disclosure of *content* — render text & cached local data first, enrich (images, previews, sync state) in place | User can start reading/working during the wait instead of after it; local-first makes the cached layer real, not a placeholder | NN/g Progressive Disclosure: defer secondary options/details to a secondary screen; improves learnability, efficiency, error rate — https://www.nngroup.com/articles/progressive-disclosure/?lm=top-10-application-design-mistakes&pt=article (index). Applied to rendering this is the standard "show primary content first" pattern. **Strong for disclosure; Moderate for the rendering extension** | **ADOPT.** Ledger and chat history should paint instantly from local storage on open — for a local-first PWA this is the core speed advantage and it is honest by construction |
| Layout stability — reserve space for everything async (avatars, images, tool cards, banners); CLS ≤0.1 | Shifting content causes mis-taps and reads as broken/unreliable even when fast | web.dev Core Web Vitals (via multiple summaries citing web.dev directly): **LCP ≤2.5s, INP ≤200ms, CLS ≤0.1 = "good", measured at the 75th percentile**; CLS = impact fraction × distance fraction; shifts within 500ms of a user interaction are excluded. **Strong (platform standard)** | **ADOPT as a release gate.** Skeleton shapes must match final geometry exactly or they *create* the shift they were meant to prevent |
| Avoiding jank — 60fps (16.6ms/frame), no main-thread task >50ms, animate only `transform`/`opacity`, virtualise long lists, yield/chunk heavy work | A dropped-frame, stuttering UI is perceived as slow regardless of total load time; responsiveness is judged per-interaction | web.dev INP guidance (summarised at https://frontend.thejsdeveloper.com/lessons/0007-rendering-performance.html, index): >50ms = long task; INP phases are input delay / processing / presentation; fixes are break up tasks, yield, move work to a Worker, virtualise. **Strong (platform standard)** | **ADOPT.** Especially: coalesce streamed tokens to one paint per frame; never re-render the whole transcript per token; virtualise chat/ledger lists |
| Animation duration & easing | Motion explains *where things went*; too slow reads as latency, linear reads as mechanical | Material Design motion (via convergent summaries of the spec): standard mobile transition ~**300ms**, entering **225ms**, leaving **195ms**, desktop **150–200ms**, tablet +30%, wearables −30%, "transitions that exceed 400ms may feel too slow"; M3 duration tokens short 50–200ms / medium 250–400ms / long 450–600ms; ease-out (decelerate) for entering, ease-in (accelerate) for exiting, standard curve cubic-bezier(0.4,0,0.2,1). Practitioner range agrees: micro-interactions 100–200ms, component transitions 200–300ms, page transitions 300–500ms. **Strong as a design-system standard, not as an RCT finding** | **ADOPT the ranges; honour `prefers-reduced-motion`** (replace movement with instant/fade state change). **REJECT** bounce/elastic "delight" on frequent, hundredth-use actions — it is a tax paid every time |
| Micro-interactions (pressed states, toggle travel, pull-to-refresh, success tick) | Each one answers one silent question — *did it hear me, what happened, what's next* (Saffer: trigger → rules → feedback → loops/modes) | Saffer, *Microinteractions* (O'Reilly, 2013); structure and haptics vocabulary summarised at https://ux.detroit3d.com/patterns/microinteractions-motion.html (index). **Moderate (framework, widely adopted)** | **ADOPT, with restraint:** feedback must be fast, honest and predictable; a progress bar inside a micro-interaction must tell the truth. Remove any micro-interaction that only decorates |
| Haptics | Confirms through skin what the eye may miss (detent crossed, action committed, error) — valuable precisely because touch has no hover/cursor | Apple HIG semantic haptics (success/warning/error notification generators; impact; selection tick) and Android `performHapticFeedback`/`VibrationEffect` primitives; guidance in both: use system semantics consistently, don't fire continuously or for every trivial touch, strength ∝ importance, respect the system haptics setting. Same Detroit3D summary (index). **Moderate (platform guidance; little independent RCT evidence — flag)** | **ADAPT — sparse and semantic:** send/commit, destructive-action boundary, error. Never the sole channel (pair with visible state), never on a PWA where support is partial/Android-only without a visual equivalent |
| Sound | Eyes-free confirmation (payment, timer, message sent) | Same source: "silent-by-default is the norm for productivity software"; respect mute/ringer; never sole channel for information (cf. WCAG 1.3.3, no single-sense cues). **Moderate/Weak as positive evidence; strong as a restraint norm** | **ADAPT — off by default, opt-in, only for completion of a background/long task** where the user has plausibly looked away. **REJECT** sent-message whooshes, typing sounds and other skeuomorphic audio on by default |
| Preload / prefetch / speculative work | Work done before it is asked for is latency that never appears | No primary source retrieved for this mission — included because it follows directly from local-first architecture (warm cache, pre-rendered shell). **Flagged: inference, not cited evidence** | **ADOPT where it is real work on the user's own device/data** (app shell, recent conversations, ledger index). **REJECT** speculatively generating agent answers the user didn't ask for and presenting the cost/speed as on-demand |

### 3. UX psychology effects — honest use vs manipulative misuse

| Effect | What it is / evidence strength | Honest application (ADOPT/ADAPT) | Manipulative misuse (REJECT) |
|---|---|---|---|
| **Visibility of system status / feedback loops** (Nielsen Heuristic #1) | The design should always keep users informed, through appropriate feedback within a reasonable time. **Strong** — foundational heuristic, underlies §1 entirely. NN/g progress & heuristics sources above | Every agent state is legible at a glance: idle / thinking / running tool (which one) / waiting on user / done / failed-and-why; ledger is the persistent version of the same principle | A perpetual "active/thinking" glow or animated presence that implies work when the agent is idle |
| **Peak-End Rule** | Experiences are judged by the most intense moment and the *end*, with duration largely neglected. Kahneman, Fredrickson, Schreiber & Redelmeier 1993 (cold-pressor: a longer trial with a slightly better end was preferred for repetition); Redelmeier & Kahneman 1996 (real colonoscopy patients). Summarised at http://lawsofux.com/articles/2020/peak-end-rule/ (index). **Strong in memory research; Moderate in direct UI transfer** | Invest in the *endings you actually control*: the completion state of a task (clear summary, what changed, where it is filed), the error-recovery ending, the export/finish screen. Fix the worst peak (a data-loss scare, a 99%-stall) before polishing averages | Engineering a euphoric fake "peak" (confetti, inflated praise, a manufactured breakthrough moment) or padding an experience with a pleasant tail to make a worse total experience rate better — the original experiment is literally about preferring *more* total pain |
| **Von Restorff / Isolation Effect** | An item that differs from a homogeneous set is remembered better. Von Restorff 1933, isolation paradigm — https://en.wikipedia.org/wiki/Von_Restorff_effect (index). **Strong (classic memory finding)** | Exactly **one** salient thing per view: the primary action, or the one item needing the user's decision (an approval request, a failed task). Salience must encode real priority | Making ads, upsells, engagement prompts or a "recommended" plan the most salient element; salience inflation (everything bold/red/badged) which destroys the effect and the hierarchy. Note the corollary: if five things are highlighted, none is |
| **Hick's Law (Hick–Hyman)** | Decision time rises *logarithmically* with the number/complexity of choices. Hick 1952. **Strong** | Fewer, better defaults: 3–5 top-level destinations, one recommended action per agent proposal, advanced options behind progressive disclosure, sensible defaults so most choices never have to be made | Choice *architecture* that hides the option the user would want (burying "keep my data local" / decline under more clicks than accept). Hick's law justifies reducing choices, never asymmetric friction |
| **Jakob's Law** | Users spend most of their time in *other* products and transfer those expectations; they prefer yours to work the same way. Nielsen. **Strong as a heuristic; it is an observation, not an experiment** | Copy the conventions users already have: chat layout (§4), iOS-style grouped settings lists, standard scrollbars, Cmd/Ctrl-K, swipe/hover idioms per platform. Spend novelty only where the agent is genuinely new (approvals, work trail) | Using familiarity as cover — making a novel, consequential agent action *look like* a harmless familiar one (an auto-send styled as a draft, a permission grant styled as a dismiss) |
| **Doherty Threshold** | Productivity rises steeply when system response drops below ~400ms, so neither party waits on the other. Doherty & Thadani, IBM Systems Journal 1982 (mainframe terminal users). **Contested as a precise number** — a 1982 mainframe productivity inflection, endlessly re-quoted as a universal 400ms law; treat it as "sub-second, ideally sub-400ms feedback matters a lot," consistent with Nielsen's independent 0.1/1s limits | Budget for it: acknowledge <100ms, paint meaningful feedback <400ms, keep INP ≤200ms; where real work can't fit, use §1's honest indicators rather than silence | Citing "400ms" as licence to *fake* the response inside the window (optimistic paint of something the system has not in fact accepted, with silent failure later) |
| **Aesthetic-Usability Effect** | Attractive interfaces are rated more usable than identical-function plain ones, and users tolerate minor flaws longer. Kurosu & Kashimura 1995 (252 participants, 26 ATM layouts — perceived appeal correlated with *apparent* usability more than with actual usability); Tractinsky et al. 2000 replication ("What is beautiful is usable"); NN/g (Moran 2017, updated Feb 3 2024): the effect "can mask UI problems during usability testing" — listing at https://www.nngroup.com/articles/?vpage=52&apage=121&page=47 (index). **Strong, with a documented failure mode: it does not survive severe usability problems** | Polish as a real investment (§7) — a coherent theme, aligned grid and calm motion genuinely raise perceived quality and patience for a long task | Using polish *instead of* fixing usability, or as trust theatre: a beautiful surface on an agent whose ledger, sources or permissions are opaque. Also a research trap for the team itself: pretty prototypes test falsely well — judge usability sessions by what users *do*, not what they say (NN/g) |
| **Zeigarnik Effect** | Interrupted/incomplete tasks are remembered better than completed ones. Zeigarnik 1927. **Weak/Contested — mixed modern replication record; treat as a heuristic, not a law** (flagged explicitly in one source reviewed: "treat it as a design heuristic, not a law") | A truthful open-loops view: drafts, tasks awaiting approval, and unfinished setup are surfaced and *resumable* — resume, don't restart; autosave so leaving never loses work. The benefit is the user's own memory, served | Manufacturing open loops to pull users back: deliberately incomplete profiles, "you left something unfinished!" notifications, withholding a completion state. That is engagement-bait built on an unreplicated effect |
| **Goal-Gradient Effect (+ endowed progress)** | Effort accelerates as a goal nears; an artificial head start increases completion. Hull 1932; Kivetz, Urminsky & Zheng 2006 (coffee-card field/lab studies: a 12-stamp card with 2 stamps gifted completed faster than an equivalent 10-stamp card). **Moderate–Strong in loyalty contexts; Moderate transfer** | Show real distance-to-done on finite, user-chosen goals: "3 of 8 files migrated," setup checklist with true counts, a task's remaining steps. Showing steps remaining *from the first step* is the honest core | **Endowed/fake progress:** pre-filling a bar, inflating the denominator, or moving the finish line (steps that subdivide as you approach). Also survey-style fast-start bars designed to exploit the gradient (cf. the NN/g exception in §1) |
| **Labor Illusion / Operational Transparency** | See §1. **Strong** (Buell & Norton 2011; Buell, Kim & Tsay 2017) | Show the agent's real steps, sources and elapsed effort in the ledger | Fake effort, fake delay, fake "searching 326 sites" counters (REJECT, §1) |

### 4. Chat UI specifics

*Evidence note: there is almost no peer-reviewed research on chat minutiae. What exists is (a) NN/g chatbot/conversation research, (b) convergent conventions of the major products, and (c) design-system specs. Product details below are conventions as widely documented in 2024–26 sources and change between releases — re-check the live products at build time; they are **index-level**, not verified live in this mission (all require accounts/devices).*

| Decision | What the evidence / major products do | Verdict for this agent |
|---|---|---|
| **Bubbles vs no bubbles** | Two stable families. *Person-to-person messaging* (iMessage, WhatsApp): bubbles for both sides — they chunk turns, carry state (delivered/read, reactions, reply-quotes) and survive very short messages ("ok"). *Document-length AI chat* (ChatGPT, Claude): the **user's** turn is a bubble (right-aligned / tinted pill), the **assistant's** turn is **not** — it is full-width, un-bubbled, document-like text, because assistant output is long, structured (headings, lists, code, tables) and a bubble's side padding + narrow measure actively harm it. NN/g-derived guidance agrees colour/alignment differentiation makes authorship "really easy to see," and warns long bot text in bubbles creates "cramped, unpleasant blocks" — break it up instead — https://lovable.dev/guides/how-to-build-a-chatbot-ui (index, citing NN/g research) | **ADOPT the AI-chat family:** user = tinted bubble, agent = full-width un-bubbled with a clear turn separator. **REJECT** iMessage-cloning for agent output — it will break on the first table, code block or ledger card |
| **Tails / direction cues** | The tail is a skeuomorphic speech-balloon pointer. iMessage shows a tail **only on the last message of a group** (and reduced/absent in many modern styles); WhatsApp uses a small pointed corner on the first message of a group. Slack, ChatGPT and Claude use **no tails at all** — alignment + colour + avatar/name already carry authorship, so the tail adds no information. No usability study found showing tails improve comprehension | **REJECT tails** (pure decoration, and they complicate grouping, reactions and RTL). Carry direction with alignment, tint, and — for the agent — a consistent name/label, which unlike a tail also works for screen readers |
| **Avatars: repeated vs once-per-group** | Slack's canonical pattern: avatar + name + time on the **first** message of a group; subsequent grouped messages show no avatar (a small time appears in the gutter on hover). Design-system spec reviewed states the same rule and its reason: without grouping "the message list becomes visually noisy and the avatar column loses meaning" — https://uidesignprompts.com/prompts/chat-app-ui (index). iMessage/WhatsApp: avatar (where shown at all, mainly groups) appears once, aligned to the **last** message of the group. ChatGPT/Claude dropped per-message assistant avatars as their turns became document-like | **ADOPT once-per-group, never per-message.** In a 1:1 user↔agent thread avatars are close to worthless — there are only two possible authors and alignment already says which. Keep a single agent identity mark per turn/group; repeating it per message wastes the left column that code/tables need. Reserve avatars for multi-party/agent-team views where authorship genuinely varies |
| **Timestamps: always vs hover/swipe vs grouped** | Three convergent patterns: (1) **Date/gap dividers** — all products insert a centred date (and, in iMessage, a time) pill when a conversation resumes or a significant gap passes. (2) **Per-group, not per-message** — Innovaccer's chat design system: messages <5 min apart group; "display the timestamp only for the first message" of the group, and status only on the last — https://design.innovaccer.com/components/chatBubble/usage/ (index). (3) **Exact time on demand** — Slack: short time beside the group header, full timestamp in a hover tooltip; iMessage: timestamps on swipe/hover in some clients; WhatsApp is the outlier, printing a small time **inside every bubble** (because its bubbles are short and delivery state lives there too) | **ADOPT (1)+(2)+(3):** date/gap dividers always; group time visible; exact per-message time on hover (desktop) / long-press or swipe (touch) / in the message details — never *only* on hover, which is undiscoverable and inaccessible. For an agent, add what messengers don't need: **elapsed duration and completion time on the work trail**, since "when did it do that, and how long did it take" is an audit question, not small talk |
| **Typing / thinking / streaming indicators** | Human chat: iMessage's three-dot typing bubble means *a person is composing* — it is a social signal. AI chat has repurposed the same slot for *the system is working*: ChatGPT/Claude show a brief indicator, then streaming text replaces it; a pulsing dot/caret at the stream head signals "still generating," paired with a **Stop** control. NN/g's framing applies directly: an indicator must distinguish working from hung, and (per §1) an indeterminate indicator is only tolerable for ~2–10s before a user needs progress information | **ADAPT — do not fake a human.** Never show a "typing…" indicator while nothing is being generated, and never use the three-dot human-typing metaphor to imply the agent is a person composing. **ADOPT:** (a) instant acknowledgement, (b) a labelled state that names the real phase — *Thinking / Searching your notes / Running [tool] / Writing* — which for an agent is available truthfully, (c) streaming text as soon as tokens exist, (d) a visible Stop from the first token to completion, (e) if a phase exceeds ~10s, escalate from dots to the step list/elapsed time |
| **Grouping & spacing** | Universal: tight spacing *within* a same-author group (a few px), clearly larger spacing *between* turns/groups, widest around date dividers — gestalt proximity does the grouping work that borders/tails would otherwise do. Common grouping rule: same author, no intervening turn, within ~2–5 min (5 min in the spec cited above). Reactions, reply-quote and hover actions attach to the group/message without shifting layout (see CLS, §2) | **ADOPT a 3-tier spacing scale from your spacing tokens (§7), e.g. 2–4px intra-group / 12–16px between turns / 24px+ around dividers,** and test it at 200% text size. Hover-revealed actions must also exist on touch (long-press / overflow) and keyboard focus |

### 5. Settings information architecture

**There is no evidence-based magic number for "when a single page breaks down."** No source retrieved — NN/g included — publishes a validated control-count threshold. What follows separates the (real) guidelines from a practical heuristic, labelled as such.

| Approach | Guidance / evidence | Verdict |
|---|---|---|
| Grouped single page (iOS Settings pattern) | iOS Settings is one long, searchable, **grouped inset list**: sections with headers/footers, related controls together, disclosure chevrons to sub-pages, search pinned at top. It works far past the point intuition suggests *because* of grouping + search + stable ordering — and it is the pattern users bring via Jakob's Law. NN/g's underlying principle is progressive disclosure: show the few important options, defer specialised ones — https://www.nngroup.com/articles/progressive-disclosure/?lm=top-10-application-design-mistakes&pt=article (index) | **ADOPT as the phone/default form** while the count is modest: one scroll, grouped, with sticky section headers and search |
| Search at the top | Necessary once users can't hold the map — but **search is only as good as its synonyms.** Mozilla's multi-phase usability studies (2024–25) of changing a default browser on iOS/Windows found participants repeatedly failed because Settings search returned **nothing for "browser" / "default browser"**: "Fix Search: ensure common search terms return relevant results and add typo correction, partial matches, and suggested alternatives" — https://research.mozilla.org/easy-default-browser-settings-arent-always-easy (index) | **ADOPT with the Mozilla conditions:** index every control by its user-word synonyms (not just its label), show the *path* ("Appearance › Theme") in results so users learn where things live, and deep-link + highlight the control on arrival |
| Sidebar nav (desktop / expanded) | macOS System Settings and Windows 11 Settings both converged on **left category list + right detail pane + top search** — the list-detail canonical layout. It keeps location visible (recognition over recall), scales to many categories, and maps directly onto the foldable expanded window class (§7) | **ADOPT for expanded/desktop:** same category model as the phone list, presented as a sidebar — one IA, two presentations. **Never** maintain two different groupings for phone and desktop |
| Tabs | NN/g *Tabs, Used Right*: tabs suit **a few, long, parallel sections** of the same level; accordions suit **many short sections, and work better than tabs on mobile** (limited space, longer labels allowed) — https://www.nngroup.com/articles/tabs-used-right/?lm=ai-sparkles-icon-problem&pt=article (index) | **ADAPT:** tabs only if there are ≤~5 peer categories with substantial content each, on desktop. **REJECT** tabs-within-tabs and tabs as the phone pattern (labels truncate, hidden categories are forgotten — content behind a tab is content users assume doesn't exist) |
| Accordions / grouped sub-pages (phone, many categories) | Per NN/g tabs-vs-accordion guidance above; also the natural extension of iOS's grouped-list-plus-subpage model | **ADOPT for compact width:** category list → category page, or accordions for short groups. One level of nesting maximum for settings |
| Category design | Group by the **user's task/mental model** (Account, Agent & Permissions, Appearance, Data & Storage, Notifications, Privacy, About), not by which engineering team owns the control; validate with card sorting / tree testing (NN/g IA methods) rather than internal debate. Keep infrequently-changed, dangerous items (data deletion, permissions, sync scope) *findable but not prominent* — and never bury them to discourage use (that is the Mozilla dark-pattern finding in reverse) | **ADOPT** |
| **Practical breakdown heuristic (labelled: practitioner heuristic, not research)** | A grouped single page stops working when any of these bite: the user must scroll more than ~3–4 viewport heights to reach a known item *and* can't remember its section; a section exceeds ~7–10 controls and needs its own sub-grouping; two controls with near-identical labels land in different sections; or find-a-setting tasks in testing start failing/being routed through search for *common* items. At that point switch presentation (sidebar/sub-pages), not just add more headers | **ADAPT — use as a trigger to test, not as a rule.** Instrument it: if most settings visits start with search, your grouping has already failed |
| Examples to copy / avoid | Copy: iOS (grouped list + search + sub-pages), macOS/Windows 11 (sidebar + search + consistent category names across platforms). Avoid: the historical Windows split of Settings *and* Control Panel (two homes for the same control — the canonical IA failure), and settings that exist only via search with no browsable path | — |

### 6. Theme / appearance customisation UX

*Evidence note: no primary study was found directly comparing "live preview on the real UI" vs "static mock preview" for themes (see Could Not Verify). The recommendation below follows from NN/g customisation research, the WYSIWYG/undo heuristics, and convergent product practice — labelled accordingly.*

| Pattern | Mechanism / evidence | Verdict |
|---|---|---|
| **Live preview applied to the real UI** (controls sit on top of / beside the actual app, which re-themes as you pick) | What you evaluate is what you get: real text lengths, real density, real contrast in your actual chat/ledger — including the failure cases a mock never shows (long task titles, code, low-contrast accent on your own data). NN/g on customisation: tools must be easy to find, easy to use, and **easy to change later**; layer options with progressive disclosure — https://www.nngroup.com/articles/customization/?lm=reset-and-cancel-buttons&pt=article (verified live) | **ADOPT — strongly preferred.** Especially for this app: a theme's real test is body-text contrast in a long agent answer and muted-text contrast in the ledger, neither of which a hero-image mock exercises |
| Static preview mock / swatch card only | Cheap, and fine as a *picker thumbnail* (name + a few colour chips + a miniature chat snippet) — but as the only preview it systematically lies: tiny type, no real content, no states (disabled, error, streaming, selected) | **ADAPT:** use as the gallery/index view only; selecting one must apply it live for evaluation. **REJECT** as the sole decision surface, and **REJECT** preview images rendered in a different layout/density than the real app |
| **Apply-instantly + Undo** (theme applies on tap; "Revert" / previous theme offered, toast with Undo) | Matches how users actually explore — by trying — and satisfies Heuristic #3, User Control & Freedom: support undo/redo, provide a clearly marked exit; make undo *discoverable* (a visible control, not a hidden gesture — NN/g's example is iOS shake-to-undo being "notoriously underused" because undiscoverable) — https://www.nngroup.com/articles/user-control-and-freedom/?lm=ten-usability-heuristics&pt=article (index) | **ADOPT as the default model for appearance** (low-stakes, fully reversible, instantly judgeable). Keep: current theme, previous theme, and "System / Light / Dark defaults" always one tap away |
| Preview-then-Save/Apply (dialog model: edit, then *Apply/Save* commits, *Cancel* discards) | The classic GUI dialog contract (NN/g *Reset and Cancel Buttons*: in window-based GUIs a Cancel button that "closes any dialog box and discards any changes" is standard and supports exploratory learning) — https://www.nngroup.com/articles/reset-and-cancel-buttons/ (index). It earns its friction where a change is *expensive, shared, or hard to reverse* | **ADAPT — reserve for the consequential cases:** a theme that will **sync to all devices**, a custom theme being published/shared, or bulk appearance changes (density + font + theme together). Then use an explicit scope + summary before commit. Using a Save gate for a simple light/dark/accent pick is pure friction |
| Reset button on the theme form | NN/g (same article): *Reset* "hurts users" and should generally be removed — **except** its legitimate form, revert-to-default for repeated/revertable forms | **ADAPT:** no Reset on the editing form; do provide a clearly labelled **"Restore defaults"** as a first-class, confirmable action in Appearance |
| Scope: this device vs all devices / sync | No primary research retrieved (flagged). The risk is a pure mental-model one: a user experimenting on their phone at night silently re-themes their desktop, or a work device inherits a personal theme. Platform precedent: OS appearance (light/dark) is per-device by default, while account themes in products like Slack/Telegram make the scope a visible choice | **ADOPT (as a design rule, evidence-flagged as inference): default to *this device*; make "Apply to all my devices" an explicit, labelled, opt-in toggle at the point of change, showing its state persistently in Appearance** ("Theme: Midnight · this device only" / "· synced"). Never silently broaden scope, and let a device locally override a synced theme without un-syncing the others |
| Contrast safety net | Users will pick / author themes that make their own agent unreadable; aesthetic-usability (§3) means they may not notice immediately | **ADOPT:** compute WCAG ratios live in the picker and warn (don't silently block) when body text <4.5:1 or UI components <3:1 against the chosen background; offer the one-tap fix (adjust foreground). See §7 |

### 7. Visual polish audit basics

| Audit item | Standard / evidence | Pass criterion |
|---|---|---|
| **Alignment & grid** | Material: all components align to an **8dp square baseline grid**; type and icons to a **4dp grid**; layout grid = columns + gutters + margins — summarised at https://www.freecodecamp.org/news/8-point-grid-typography-on-the-web-be5dc97db6bc/ and https://www.netguru.com/blog/design-system-roadmap (index). Alignment is a gestalt cue: stray edges read as errors, shared edges read as grouping | Every element aligns to something; no 1–3px "almost aligned" edges; screenshot at 100% and check left edges of chat, ledger rows and settings groups form unbroken lines |
| **Spacing scale** | Tokens on an 8pt base (4 for fine adjustment), in clearly distinguishable multiplicative steps; at least three semantic tiers — within-component / between related elements / between sections (e.g. 8 / 16 / 48) — because spacing *is* the grouping signal (proximity). Sources: Material summaries above; https://ux.detroit3d.com/foundations/layout-spacing-grids.html (index) | No arbitrary spacing values in code (search for them); gap-inside-group < gap-between-groups everywhere; adding a divider/border to fix a grouping problem is a smell — fix the spacing first |
| **Contrast (WCAG)** | **WCAG 2.x SC 1.4.3 (AA): 4.5:1 normal text, 3:1 large text (≥18pt, or 14pt bold); SC 1.4.11: 3:1 for UI component boundaries and meaningful graphics; SC 1.4.6 (AAA): 7:1 / 4.5:1.** Never colour alone to convey state (1.4.1). Correctly stated at https://www.miquido.com/blog/app-accessibility-in-mobile-development-design/ (index). **Caution:** several secondary sources misstate these — verify against the W3C text | Audit **every theme** (including user themes and both light/dark) in every state: body, muted/secondary text (the most common failure), timestamps, placeholder text, disabled states, text over streaming/selection highlights, focus indicators. Muted grey timestamps are the classic chat failure |
| **Touch targets** | **WCAG 2.2 SC 2.5.8 (AA) floor is only 24×24 CSS px** (with spacing exceptions) — often misquoted as 44. **SC 2.5.5 (AAA) is 44×44.** Platform requirements are higher and are the ones to build to: **Apple HIG 44×44pt, Material 48×48dp, ~8px between targets.** Same Miquido source (index) | Build to 44/48, not to the 24px WCAG floor; the *hit area* counts, not the glyph (a 20px icon in a 48px button passes); check icon-only chat actions, ledger row actions, settings chevrons, theme swatches |
| **Scrollbars: show / hide** | NN/g *Scrolling and Scrollbars*, 5 guidelines: **(1) Offer a scrollbar if an area has scrolling content** — don't rely on drag/auto-scroll people may not notice; **(2) Hide scrollbars if all content is visible** — a visible bar promises content that isn't there; (3) Comply with GUI standards — use bars that look like bars (custom/home-made bars in NN/g testing were simply not used/recognised); (4) Avoid horizontal scrolling; (5) Put important information above the fold — https://www.nngroup.com/articles/scrolling-and-scrollbars/?lm=web-page-design&pt=course (index). **Strong** | A scrollable region must *signal* scrollability at rest on desktop: a visible (or at minimum persistent-on-hover/focus with a fade cue + cut-off content peek) bar, correctly sized thumb ∝ visible fraction. A bar that appears only mid-scroll fails touch-laptop and keyboard users and hides the ledger's length/position |
| **Overlay vs always-on / custom-styled bars** | Overlay (auto-hiding, OS-drawn) bars are the platform default on macOS/mobile and are acceptable *there* because they are the user's global setting — respect it, don't override it. Thin, low-contrast, custom-recoloured web bars are the NN/g failure mode above. `scrollbar-gutter: stable` prevents the layout shift when a bar appears | Respect the OS setting; don't ship a 4px custom bar; reserve gutter space so chat/ledger content doesn't jump sideways when a bar appears (a CLS-adjacent defect); ensure the bar is keyboard- and screen-reader-equivalent (the region itself must be focusable/scrollable, the bar is not the only path) |
| **Nested scrolling** | No single canonical study retrieved — convergent practitioner/platform guidance, **flagged as Moderate/Weak evidence**: nested scroll regions trap wheel/touch gestures, break find-in-page and scroll-restoration, make scrollbar position meaningless, and on touch create scroll-chaining fights | **Rule: one scroll container per view.** Chat transcript scrolls; the composer, header and any work-trail panel do not create competing vertical scrollers (the trail expands *inside* the transcript flow or in a non-scrolling side pane). Settings: the page scrolls, the sidebar list does not trap the wheel. Any unavoidable inner scroller (code block, table) should scroll *horizontally only*, with a visible cue |
| **Responsive failures across sizes / foldables** | Design to **window size classes, not devices** (Android/Material): width **Compact <600dp** (single column, bottom nav), **Medium 600–839dp** (navigation rail, possible second pane — a foldable half-open, a phone in landscape), **Expanded 840–1199dp** (list-detail, persistent sidebar), **Large 1200–1599 / XL ≥1600dp**. Canonical adaptive layouts: list-detail, supporting pane, feed. Foldable specifics: the **hinge/crease is off-limits** for controls and primary content; tabletop posture = content top / controls bottom; a device can change class *mid-session* on fold/unfold. Sources: Android/Material summaries, e.g. https://ux.detroit3d.com/platforms/mobile.html (index) | The signature failures to test for, in order: **(1) state loss on fold/unfold/rotate/resize** (scroll position, draft message, settings edits — "losing scroll position or form input on unfold is the signature failure"); (2) a stretched phone layout on expanded width (single column of very long lines — cap measure ~45–75ch and use the extra width for a second pane: conversation list + thread, or thread + work trail); (3) controls/content under the hinge; (4) hover-only affordances on touch widths and touch-only affordances on desktop; (5) layouts breaking at **200% text / largest Dynamic Type**; (6) a bottom tab bar persisting at expanded width where a rail/sidebar is expected, and vice versa |
| **Type & measure** | Body text must survive 200% scaling without loss (WCAG 1.4.4); long-form agent answers need a capped line length for readability (45–75ch convention, design-system sources above) | Agent answers set in a measure-capped column even on a wide desktop window; ledger/settings can use the full width, prose cannot |

## Could not verify / open questions

- **No primary evidence for a numeric "settings page breakdown" threshold**, and **no head-to-head study of live-real-UI vs static-mock theme preview**, or of **per-device vs synced theme scope**. Those recommendations are labelled inference from NN/g heuristics + platform precedent, not findings.
- **Skeleton-screen effect sizes:** NN/g supports the qualitative claim (perceived shorter wait, lower cognitive load) and cites Mejtoft et al. 2018; the widely repeated "20–30% faster" figures come from blogs with no traceable study and were **not** used.
- **Chat product specifics** (exact grouping windows, which clients show tails/avatars today) are from index-level secondary sources; iMessage/WhatsApp/Slack/ChatGPT/Claude all change these details between releases and none could be verified live in this session (accounts/devices required). Treat §4's product descriptions as conventions to re-check, while its *recommendations* rest on the structural argument (message length, authorship count) that survives version changes.
- **Doherty 400ms and Zeigarnik** are both routinely over-claimed in UX content; both are flagged Contested/Weak above and neither should be quoted to justify a design on its own.
- **Haptics evidence** is platform guidance, not independent research; the "haptics improve accuracy by up to 20%"-style claims in vendor blogs were not verified and were not used.
- Baymard Institute material was sought but no freely accessible Baymard page with settings/progress findings was retrieved in this session; no Baymard claim is made above.
