### Important — I1: Refuse a diagnostics attachment when the required known-secret scan is unavailable

**Locations:** `src/core/diagnostics/index.ts:100`, `:154`, `:199`, `:211`; production activation at `src/core/index.ts:1506`. Related contract: `docs/plans/diagnostics.md:81`–84.

`knownSecrets()` catches a vault enumeration/decryption error and returns an incomplete secret set. `buildDiagnostics()` then scrubs included metadata/log messages against that incomplete set and `diagnosticsRoutes()` returns a normal 200 attachment. A credential Nova already stores can therefore survive in an encoding that the shape layer cannot recognize. The source of the defect predates this branch, but this branch exposes it through the production endpoint, so it is a release blocker for this integration.

This is proven with the real mounted `createNova` HTTP endpoint and a real private file vault, without replacing the builder, vault, route, or scrubber:

1. A truly empty vault downloads normally: status 200, warning count 0.
2. Save a synthetic credential in the vault, and write its base64 form into an included service log message. With the readable vault, the download removes it.
3. Close Nova, move only that disposable fixture's key file aside, and start Nova again against the same fixture home. The real vault reports `ok:false`.
4. The diagnostics request returns **200**, `content-disposition` attachment and `cache-control:no-store`, with the encoded credential still present. The assertion that it must be absent fails.

The failure is **not literally silent**: `redaction.warnings` contains one warning. The warning does not prevent credential disclosure in a file advertised for sharing, and contradicts the plan's “redaction never fails open” statement and the endpoint's “every secret replaced” description. This is not a demand for a universal free-text classifier: the canary is an actual stored credential in an explicitly supported encoding. Nor is it a request to reject legitimately empty vaults.

**Required change:** treat inability to complete the required known-secret enumeration as an unsafe build and refuse the attachment before serializing included free text, with a fixed, non-sensitive error. Preserve normal empty-vault downloads. Do not simply add a warning, weaken canaries, add an arbitrary raw-secret getter, or expose raw scan errors in an unsanitized response. Update the contradictory failure-mode documentation. Add meaningful regression coverage for the mounted route with an unavailable populated vault, alongside a successful empty/readable-vault control; preserve existing encoding/excluded-store tests.

**Evidence:** `evidence/task-1/review-vault-unavailable.mjs`, `.json`, `.stdout`, `.stderr`. Run `2026-11-03T07:51:38.636240+00:00`–`07:51:39.987184+00:00`, exit **1**, from the explicit no-canary assertion. No setup failure or unexpected service call occurred. Its only printed outcome is synthetic boolean/status metadata, not a diagnostic bundle or generated private keys.
